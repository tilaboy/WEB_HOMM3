**探针必须能 RED**（本团队纪律）。故附**负测**：喂一张故意错的图，探针必须**给出 FAIL 且退出码 1**（而不是抛异常）。

### 0.0 方法学：本审计**不用 shell `grep`**（免疫一类"永远绿"的假阴性）

本脚本的查找一律走 **`node:fs` 遍历 + `node:zlib` 自解**，**不依赖 shell `grep` / `rg`**。

**原因（本档实测踩过，且已第二次更正口径）：**
- 本环境 `grep` = **`toybox 0.8.13`（非 GNU）** —— 权威识别见 `design/accessibility-requirements.md:581`。
  > ⚠️ **本档 V1 稿曾误写"BSD `grep`"，已按 `:581` 更正**（同族误标：`art-director` 也发过同一处更正，见 `accessibility-requirements.md` V1.32 尾）。
- **同一个陷阱家族**（本档 2026-09-21 实测，样本 `const b = len === 0;`）：

| 命令 | 实测 | 含义 |
|---|---|---|
| `grep -E 'alpha|beta'` | 命中 | **`-E` + 不转义的 `|` 才是交替** ✓ |
| `grep 'alpha\|beta'` | **0 命中 / exit 1** | `\|` **是字面量** ⇒ **静默空** |
| `grep -E 'a\b'` | **0 命中** | **`\b` 同样不支持** ⇒ **又一类静默空** |
| `grep -E '=== \s*0'` | 命中 | `\s` **退化成字面 `s`** ⇒ `s*` 仍匹配 ⇒ **更隐蔽** |

⇒ **凡交替与边界：用 `grep -E 'a|b'`（去掉反斜杠），且不用 `\b \s \d \w`**；否则"探针"会**恒绿**。
⇒ ⚠️ **本机无 `rg` CLI**（`command not found`）⇒ 脚本里**不能**依赖 `rg` 兜底。
> 例：`grep -rln "crest\|crestL" src/` 恒空 —— **与 `src/` 里到底有没有 crest 无关**。
> （本档据此复核过一条旧结论：`crest|立绘|纹章` 在 `src/` **确无匹配** —— 结论成立，但原方法无效、已换 ripgrep。）

> 修一处自己的错：首版负测**抛 `TypeError`**（RGBA 图没有 `PLTE`，脚本解引用 null）——**这不是合格的 RED**。
> 已改为"非索引色 ⇒ 记一条 FAIL 并跳过槽位分析"，负测才是干净的 RED。

### 1.1 一条口径澄清：`24 色` 与 `23 色` **不是同一个量**

`§6.1.1` 交叉验证行写着「对方 **5704 B / 24 色**」「本档 **5724 B / 23 色**」。这两个数**都对**，但**必须标口径**，否则会被读成"同一个量的两个值"：

| 口径 | 值（对 5704 B 那张） | 定义 |
|---|---|---|
| **(A) PLTE 槽位数** | **24** | 调色板表长度；**24 个槽位全被引用，且 24 个相异 RGB** |
| **(B) 不透明区相异 RGB** | **23** | 只统计 alpha ≥ 128 的像素 ⇒ **少的那 1 个 = 透明底那一槽** |

⇒ 两种实现的 `24` / `23` 是**各自的调色板 cap**（`reduceColors(…,24)` vs `capColors(…,23)`），**同口径、可比**。
⇒ 但只要有人拿 (A) 去比 (B)，就会得出"差 1 色"的假矛盾。**已在审计里把两者分开断言（各 1 条）**。

## 2. ★ 头条发现：「打开游戏第一眼」现在是 **Capacitor 的默认占位图**

用户原话点名的就是**这个位置**。它**不是 Web 资源**（不受"零位图不变量"约束），它是**原生启动图**，随 APK 出。

| 项 | 实测 |
|---|---|
| 文件 | `homm-web/resources/splash.png` = **2732×2732**、`colorType=6`（RGBA-32）、**161 021 B** |
| 内容 | **Capacitor 出厂占位**：深底 + **绿色等距方块 + 一面小旗** —— **与本作美术无关** |
| `splash-dark.png` | md5 **与 `splash.png` 逐字节相同** ⇒ "暗色版"**没有单独设计**，就是同一张 |
| `res/` 下的源文件 | `android/.../res/` 下 **26 个 splash 变体**，合计 **704 111 B（687.6 KB）** |
| **APK 内实际条目** | `app-debug.apk`（**5 216 926 B**，md5 `152854993233…`，mtime **2026-09-21 10:29:24** —— 与决策书 §7 同一构建）里 **30 个 splash 条目，合计 707 025 B（690.5 KB）** |

**⇒ 这一格占 APK 的 13.55%**（707 025 / 5 216 926）。

**为什么这条重要（两条）**：

1. **它直接解释用户的抱怨。** 冷启动时**满屏**给玩家看的第一张图，是一颗**跟游戏无关的绿方块**。
   "打开游戏第一眼""画面也没什么提升" —— 这一格目前**根本不是本作的美术**，谈不上"提升"。
2. **它反转了"位图 = 涨体积"的直觉（仅对这一格）。** 把它换成**像素风 PNG-8**（大色块 / 少色 / 大片纯色底），
   源图与 30 个条目**都会变小** —— 本作自己的 (b) 立绘 256×384 才 **5704 B**。
   ⇒ **对"启动图"这一格，走位图是省体积，不是涨体积。** 这是"门面类位图"与"游戏内位图"的**又一个不对称**。
