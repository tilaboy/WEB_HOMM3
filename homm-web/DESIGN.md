# 《魔法门之英雄无敌 II》风格网页策略游戏 — 项目设计文档

版本 v1.2 ｜ 状态：M1、M2 已交付 ｜ 目标：分 4 个里程碑交付一个可在浏览器里玩通的完整策略游戏

---

## 一、项目目标与范围

复刻 HOMM2 的核心循环：**探索地图 → 积累资源与军队 → 攻城略地 → 英雄成长**。

### 设计原则

| 原则 | 说明 |
|---|---|
| 逻辑与渲染分离 | `core/` 是纯 TypeScript、零 DOM 依赖的规则引擎；`render/` 与 `ui/` 只负责画。好处：战斗解算器可以在无动画模式下跑（M1 的"预估损失"就是这么来的），M3 只做可视化接入。 |
| 数据驱动 | 兵种、建筑、宝物、魔法、地形全部是配置表（`core/data/*.ts`），加内容不改代码。 |
| 无美术依赖可跑 | 所有图形先用 Canvas 程序化绘制 + 纯色/几何图形占位，后续可无缝替换为真素材。 |
| 纯前端、可存档 | 无后端，状态存 `localStorage`，单页面可离线玩。 |

### 明确不做（本期）

- 多人/AI 势力对抗（M1–M4 只做**一个玩家 + 中立野怪 + 空城/敌城占位**，M5 再考虑 AI 领主）
- 士气 / 幸运 / 英雄技能树 / 外交（列入"后续扩展"）
- 音效与动画特效（留接口，不实现）

## 二、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite | 冷启动快，配置为零，TS 开箱即用 |
| 语言 | TypeScript（strict） | 数据模型重（英雄/兵种/建筑/魔法互相引用），类型是刚需 |
| 地图渲染 | Canvas 2D | 格子数量多、需缩放/平移/迷雾遮罩，DOM 扛不住 |
| UI 层 | 原生 HTML + CSS 覆盖层 | HOMM2 的 UI 是大量固定面板（资源栏、英雄面板、城建窗口），DOM 比 Canvas 好维护 10 倍 |
| 状态管理 | 单个 `GameState` 对象 + 事件总线 | 规模不需要 Redux；`core/events.ts` 负责通知 UI 刷新 |
| 地图视角 | **2:1 等距菱形**（斜 45°） | ✅ 已确认。视觉目标对齐《The Battle of Polytopia》：扁平色块 + 方块"挤出厚度"的 low-poly 感，不要精细贴图。等距只影响渲染层，`core/` 逻辑仍按矩形网格运算 |
| 存档 | `localStorage` + JSON 序列化 | 版本号字段 `saveVersion`，反序列化时做迁移 |

**为什么不用 React/Vue**：本项目 95% 的屏幕面积是一张 Canvas，剩下的是十来个模态面板。引入框架带来的收益远小于它增加的心智负担。

## 三、里程碑路线（对应你的四步）

| 里程碑 | 内容 | 产出（可玩闭环） |
|---|---|---|
| **M1** 探索 | 等距地图生成、英雄、**弓手（单一兵种）**、移动与寻路、迷雾、地图交互（野怪/宝物/泉水/资源）、**无动画战斗解算 → 预估损失** | 能操控英雄在 24×24 地图上跑一整天，打野、捡钱、喝泉水 |
| **M2** 城建 | 资源系统、城镇建筑树、兵种生产与周增长、多兵种解锁 | 能占城 → 造兵营 → 攒兵 → 滚雪球 |
| **M3** 战斗 | 战斗场景（六边形/方格战场）、回合制指令、伤害公式、英雄攻防加成 | 打野变成一场可操作的真战斗 |
| **M4** 魔法 | 魔法书、魔法值、战斗魔法 + 冒险魔法 | 英雄从"数值挂件"变成"战术核心" |
| **M5** 多阵营 | 开局设置页、4 阵营 / 3 档难度、独立迷雾、电脑对手、胜负判定；**M5.2** 城镇升级为 2×2 城堡（只能从正面进城） | 一局真正的 4 人争霸，且四家的城在视觉与规则上都"有门" |

每个里程碑都是**独立可玩**的：M1 结束时游戏就已经是一个完整的小游戏了。

## 四、核心数据模型

### 4.1 资源

```ts
type ResourceKind = 'gold' | 'wood' | 'ore' | 'gem' | 'crystal' | 'sulfur' | 'mercury';
type ResourceBag = Partial<Record<ResourceKind, number>>;  // 金币量大，木石次之，稀有资源个位数
```

M1 只用 `gold`；M2 城建时启用 `wood`/`ore`；稀有资源留给 M4 的魔法行会与高级建筑。

### 4.2 兵种与军队

```ts
interface UnitType {
  id: string;
  name: string;
  tier: 1 | 2 | 3 | 4 | 5;        // 1 最弱
  attack: number;
  defense: number;
  damageMin: number;
  damageMax: number;
  hp: number;
  speed: number;                   // 战场行动顺序 + 地图移动加成
  shots?: number;                  // 有值 = 远程
  isFlying?: boolean;
  growthPerWeek: number;           // 城镇周增长基数
  cost: ResourceBag;
  spriteKey: string;               // 程序化绘制用的图元标识
}

interface Stack {                  // 英雄军队里的"一坨"兵
  unitTypeId: string;
  count: number;
}

type Army = Stack[];               // 最多 5 个 slot（HOMM 传统）
```

**M1 只配 1 个兵种：`Archer 弓手`** ✅ 已确认

```ts
{ id: 'archer', name: '弓手', tier: 2,
  attack: 4, defense: 2, damageMin: 2, damageMax: 3,
  hp: 10, speed: 4, shots: 12,
  growthPerWeek: 5, cost: { gold: 100 } }
```

选弓手而非农民的理由：农民（ATK 1/HP 3）打初级野怪都要掉一大半兵，M1 第一小时的体验会很挫败；弓手是远程单位，能让玩家第一天就体会到"站位"的乐趣，也顺带验证了远程逻辑，M3 做战斗场景时省事。

M2 补齐 5 级：`弓手 → 枪兵 → 骑士 → 天使`（数值对齐 HOMM2 骑士城，略有简化，农民降为 tier 1 可造但不再作为起手兵）。

### 4.3 英雄

```ts
interface Hero {
  id: string;
  name: string;
  heroClass: 'knight' | 'sorceress';       // M1 先给骑士
  level: number;
  exp: number;
  primary: { attack: number; defense: number; spellPower: number; knowledge: number };
  mana: number; manaMax: number;           // M4 启用
  movePoints: number; movePointsMax: number;
  army: Army;
  artifacts: Artifact[];                   // 上限 14（HOMM 传统）
  spells: string[];                        // M4 启用
  pos: { x: number; y: number };
  owner: PlayerId;
}
```

**主属性规则**（HOMM2 风格）：
- 攻击力 = 给全军 `+N` 攻击，防御力 = 给全军 `+N` 防御
- 升级：每级随机 +1 到某一主属性；经验阈值 `100 * level * 1.2^(level-1)`
- 升级时弹出 2 选 1 的属性/技能选择（M1 简化为随机 + 提示）

### 4.4 地图

```ts
type TerrainKind = 'grass' | 'dirt' | 'sand' | 'snow' | 'swamp' | 'water' | 'rock';

interface Tile {
  terrain: TerrainKind;
  moveCost: number;        // 草地 100 / 泥路 125 / 沙地 150 / 雪地 150 / 沼泽 175 / 水面不可通行
  objectId: string | null; // 指向 MapObject
  passable: boolean;
}

interface GameMap {
  width: number; height: number;   // M1: 32 × 32
  tiles: Tile[];                   // 一维数组，index = y * width + x
  objects: Record<string, MapObject>;
}
```

**地图尺寸**：✅ 已确认为 **24 × 24 = 576 格**（"小而精"路线）。

理由：576 格在等距视角下一屏能看全约 1/3，跑完一圈约 3–4 天，节奏紧凑不注水；同时格数足够放下 12 组野怪形成难度梯度。尺寸是 `data/` 里的配置项，随时可改 32/48 而不动逻辑。

### 4.5 地图物件（Adventure Map Objects）

统一用**可访问点（visitable）**抽象 —— 这是 HOMM 系列的精髓：所有交互都是"英雄站到那个格子上"。

```ts
type MapObjectKind =
  | 'resourcePile'    // 资源堆（金/木/石）
  | 'treasureChest'   // 宝箱：金币 或 宝物
  | 'artifact'        // 地面宝物（有守卫）
  | 'fountain'        // 泉水：当日移动力 +X
  | 'wanderingMonster'// 野怪：战斗
  | 'town'            // 城镇
  | 'mine'            // 矿场：占领后每日产资源
  | 'dwelling'        // 野外招募点
  | 'obstacle'        // 树/山/岩石：纯阻挡装饰
  ;

interface MapObject {
  id: string;
  kind: MapObjectKind;
  pos: { x: number; y: number };  // 可交互格；多格物件里它是唯一的入口格
  footprint?: { x: number; y: number }[]; // 多格物件的全部占地（含 pos）
  payload: object;        // 按 kind 变化：野怪存 Army，宝箱存 gold/artifactId，矿场存 kind+daily
  once: boolean;          // 访问后是否消失（宝箱 true，城镇 false）
  visitedBy: PlayerId[];
}
```

> `footprint` 是 M5.2 加的：2×2 城堡占四格，但只有 `pos`（城门）能站人。
> 单格物件不设置这个字段，行为与以前完全一致。详见第十七节。

**M1 地图物件配比**（24×24 = 576 格，水域约 15%，陆地约 490 格）

| 物件 | 数量 | 说明 |
|---|---|---|
| 野怪 | 12 | 分 3 档难度（弱/中/强），随距出生点距离递增；4 弱 / 5 中 / 3 强 |
| 宝箱 | 8 | 1000–3000 金，20% 概率给宝物 |
| 资源堆 | 24 | 金堆 / 木堆 / 石堆，各 8 |
| 泉水 | 3 | 当日移动力 +50% |
| 城镇 | 2 | 1 座己方起始城 + 1 座中立城（M2 后可攻占）；M5.2 起每座城占 2×2 |
| 障碍 | ~70 | 树/岩石/山，纯装饰 + 阻挡 |

### 4.6 城镇（M2）

```ts
interface Town {
  id: string;
  name: string;
  pos: { x: number; y: number };
  owner: PlayerId | 'neutral';
  buildings: Set<string>;
  garrison: Army;                       // 驻军
  growthPool: Record<string, number>;   // 未招募的累积兵（每周刷新）
  buildQueueLockedOnDay: number;        // 每天只能造 1 座
}

interface Building {
  id: string; name: string;
  cost: ResourceBag;
  requires: string[];      // 前置建筑
  effects: BuildingEffect[]; // 产金 / 解锁兵种 / 提高增长 / 加防御
}
```

**建筑树（M2 已实现，共 12 座，酒馆预置）**

```
Tavern 酒馆（预置）
  └─ 每周可招募 1 位英雄（2500 金）
Marketplace 市场 (500g + 5wood)
  └─ 资源交易：1000 金 → 5 木/矿；5 木/矿 → 500 金
Town Hall 议事堂 (1500g + 10wood + 5ore)
  └─ 每日 +250 金
Fortification 城防线（防御取最高档，不叠加）
  ├─ 木栅 (1000g + 10wood)        → 驻军 DEF +2，每日 +100 金
  ├─ 石墙 (2500g + 10ore)         → 驻军 DEF +4，每日 +200 金
  └─ 堡垒 (5000g + 10wood + 15ore) → 驻军 DEF +6，每日 +400 金，全城周增长 +25%
Dwelling 兵营（每兵种一级，周增长可叠加累积）
  ├─ 农舍 (300g + 5wood)          → 解锁农民，+10/周
  ├─ 射箭场 (1000g + 5wood + 5ore) → 解锁弓手，+5/周
  ├─ 兵营 (2500g + 10ore)         → 解锁枪兵，+4/周
  ├─ 马厩 (5000g + 10wood + 10ore) → 解锁骑士，+3/周
  └─ 圣殿 (9000g + 10wood + 20ore) → 解锁天使，+2/周
```

**周增长规则**：每周一（第 8、15、22…天），`growthPool[unit] += Σ(各兵营 baseGrowth) × (1 + 堡垒 25%)`，兵在池中**累积**直到被招募。招募时按 `unit.cost × 数量` 扣金币，从 pool 扣减。英雄部队上限 5 个兵种槽位（HOMM 规则）。

**城镇税收**：每座己方城每日基础 +500 金，加上议事堂/城墙线的加成。

**攻占中立城**：走进中立城 → 弹「预估损失」攻城确认框（守军含城墙防御加成）→ 胜则城镇易主、驻军清空、自动补上酒馆并可开始建设；空城可直接接管。

## 五、关键系统设计

### 5.1 移动与寻路

- **移动力**：每格消耗 = `tile.moveCost`（草地 100）。英雄 `movePointsMax = 1500`（≈ 15 格草地）。对角线消耗 × 1.4。
- **寻路**：Dijkstra（8 邻域，见 `core/map/pathfinding.ts` 的 `computePaths`）。目标：点击地图任意可达格 → 计算路径 → 沿路径逐格动画移动，每步扣移动力。**遇到野怪自动停下并弹确认框**。
- **多格物件**：`isPassable()` 对带 `footprint` 的物件只认 `pos` 那一格可通行，其余占地格一律阻挡。所以 2×2 城堡天然只有城门能进，寻路不需要任何特例（详见第十七节）。
- **迷雾（Fog of War）**：每个玩家维护 `revealed: Uint8Array`。英雄视野半径 = `5 + 侦察术加成`。移动时实时更新。迷雾区渲染为纯黑，`explored but not visible` 区域渲染为半暗（地形可见、物件不可见）。
- **移动力恢复**：新的一天 `movePoints = movePointsMax`；泉水可临时超出上限（`overflow` 标记，第二天重置）。

### 5.2 等距渲染与坐标换算（Polytopia 风格）

**关键约定：`core/` 完全不知道等距的存在。** 逻辑层一律用 `(x, y)` 整数格子坐标，A*、迷雾、距离计算全部按矩形网格走。等距只存在于 `render/` 的一个换算函数里。

**2:1 等距换算**（菱形宽 64px、高 32px，即 `TILE_W = 64, TILE_H = 32`）

```ts
// render/iso.ts
export const TILE_W = 64, TILE_H = 32;

// 格子 → 屏幕（菱形顶点在上的中心点）
export function gridToScreen(x: number, y: number) {
  return { sx: (x - y) * (TILE_W / 2), sy: (x + y) * (TILE_H / 2) };
}

// 屏幕 → 格子（点击拾取，向下取整）
export function screenToGrid(sx: number, sy: number) {
  const a = sx / (TILE_W / 2), b = sy / (TILE_H / 2);
  return { x: Math.floor((b + a) / 2), y: Math.floor((b - a) / 2) };
}

// 菱形四顶点（用于绘制地块顶面）
export function diamond(sx: number, sy: number) {
  return [
    [sx, sy - TILE_H / 2], [sx + TILE_W / 2, sy],
    [sx, sy + TILE_H / 2], [sx - TILE_W / 2, sy],
  ];
}
```

**遮挡排序**：按 `depth = x + y` 升序绘制（y 小 x 小的先画，即"远"的先画）。物件与单位插入到所在格的深度序列里，保证站在格子上的单位盖住它后面的地形。

**视觉构成（Polytopia 的精髓：挤出厚度）**

每个地块画三部分，就能立刻有 low-poly 立体感：

```
      ◇  ← 顶面：地形主色（草地 #7FA650 / 沙地 #E0C68C / 水面 #4A90C2 ...）
    ▰▰▰▰  ← 左侧面：主色 × 0.75 暗化，高 8px（可配置 THICKNESS）
    ▰▰▰▰  ← 右侧面：主色 × 0.55 更暗
```

- 顶面边缘描 1px 半透明白，缝隙感立刻出来
- 单位/物件：不用贴图，画**几何剪影**——弓手 = 一个圆头 + 梯形身体 + 一条弧线弓，用队伍色描边区分敌我
- 选中格：顶面覆盖 30% 白色 + 描金色边框
- 可移动范围：走 A* 拿到所有 `cost <= movePoints` 的格子，顶面叠一层淡蓝

**摄像机**：`camera.ts` 维护 `{ offsetX, offsetY, zoom }`，zoom 范围 0.5–2.0，绘制时统一 `ctx.translate/scale`。屏幕坐标要先减 offset、除 zoom 再喂给 `screenToGrid`。

**性能**：576 格 × 3 面 = 1728 个多边形/帧，Canvas 2D 在手机上轻松 60fps。稳妥起见做**视口裁剪**——只画屏幕矩形外扩 2 格范围内的地块。

### 5.3 战斗解算器 —— M1 与 M3 的桥梁（核心设计）

这是整个架构最关键的一处决策：

```
combat/solver.ts   ← 纯函数：输入双方 Army + 英雄属性，输出 BattleResult（含每方剩余兵力）
     │
     ├─ M1 用法：headless 跑一遍 → 得到损失 → 弹窗显示"预估损失：轻微/中等/惨重/全灭"
     │           玩家点「确认战斗」→ 直接套用结果，无动画
     │
     └─ M3 用法：同一套 solver 改为**逐回合产出事件流**（BattleEvent[]）
                 UI 层消费事件流播动画，逻辑零改动
```

**伤害公式（HOMM2 近似）**

```ts
function computeDamage(attacker: Stack, defender: Stack, atkBonus: number, defBonus: number) {
  const A = unitType(attacker).attack + atkBonus;   // atkBonus = 英雄攻击力 + 宝物
  const D = unitType(defender).defense + defBonus;
  const base = randInt(damageMin, damageMax) * attacker.count;
  let mod = 1 + 0.05 * (A - D);
  mod = Math.min(Math.max(mod, 0.3), 3.0);          // 封顶 ±3 倍 / 0.3 倍
  if (isRanged && dist > 10) mod *= 0.5;            // 远程惩罚
  if (isRanged && adjacentEnemy) mod = 0;           // 近身不能射（需先"射击惩罚"处理）
  return Math.max(1, Math.round(base * mod));
}
```

**解算流程**（无动画版）：
1. 按 `speed` 降序建立行动序列
2. 每单位行动：远程且有弹药 → 射击；否则 → 移动到最近敌人 → 近战
3. 反击：被近战攻击且未死亡 → 反击一次（每回合限一次）
4. 直到一方全灭或跑满 20 回合（判平）

**损失分级 → 玩家提示文案**

| 损失比例 | 显示 |
|---|---|
| 0% | 完胜，无损 |
| < 15% | 轻微损失 |
| 15–40% | 中等损失 |
| 40–70% | 惨重损失 |
| > 70% | 几乎全灭 |

M1 还给玩家「**撤退**」按钮（保留 60% 兵力，英雄当日行动结束）。

### 5.4 战斗场景（M3）

| 项 | 设计 |
|---|---|
| 战场 | **12 × 10 方格**，同样用等距菱形渲染，左右两侧各一列出生区 |
| 回合制 | ATB：按 `speed` 排序的行动条，speed 高的先动；每单位每回合 1 次行动 |

### 5.5 魔法（M4）

```ts
interface Spell {
  id: string; name: string;
  level: 1|2|3|4|5;
  school: 'fire'|'water'|'air'|'earth';
  manaCost: number;
  target: 'enemyUnit'|'allEnemy'|'ownUnit'|'allOwn'|'tile'|'global';

```

**战斗魔法（12 个）**：Magic Arrow、Lightning Bolt、Fireball、Ice Bolt（伤害类）；Bless(+3 ATK)、Curse(-3 ATK)、Haste(+SPD)、Slow(-SPD)、Shield（远程伤害减半）、Bloodlust、Stone Skin、Resurrection（复活 20%/点）

## 十二、交付形态：Web + PWA（为什么不做原生 App）

### 体积与加载评估

| 项 | 估算 |
|---|---|
| 自研 JS（M1–M4 全部，零运行时依赖） | 150–250 KB 未压缩 → **gzip 后 40–70 KB** |
| HTML + CSS | < 15 KB |
| 图片 / 字体 / 音频资源 | **0**（全部程序化绘制） |
| **首屏下载总量** | **约 60–90 KB** |
| 4G 首屏可交互 | < 1 秒 |
| 单局存档 | 3–8 KB JSON（localStorage 上限 5 MB） |
| 运行时帧预算 | 576 格 × 3 面 ≈ 1728 多边形/帧，手机 60fps 无压力 |

对比参照：Flutter "Hello World" 的 Android 包 ≈ 15 MB；含素材的商业手游 100 MB–2 GB。**本项目比任何原生 App 小三个数量级**，原因就是没有美术资源包。

### 为什么 Web 优于原生 App

| 维度 | Web + PWA | 原生 App |
|---|---|---|
| 迭代速度 | 改完刷新即可 | 需重新编译打包 |
| 分发 | 一个链接 / 加到主屏幕 | 应用商店审核 |
| 跨平台 | 桌面 + iOS + Android 一套代码 | 至少两套 |
| 环境依赖 | 浏览器 + Node | Xcode / Android SDK |
| 离线可玩 | ✅ Service Worker | ✅ |
| 主屏幕图标 | ✅ Web App Manifest | ✅ |

唯一需要额外付出的，是**交互层从第一天就要同时支持鼠标和触摸**（已在 §七 给出映射表）。这个成本远小于维护两套原生工程。

### PWA 接入时机（M1 结束时，约 1 小时工作量）

```
public/
├── manifest.json       name / icons / display: standalone / theme_color
├── icon-192.png        程序化生成的图标
├── icon-512.png
└── sw.js               预缓存 index.html + 打包产物，cache-first
```

`index.html` 加 `<link rel="manifest">` 与 `navigator.serviceWorker.register('/sw.js')`；同时设 `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no">` 与 `touch-action: none` 防掉双指缩放与页面滚动冲突。

### 如果将来真的想要原生 App

`core/` 是零 DOM 依赖的纯 TypeScript，可以原样打包进 Capacitor / Tauri 壳子里，渲染与 UI 层复用 WebView，改造成本极低。**先把 Web 跑通，是最省的一条路。**

## 十四、M3：六边形战术战斗（已实现）

### 14.1 战场

| 项 | 取值 | 说明 |
|---|---|---|
| 网格 | **15 × 11 六边形**，pointy-top + odd-r 偏移 | 比 HOMM2 的 13×9 稍大，给远程与包抄留空间 |
| 单格 | 外接圆半径 22px，横间距 38、纵间距 33 | 地砖/高亮/单位全部烘焙进独立战斗图集 |
| 布阵 | 我方贴 col 0，敌方贴 col 14，各部队沿一列均匀铺开 | 最多 5 支（`MAX_STACKS`） |
| 缩放 | 画在 603×388 的基准位图上，再按容器整体放大 | 优先整数倍；差一点时退回小数倍，并乘 DPR |

### 14.2 规则

- **回合**：每回合按 `speed` 降序建行动序列（同速攻方先、建队序号先后），全员各动一次。
- **一回合可以「移动 + 攻击」，但不能移动两次**（`moved` 标记）。
- **近战**：相邻格；防守方每回合限反击一次，伤害 ×0.5。
- **射击**：全场可射，但 ① 被敌人贴身时不能放箭，② 弹道被其他单位挡住伤害 ×0.5，③ 距离 > 10 格（`LONG_RANGE`）抛射伤害 ×0.5。
- **防御**：防守 +3，持续到下次行动；**等待**：挪到本回合行动序列末尾。
- **血量模型**：`总血量 = (count-1) × hp + hpTop`，伤害先啃队首残血，再整只整只地死——击杀数因此是真实整数。
- **撤退**：战场上点「撤退」→ 立即结束，世界层按"撤退"处理（折损四成、退回上一格、当日不能再动）。
- 上限 40 回合，超时判攻方失败。

### 14.3 唯一规则来源（重要）

M1 的无位置 `solver.ts` 已删除。现在 **战斗规则只有 battle.ts 一份**：

```
quickBattle()  = createBattle + autoResolve（AI 双方对打，一帧跑完）
  ├─ 战前「预估」弹窗  ← quickBattle
  ├─ 战场上「自动战斗」← 同一颗种子，结果 = 预估
  └─ 亲手指挥          ← 同一套规则 + 同一颗种子，只是由你下指令（通常打得更好）
```

好处：预估不再"吓唬人"，玩家看到的数字就是 AI 打出来的数字。

### 14.4 数值（用 quickBattle 实测，200 场/档）

起手 20 弓手（攻 1 防 2）：

| 档位 | 规模 | 胜率 | 平均损失 | 平均回合 |
|---|---|---|---|---|
| 弱 | 20~28 野狼 | 100% | 11% | 3.4 |
| 中 | 11~15 野猪 或 18~26 狼 + 4~7 猪 | 93% | 26% | 5.8 |
| 强 | 10~13 食人魔 或 7~10 猪 + 5~7 魔 | 56% | 71% | 8.1 |
| 绝望 | 22 食人魔 | 0% | 100% | — |
| 中立城 | 20 野狼 + 10 野猪 | 83% | 61% | — |

> 野怪规模是按战术战场重新标定过的：起手弓手在 15 宽的战场上能白嫖 3~4 轮射击，
> 所以怪必须扛得住那几轮才有威胁。超远距离减半就是为此加的。

## 十六、M5：开局设置 + 电脑对手（已实现）

### 16.1 开局设置页

打开页面先停在设置页，而不是直接开一局随机地图。可选项：

| 项 | 取值 | 说明 |
|---|---|---|
| 领主名字 | 自由文本（≤12 字） | 同时作为第一位英雄的名字 |
| 地图尺寸 | 小型 24×24 / 中型 32×32 / 大型 40×40 | 物件数量按面积 `k = w·h / 32²` 缩放 |
| 电脑对手 | 0 ~ 3 | 对手越多中立城越少：`max(2, round(3k) − round(opp/2))` |
| 难度 | 轻松 / 普通 / 困难 | 只影响 AI：起始资源倍率、周增长加成、出兵门槛 |
| 地图种子 | 整数，可随机 | 同种子 + 同设置 → 完全同一张地图 |

右侧是**实时小地图预览**：直接调用 `createGame(当前设置)` 拿到真实地图，把地形色块铺出来，
各阵营主城用阵营色方块标出、中立城画成空心方块。看到什么就玩到什么，不会出现"预览和实际不一样"。

### 16.2 阵营与主城布局

四个阵营（晨曦军团 / 赤焰部落 / 翠林守望 / 紫晶密会）只做配色与命名区分，兵种、建筑、价格完全共用。

主城布局是 `pickHomeSpots()`：围绕地图中心按 `radius = 0.35 · min(w,h)` 均分成正多边形，p1 从正左方出发。
关键在于**整体旋转 + 整体平移**，而不是每家各自随机 —— 任意两家的相对距离在每一局里严格相等，
谁也不会抽到更近的邻居；但整张布局随种子旋转，所以每局的开局位置又不一样。

选点还会避开"只有一格宽的缝"（要求 4 邻域里至少 3 格可通行）。

### 16.3 电脑对手（`core/game/ai.ts`）

设计目标不是聪明，而是**可信**。每天每个 AI 阵营按固定顺序做四件事：

1. **建造** —— 按优先级表挑第一座建得起的（每城每日限一座，和玩家同一条规则）。
2. **贸易** —— 有市场且存款 ≥ 4000 时，把木/矿补到 25 的库存。
3. **征兵** —— 英雄在城里就补进部队，否则补进驻军。
4. **推进** —— 英雄按候选目标打分选一个，沿最短路径走过去。

候选目标的打分（分值越高越优先）：

| 目标 | 分数 |
|---|---|
| 敌方/中立城镇 | `620~760 × min(1.6, 兵力比)`，兵力比 < 0.85 直接不考虑 |
| 野怪（有守卫） | `240 + 守卫价值 + 档位×40`，**先跑一遍 `previewInteraction`，打不赢就不去** |
| 宝物 / 宝箱 / 资源堆 | 200 / 170 / 100~130 |
| 敌方英雄 | `820 × min(1.5, 兵力比)`，兵力比 < 1.15 不考虑 |
| 迷雾边缘（探索） | `90 + 离家距离×3 − 路程×0.03` |
| 回城补给 | 增长池有兵或部队打残时 400+ |

三个关键约束：

- **不透视迷雾。** 所有非探索类目标都要求 `isRevealed(state, player, x, y)`。这一条是"AI 会不会第一天就冲到家门口"的分水岭 —— 加上它之后，AI 变成先向外探索、沿途捡东西、撞上谁打谁。
- **不送兵。** 打不赢的守卫、城镇、英雄一律跳过；`aiMarch()` 在每一格落地前都会再判一次，打不过就原地停住。
- **不作弊。** 税收、矿场、建筑树、征兵价格、移动力，全部调用和玩家同一批函数（`build/town`、`hireHero`、`claimGuard` 里的那套）。

战斗分两种：**玩家参与的仗进战术战场**，AI 与野怪/城镇/其他 AI 的仗用 `quickBattle()` 无头结算，
结果同样是唯一规则源，不会出现"预估和实战不一致"。

### 16.4 难度

| 难度 | 起始资源倍率 | 周增长加成 | 出兵门槛倍率 |
|---|---|---|---|
| 轻松 | 0.75 | 0 | 1.35 |
| 普通 | 1.00 | +10% | 1.00 |
| 困难 | 1.40 | +30% | 0.75 |

出兵门槛基准是 200 血（起手 20 弓手的血量）。**难度不削弱玩家**，只让 AI 发育得更快、更早出门。

### 16.5 胜负

`isEliminated()` 的判据是「**城镇和英雄都没了**」——
只要还剩一座城，玩家就能在酒馆重新雇一位英雄翻盘，所以不能按"英雄全灭"直接判负。
每次世界状态变化后调 `evaluateOutcome()`：玩家出局 → 失败；其余阵营全部出局 → 胜利。
结算面板会列出每个阵营的城数、将数与是否已出局。

### 16.6 实测（Node 里跑 120 天长局）

`core/` 零 DOM 依赖，所以可以直接在 Node 里空过上百天做回归：

- 简单档 120 天：AI 拿下 4 座城、2 位英雄，建筑停在 `market` 一档 —— 缓慢但确实在发育。
- 普通档 120 天：AI 走完整条建筑线（`dwell5 / wall3 / guild3` 全部建成），玩家主城未被攻破。
- 难度确实单调：困难档 AI 平均比轻松档早 20~25 天打到玩家城下（同种子对比）。

### 16.7 踩过的坑

- **AI 第一天就冲主城。** 早期目标打分里"敌方城镇 = 900 分"权重过高，加上 AI 能看穿迷雾，开局两三天就打到家门口。修复 = 目标必须已在 AI 的迷雾视野里 + 探索目标独立成一类。
- **AI 卡在 `dwell4` 的 10 木上。** 木/矿只有矿场能产，而矿场基本被中档以上的野怪守着。建造顺序里把 `market` 提到高阶兵营之前，再补上"缺木就买"，AI 才有后半程。
- **主城位置每个种子都一样。** 原来的选点是从地图中心按固定角度取"最近的陆地格"，几乎总是命中同一批格子。改成整体旋转+平移后每局都不同，同时保持四家的相对距离严格相等。
- **旧 smoke 断言写死了方向。** 若干断言用 `{x, y-1}` 当撤退落点、或依赖"第一支野怪一定很弱"。地图布局一变就红。已改成动态找可站立格 / 先摆兵力再取 `battleSetup`。

## 十七、M5.2：2×2 城堡（占 2×2、只能从正面进）

需求来自最初的四条方向里第 3 条：「调节城堡的站位，只能从正面进，占 2×2」。

### 17.1 不变量

只有一条核心不变量，其余都是它的推论：

> **多格物件的 `pos` 必在 `footprint` 内，且是其中唯一可通行的格子。**

对城堡来说 `pos` 就是**城门**。三条推论：

1. 寻路（`computePaths` → `stepCost` → `isPassable`）只能把英雄送到城门；
2. 渲染、存档、`objectAt()`、AI 目标打分全都不需要为"多格"写特例 —— 它们本来就只看 `pos`；
3. 攻城/进城判定的入口点没有变化，仍是 `hero.pos === obj.pos`。

### 17.2 几何：城门固定在左下角

```ts
const CASTLE_W = 2, CASTLE_H = 2;

castleAnchor(gate) → { x: gate.x, y: gate.y - 1 };   // 城门 → 2×2 左上角
castleCells(gate)  → [左上, 右上, 左下(=gate), 右下];
```

城门**永远**在左下角，也就是正面朝南（屏幕下方），和 HOMM2 的城堡一样永远面向镜头。
这样美术只需要一套精灵，不用为四个朝向各画一遍。

"只能从正面进" 是几何自然结果，不是特判：城门格的正交邻居里，北和东都在占地内 → 被挡；
只剩西、南两个方向能站人，再加上斜向的西南。所以打到城门的路只有正面那一条。

### 17.3 通行规则

`core/map/grid.ts`：

```ts
export function isPassable(map, x, y): boolean {
  const obj = ...;                       // tile.objectId
  if (!obj) return true;
  if (obj.footprint) return obj.pos.x === x && obj.pos.y === y;  // 多格：只有入口
  return !obj.blocking;                                          // 单格：照旧
}
```

注意 `blocking` 对城堡刻意留 `false`：它不是"障碍物"，而是一个入口被封住的建筑。
把三面墙做成 `blocking: true` 的独立障碍会多出三个物件、三份存档体积，还会让
"这座城是谁的"散落在四个 id 上，得不偿失。

### 17.4 选址校验

```ts
gateOpenings(gate) = 西 / 南 两个外侧正交邻居里有几个能站人
castleRoom(gate)   = 2×2 外圈 21 格里能站人的格数（观感偏好，非硬条件）
castleFits(map, gate) = 四格都在界内 && 都是无主可通行地形 && gateOpenings ≥ 1
```

`gateOpenings ≥ 1` 是硬条件，也是这次最容易被忽略的一条：**没有开口就等于英雄被自己家的
城墙关在门外，那座城等于不存在**，比"城挤在角落"严重得多。

`pickHomeSpots()` 从 `castleFits` 通过的格子里挑，并保持原有的"整体旋转+平移"对称性；
候选不够就返回空数组，交给 `buildGame` 换偏移种子重掷地形。
`pickTownSpots()` 增加一个 `fits` 谓词参数给中立城复用同一套校验。

### 17.5 放置顺序（踩过坑，顺序是有讲究的）

```
1. pickHomeSpots()                      只算坐标，不落地
2. addCastle() × 阵营数                  ← 先落主城
3. pickTownSpots(fits = castleFits)      ← 此时 castleFits 已经能"看见"主城占地
4. addCastle() × 中立城数
5. 英雄出生点：从城门往外退 1~2 圈找空地
6. 连通性复核：从 1 号英雄 4 邻域 BFS，所有城门 + 英雄出生点都得可达，否则重掷
```

第 2 步必须在第 3 步之前。反过来写的话，`castleFits` 检查的是一张还没有主城的地图，
中立城就可能和主城叠在一起 —— 两座 2×2 共享格子时，`tile.objectId` 会被后放的覆盖掉，
于是那座城变成"四格里有**两格**能站人"，寻路和渲染都会跟着错。

第 6 步是兜底：城堡一次占掉 3 格，理论上能把地图切出孤岛。真切了就换种子重来。

### 17.6 渲染

- **按物件去重、只在锚点画一次。** 2×2 的四格挂同一个物件 id，旧循环会画四遍。
  现在每帧用一个 `Set<objectId>` 去重，绘制位置统一取 `drawAnchor(obj)`（最上、再最左那格）。
  单格物件的 `drawAnchor` 就是它自己，所以旧行为不变。
- **精灵**：`castle(roof, wall, tier)` 画成 **72×96**，锚点 `CASTLE_AX = -4, CASTLE_AY = -32`。
  换算下来：占地区域 64×64，精灵左右各外扩 4px，底边**严格对齐**占地格下沿（`-32 + 96 = 64`），
  上方多出的 32px 放塔楼和旗子。所以英雄站上城门格时，脚正好落在城墙根，不会被精灵盖住。
- **记忆迷雾**逐格压暗：多格物件对每个仍在 `revealed` 但不在当前视野内的占地格单独叠一层暗色，
  否则城堡会一半亮一半暗。

### 17.7 验收

- `tools/smoke.mjs`：**349** 条断言全绿（新增 15 条：占地 4 格 / 三面墙不可通行 / 城门唯一可站 /
  北面与东面进不来 / 正面必有开口 / 每座城都走得到 / 进城的最后一步必须来自正面 / 站上城门能触发进城 /
  30 张地图 ×4 座城的批量校验）。
- 独立脚本扫 **432 局**（3 尺寸 × 4 对手数 × 3 难度 × 12 种子）：占地格数、唯一入口、
  正面开口、城门可达、英雄可达、阵营主城间距 —— 0 异常。
- 120 天长局 A/B（对照 `d4dad72`，同 15 组种子）：AI 平均首次攻城 **12.2 天 → 26.9 天**，
  AI 最高兵营 **3.4 → 3.9 级**。城堡让扩张变慢变稳，没有出现"AI 反而更早打到玩家"的回归。
  日志里能看到 AI 确实是从城门那一格进的城（`移动到 (4,18)` → `攻陷了 曙光城`）。

### 17.8 踩过的坑

- **"四格里有两格能站人"。** 两座城堡重叠，后放的把 `tile.objectId` 覆盖了。根因是中立城
  在主城之前选点（见 17.5）。修复 = 调整顺序 + `pickHomeSpots`/`pickTownSpots` 增加
  Chebyshev ≥ 2 的不重叠硬检查。
- **屋脊被裁掉。** 精灵原本 72×88，`keepTop - 22` 算出来是负数，三角形的顶点直接画到了画布外，
  顶棚看起来是平的。修复 = 高度加到 96、锚点改成 −32，并重新排了一遍纵向坐标。
- **旗杆穿过屋脊。** 旗子先画、屋顶后画就能自然"插在塔尖上"；反过来画会看到旗杆压在屋顶上。


## 十八、M6：攻城战（城墙 / 城门 / 箭塔 / 护城河）

### 18.1 规则

城镇建了 `wall1/2/3` 之后，攻打它就不是野战，而是一场**真正的攻城战**。战场从普通的
15×11 空地变成：攻方在左，右半场立着一整套城防。

| 结构 | 占位 | 作用 | 血量（1/2/3 星） |
|---|---|---|---|
| 城墙 | 第 11 列整列（10 段） | 挡住步兵，**同时挡视线** | 255 / 310 / 365 |
| 城门 | 墙列正中第 5 行 | 同城墙，但更硬 | 490 / 600 / 710 |
| 箭塔 | 墙后第 12 列，1/2/3 座 | 每回合开始自动射击攻方 | 170 / 220 / 270 |
| 护城河 | 墙前第 10 列 | 站进去的攻方防御 −2 | — |

几条关键规则，都是刻意的选择：

- **城墙挡人不挡箭？不，挡人也挡视线。** 初版做成了"只挡人不挡箭"（HOMM3 的做法），
  实测发现弓箭手隔着墙对射，攻方步兵永远在挨打、永远打不到人，
  城防 2 星以上就是 100% 团灭 —— 没有决策，只有送死。改成**挡视线**之后：
  守军躲在墙后是安全的，攻方全员的目标变成"先把墙砸开"，
  破墙之前双方互不损耗，破墙之后才是真正的战斗。节奏清晰，决策也清晰。
- **城防不会反击。** 反击是"部队"的概念；让城墙反击，攻方会在破门前就被磨掉一半。
- **一段墙塌了，相邻两段跟着掉血（40%）。** 这是实测逼出来的：一个格子宽的口子
  只能容一支队伍挤进去，攻方会像排队送死一样被点名，12 回合还打不下来。
  让缺口自己变宽之后，"破门"才真的意味着"冲进去"。
- **箭塔不听人指挥**，每回合开始自己挑攻方威胁最高的部队射一发 —— HOMM3 的老规矩，
  也是"城防等级"最直接的体感来源。

### 18.2 数值是怎么定下来的

用 15 组（攻方兵力 × 守军兵力）× 5 种子扫出来的目标曲线：

| 场景 | 0 星 | 1 星 | 2 星 | 3 星 |
|---|---|---|---|---|
| 早期部队 vs 小驻军 | 胜 7~10% | 胜 40~93% | 败 | 败 |
| 中期部队 vs 中驻军 | 胜 10~14% | 胜 53~62% | 大多败 | 败 |
| 后期部队 vs 中驻军 | 胜 22~27% | 胜 13~20% | 胜 33~42% | 胜 64~82% |
| 后期部队 vs 大驻军 | 胜 22~27% | 五五开 | 败 | 败 |

粗略地说：**每升一星城防，攻方要多带约五成的兵**。这就是"该不该现在攻打这座城"
的决策依据，预估面板会把这条线告诉玩家。

### 18.3 实现要点

- `core/combat/siege.ts` 只放**纯几何与结构数据**（布局、血量、视线判定），
  所有涉及部队的逻辑在 `battle.ts` —— 单向依赖，避免循环引用。
- 战场几何验证过：odd-r 偏移下第 11 列是一个**完整的分隔**，
  从第 ≤10 列到第 ≥12 列必然经过墙格，所以"挡住"是几何结果，不需要额外特判。
- `BattleState.siege` 是**战斗局部的临时状态**，不进 `GameState`、不进存档，
  所以存档版本没有动。城墙每次战斗都按满血重算（HOMM3 的城墙也是打完就修好）。
- AI 与玩家走完全同一套规则：AI 的预估和结算（`applyInteraction` 的兜底路径）
  都传入 `wallLevelOf(town)`。这里抓到一个真 bug：AI 结算那次 `quickBattle`
  没传城墙等级，导致"预估说打不下来、实际却按野战打赢了"—— AI 会因此去送死。

### 18.4 验证

- smoke 新增 21 条攻城断言（共 370 条全过），包括：
  墙列挡路、砸墙掉血、缺口变宽、挡视线、箭塔墙后不可被远程点名、
  20 场攻城全部在 40 回合内破墙、城防越高攻方损失越大（0<1<2<3 星单调）。
- 120 天长局回归（3 难度 × 5 种子）：AI 首次攻陷城镇平均 21.9 天、最高兵营 3.8 级，
  与改前一致 —— 城墙没有把 AI 卡死，它该打还是打、该绕还是绕。
- 无头 Chrome 截图核对战场：墙/门/塔/护城河的位置、血条、旗帜。

### 19.2 M7 矿场与宝库区（已实现）

**矿场（七种资源）**

| 矿 | 产量 | 摆放 |
|---|---|---|
| 锯木场 / 采石场 | 木/石 +3/天 | 每家主城 3~7 格内**保底各一座**（无主，先到先得） |

## 二十、M8：地图布局模板（旷野 / 同心环 / 双子岛 / 三路走廊）

### 20.1 为什么要模板

程序化噪声的毛病是**没有叙事**：开局那一眼，玩家只能看到"一片绿"，
不知道自己该往哪走、对手离得多远、哪块地值得抢。四档模板解决的就是这件事——
**结构由模板决定，纹理仍由种子决定**。同一档在每一局保持同一个骨架
（几片陆、几条水道、主城在哪一带），湖岸线、矿点、宝物照样随种子变化，
所以既"一眼看懂"又"每局不同"。

| 布局 | 骨架 | 想逼出的决策 |
|---|---|---|
| 旷野 | 纯噪声，四家环绕中心起步 | 无额外约束，标准图 |
| 同心环 | 中央高地 + 两道护城河 + 三处渡口 | 最肥的宝库在中心，先过河的人先富，但渡口只有一个方向 |
| 双子岛 | 一条蜿蜒海峡 + 两座桥，四家 2/2 分居 | 前中期各岛发育，决战靠抢桥 |
| 三路走廊 | 两条横向河脊 + 每条两个缺口 | 正面突破还是绕路，缺口是必经之路 |

### 20.2 实现：在噪声之上"盖章"

`applyLayout()` 拿到已经算好的高度场，按几何量（到中心的半径、到中线的距离）划出结构带，
**再把每格的原噪声塞回带内**（`band(noise, base, amp)`）。

- 护城河/河脊：`base = SEA(0.12)`，压到水域阈值以下；陆地：`base = LAND(0.5)`，落在草地~土路。
- 渡口/桥梁：`base = CAUSEWAY(0.66)`，正好落在"土路"那一档——跨水的地方一眼能认出是条路。
- **顺序很关键**：布局要盖在噪声之上、海岸线之前；渡口要刻在最后。
  渡口是布局的"承重墙"，被任何规则改掉都会让整张图断成走不到的孤岛。

几条踩过的坑，都是这次实测逼出来的：

- **绝对格数，不是半径百分比。** 初版护城河宽度取半径的 8%，小图（24×24）上河宽只有 1 格，
  预览里看着是一圈虚线；改用 `max(1.5, min·0.06)` 格之后，三种尺寸的河宽手感才一致。
- **同心环的"深处"不是"离主城远"。** 矿/宝库的"深度"量尺一直是"离最近主城的曼哈顿距离"，
  但同心环的腹地是**地图中心**——那里离各家主城只有六七格，用它当尺子会得出一张
  "中间啥也没有"的环带图。所以布局自带深度量尺：`deepness = (R − r) · 1.35`，
  系数 1.35 让中心在三种尺寸下都刚好越过"强档宝库"的 16·kl 门槛。
- **主城锚点要跟着骨架走。** 旷野沿用"围绕中心的等分多边形"（整体旋转 + 整体平移，
  保证任意两家相对距离相等）；双子岛/三路走廊则直接给定锚点，再吸附到放得下 2×2 城堡的格子。
- **重试必须封顶。** 地形不理想时会换种子重掷（`attempt + 1`），原来没有上限。
  新布局如果系统性放不下四座城，就会一路递归到栈溢出。现在超过 20 次先退回旷野，
  旷野再不行就退回最小尺寸——宁可给一张朴素图，也不能崩。

### 20.3 验证

- smoke 446 条全过（新增 20 条）：四档 × 12 种子全部生成成功、四家与所有城镇都连通、
  城堡"只有正面能站人"这条规则没被布局破坏；同心环两道护城河在 12 个方向上都是水、
  中心必有强档宝库、四家主城都在外护城河之外；双子岛四家 2/2 分居东西、中线上半数以上是水；
  三路走廊两条河脊以水为主且各有缺口、四家铺满三条道；四档布局的矿/宝库/野怪数量一致。
- 布局审计脚本（`tools/layoutaudit.mjs`）：4 档 × 3 尺寸 × 40 种子 = **480 局全部通过**
  （连通、城数、资源数量、水面占比）。
- AI 长局回归（`tools/ailayout.mjs`，120 天 × 4 种子）：AI 占矿 10.8~13.8 座、
  分区覆盖 同心环 1.8/2、双子岛 1.8/2、三路走廊 3.0/3，各档都开掉 0.5~2.3 座宝库——
  没有哪一档把 AI 关在起手区。个别"纹丝不动"的 AI 英雄不是被地形困住：
  实测其本回合可达格数 99~266，纯粹是"兵太少、附近目标打不过"的既有策略（不送兵）。
- 无头 Chrome 截图核对四档预览与进场画面：同心环的双环渡口、双子岛的海峡双桥、
  三路走廊的两道河脊缺口都清晰可读。

## 二十一、M9：三条玩家实测反馈

玩家上手后提的三件事，都是"功能在、但玩家看不懂"的类型。

### 21.1 施法后战场留着"印记"

**现象**：施法之后，战场上那圈白框不消失，一直挂在原地。

**根因**：战场上的 `hover`（白色六边形描边）只在 `pointermove` 时刷新。
鼠标施法完停在原地不动，就没有任何事件去改它，于是那圈白框一直画着——
玩家读成"施法留下的印记"。

**修法**：新增 `clearAim()`（清 `hover` + 属性浮框 + 浮框定时器），
在**每一条"状态发生切换"的出口**都调一次：移动 / 攻击 / 攻城 / 等待 / 防御 /
自动 / 选中法术 / **施法** / **展开法术书**。另外在 canvas、`fieldWrap` 的
`pointerleave`、`window blur`、`visibilitychange` 上兜底，`close()` 时摘掉监听。
绘制侧再上一道闸：`hover` 只在 `!busy()` 且轮到我方时才真的画出去。

第一个补丁漏了"展开法术书"这条入口（`btnCast` 与快捷键 `C` 只调
`renderSpellBook()`），结果点"施法"的瞬间白框照样留着——**这多半才是玩家
真正看到的那一幕**，因为从玩家视角"点施法"就是"施法"。两个入口都补上后才干净。

**这类 bug 截图测不出来**（无头截图没有鼠标，压根复现不了），
所以做了 `tools/hoveraudit.mjs`：开 `opts.debugProbe` 时 BattleScreen 把每帧
**实际画出去**的悬停格写到 `window.__battleHover`，探针页摆一场战斗，
用 CDP 打真事件再读回来。断言四条：悬停要出现 → 点"等待"要消失 →
再悬停要回来（别把功能修掉）→ 开法术书要消失。

踩过的坑（注释里也写了）：
- **不能用 `--virtual-time-budget`**：虚拟时间下 `requestAnimationFrame` 不触发，
  战斗渲染循环根本不跑，`__battleHover` 永远是 `undefined`。必须真实时间 + CDP。
- 等状态别用"固定 N 帧"：无头帧率不稳，会读到上一拍的陈旧值（第一版就栽在这），
  要轮询到条件成立。
- chrome 要带临时 `--user-data-dir`，否则会动用户自己的 Chrome 配置；
  收尾还要等它真退出再删 profile，否则 `ENOTEMPTY`。

### 21.2 地图要更大 + 每座城周围都要有木石矿

- **尺寸**：新增 `huge`（48×48），`SIZE_ORDER` 同步。
- **矿场**：原来只遍历 `homeSpots`（四家玩家主城），中立城周围什么都没有——
  占了中立城等于占了个空壳。改为遍历 `[...homeSpots, ...neutralSpots]`，
  每座城保底一座锯木场 + 一座采石场，摆在曼哈顿 3~7 格（`HOME_MINE_RING`）；
  同心环上主城被水面占掉时退一档放到 +5 格。
- `tools/minesaudit.mjs` 用数字验收：48 张图 / **336 座城（含中立城）全部达标**，
  最远 7 格，"外退一档"兜底一次都没触发。
  **量尺必须和被审对象一致**：生成器用曼哈顿距离，一开始审计用切比雪夫去量，
  把设计内的 7 格误报成不合格。

### 21.3 "资源不足（4500 金）"但玩家明明有钱

**现象**：建造框里点大法师塔提示资源不足，可玩家有两万金。

**根因**：`costText()` 只印金 / 木 / 矿三种。大法师塔的真实造价是
**4500 金 + 4 水晶**，那 4 个水晶根本没被印出来，玩家只看到"4500 金"，
自然以为游戏算错了。

**修法**（显示层全面补全稀有资源）：
- `costText()` 覆盖全部七种资源（`COST_ORDER` / `COST_LABEL`）。
- `BuildStatus` 增加 `cost` 与 `missing` 字段，新增 `missingResources()`；
  资源不足时的文案从"资源不足（4500 金）"变成
  **"资源不足：水晶 0/4"**——把"现有 / 需要"一起报出来。
- 建筑卡片：先压暗显示完整造价，再点红缺项：
  **"4500 金 · 4 水晶　还差：水晶 0/4"**。只写"还差"看不见总价，
  只写总价正是当初那条误导信息的来源，两行都要。
- HUD 资源条从 3 项扩到 7 项，为 0 的资源加 `.zero` 变暗（"我没有"和
  "我没有但用不到"要能区分）；城镇总览也补上宝石 / 水晶 / 硫磺 / 水银。
