## 一、做成了什么

| 项 | 实现 | 读数 |
|---|---|---|

| 随机流 | `deriveSeed(seed, 0x706f636b, minDist)` 单开一条 | 主 `rng` 调用序列不动 |

跨了三处旧代码，每一处都是"不改就会静默错"：

- `types.ts`：`MapObjectKind += 'statBoost'`；`visitedBy` 从 `PlayerId[]` 放宽到 `string[]`
  （泉水存**玩家**、属性物件存**英雄**，同一个字段两种语义，注释写死在类型上）；
  各 payload 加可选 `pocket` 标签；守卫 payload 加 `pocketDist`（探针报真实深度用）。
- `interaction.ts`：`previewInteraction` / `applyInteraction` / `pendingObjectAt` 三处都要认"这个英雄领过了"，
  少一处就会出现"不弹框但走上去仍然加属性"（只改 `apply` 会漏掉 `pending`）。
- `MapRenderer`：`statBoost` 的图标按 `iconStat + pips` 映射到 **6 张** `stat_*` 帧。
  9 种物件没有 9 张画：32×40 上能读出的只有"颜色 + 颗数"，同色同颗数复用同一张（`fighters_guild`/`magic_school` 用 +1 帧）。

## 二、九个 bug（全是"看起来对"的那种）

这一批真正花时间的不是写功能，是**尺子**。九条都在门里留了注释，防止下次再写一遍。

### ① `floodBan` 的循环变量遮蔽了地图高度

```ts
const q = [s];
for (let h = 0; h < q.length; h++) {   // h = 队列下标
  ...
  if (ny < 0 || ny >= h) continue;      // 却拿它当地图高
```

第一轮 `h = 0` ⇒ `ny >= 0` 恒真 ⇒ **每个邻居都判越界** ⇒ 每次洪水都只有起点 1 格。
读数表现是"口袋一个都生成不出来，`compSizes` 全是 `[1,1,1]`"。
这条是典型的"数字看起来像结论"：如果当时把 `oneDoor` 判据放松成 `≥1`，它会立刻绿，而口袋全是漏的。

### ② 连通性判据用错了命题

围完墙要验"没把别的地方隔开"。第一版写的是：

```ts
const townsOk = [...homeSpots, ...heroSpots, ...neutralSpots].every(
  (p) => fromStart[idx(map, p.x, p.y)] === 1,   // 从 heroSpots[0] 出发
);
```

分岛图上这个命题**天然为假** —— 实测 lanes 图本来就有两块 1417 格的大陆，
于是每个合法候选都被判死（`townsOk: false`，其余全对）。
换成真正的命题：**加墙不许把任何原有连通块切开**（`keepsComponents(before, after)`），
O(n) 且与布局无关。

### ③ 相位顺序错了：口袋排在障碍物之后

`130·k` 棵树先铺满地图，然后才去找"8~20 格空地 + ≥6 格干净外圈"——
24×24 上从 3 块掉到 **0~1 块**。

结构性要素必须早于装饰物。把整块挪到**障碍物之前**后：小图从 0~1 变成 3 块，
并且墙先占格 ⇒ 后面的障碍/野怪/宝箱自然绕开，"块内恰好 1 件"不靠补丁成立。

> 代价要认：物件 id 与障碍落点会变。**"与上一批逐字节一致"只对地形成立**，
> 这句已经写进生成器的注释里，避免下一批拿旧指纹当回归基线。

### ④ "一个入口"的判据不能数块数

第一版：拿掉门那一格，从四个相邻格分别洪水，**8~20 格的连通块必须恰好 1 个**。
实测报出 `BAD(18/20/770)`：

- 20 = 我们的口袋；
- 18 = 口袋生成**之后**、障碍物相位在门边顺手圈出来的**空壁龛**；
- 770 = 外面。

壁龛不是第二个口袋（里面什么都没有），但它让"数 8~20 格块"数出 2。
真正的判据是**不能漏**：从奖励格洪水（禁走门），水量必须**正好等于**内部格数。
多一格 = 有第二个洞。一条洪水代替四条，且定义正确。

### ⑤ 外圈"至少要 6 格可通行"是反的

原判据想防"一小块空地被当成口袋"，但真正被它杀掉的是**天然洞穴**——
外圈全是山/水、只有一个口，那是最理想的形态。
"到底围没围住"已经由 ④ 的漏水检验严格保证，这条只能删。
删掉后 `ring small` 的 D3 立刻从 0 变成 1。

另外两条小的：口袋的长相会**蹭到城堡城门**（城门格"可通行 + 有 objectId"，
是唯一堵不上的外圈格）⇒ 改成开局就躲开城门四邻（`avoidNear`），
而不是"长完了再否掉"；隘口守卫会**落进口袋**（它按几何挑路口，不看 `taken`）
⇒ 加一道 `taken.has(cell)`。

### ⑥ 外圈把树种到了英雄脚下（真的把棋子封死）

修好 ①–⑤ 之后全量门报 `audit:layout` 九档红（`un.` = 1~3，即"有几座城走不到"）。
A/B 两臂证实是口袋的锅：`wild/small` 关掉口袋 0 张坏图，打开 2/40 坏；
`/tmp/diag.mjs` 抓到 `hero_p3` 自己脚下就是 `o22:obstacle:tree`。

根因：`eligible()` 早就用 `blocked` 挡住了"内部"不许含城镇/英雄格，
**外圈漏了**；而英雄出生格在引擎里**不是 `MapObject`**（`objectId` 为空），
只靠 `map.tiles[i].objectId` 看不见它 ⇒ 墙直接栽在英雄身上，整局动不了。

```ts
if (map.tiles[i].objectId || o.blocked.has(i)) { sealable = false; break; }
```

门里补了 **[G6] 英雄出生格仍可通行** —— 它把因果钉在门口，
否则下次还是会先去查"城堡为什么走不到"，绕一大圈。

### ⑦ "能长到 20 格就长满 20 格"把小图的 D1 全灭了

加了 ⑥ 之后，`ring/small` 三颗种子只剩 2 块（D1 = 0）。
`POCKET_DEBUG=1` 的 trace 给出读数：D1 单档 `rimHasObject` **133~137 次**、
`blobTooSmall` 8~14 次、`found` 只有 3~5 次 —— 而 5~9 环带总共约 150 个候选起点。

20 格的面有 10~14 格外圈，其中**任何一格**是城镇 / 英雄出生格 / 已有物件就整块作废；
24×24 四家的小图上这几乎必然发生。§18.1 只要求 **8~20**，固定取上限是多余的自我设限。
改成**每个候选随机抽一个目标格数**（8~20，仍走同一条单开的随机流），
紧凑小口袋多起来，三张图立刻回满 3 块，且 80 图内部水量仍全在 [8,20]。

### ⑧ "深档先挑"不等于"深档更深"

`islands/small/9100`：D3 的 16+ 带落空退到 14，随后 D2 在 10~15 带随手挑了 **15**
⇒ `D2 > D3`，阶梯反过来，[G4] 红。D3 先挑只保证"先占深的候选面"，
不保证"围得住的那块更深"；一旦深档的候选面因外圈堵不上而放弃，
浅档就可能捡到更深的那一格。

修法不是再调排序，而是把深档**实测**深度写下来，给浅档的 `maxDist` 封顶：

```ts
const cap = placedDist[deeperTier];           // D3 先落，D2 用它封顶；D1 用 D2 的
const maxOf = (m) => (cap == null ? m : Math.min(m, cap));
```

D1/D2/D3 的**距离**阶梯是规格，不能靠"随机挑选顺序"碰运气。48 图与 80 图各 0 处不单调。

### ⑨ `process.env` 在浏览器里是 `ReferenceError`，九道门一起红

排障用的 `if (process.env.POCKET_DEBUG)` 写进了生成器模块顶层逻辑里。
Node 侧全绿；浏览器**没有 `process`**，建图那一刻直接抛
`Uncaught ReferenceError: process is not defined @ core/map/generator.js`。

表现极具欺骗性：`probe:exchange` 说"`?devexchange=1` 的入口坏了"、
`audit:scenario` 说"开始页未在 12s 内就绪"、`probe:castle` 说"地图没起来"、
`audit:tutorial` FAIL 5 条 —— 九道浏览器门全红，看上去像九个独立故障，
也像"跑门途中重建了 dist"（这一批确实也踩过那个坑，两次全量跑因此作废）。

抓法：用 `Page.addScriptToEvaluateOnNewDocument` 挂 `window.onerror` 再导航，
一条错误就够：`process is not defined @ core/map/generator.js:1169`。
改成 `const POCKET_DEBUG = typeof process !== 'undefined' && !!process.env?.POCKET_DEBUG`。

> **流程纪律（写进记忆）**：① 门在跑的时候**不许 `npm run build`** —— 零打包器下
> `dist/` 被整目录重写，Chrome 手里的 bundle 会中途换掉；② 浏览器门红了先单独复跑，
> 别急着归因给并发；③ 全绿之前不要提交。

## 四、两处规格偏差（要认账，不要当成"已实现"）

### 1. 小图的 D3 深度落不下去

规格 §18.3：D3 = **距最近主城 16+ 格**。实测（`/tmp` 口径，4 布局 × small）：

| 布局 | 全图最远空格 | ≥16 格的空格数 |
|---|---|---|
| wild | 14 | **0** |
| ring | 14 | **0** |
| islands | 15 | **0** |
| lanes | 16 | 2 |

24×24 上摆四家，几何上就没有"16 格深"的地方。生成器退两步：
① 上一档 +3；② 按 D2 下限、**由深到浅**试（先试全图最深那格）。
且**从深到浅分配档位**（D3 先挑），否则 D2 会先把唯一的深区吃掉，D3 空转
（实测 `ring small` 就是这么空的）。浅档的 `maxDist` 还要用深档**实测**深度封顶，
否则会出现 `D2=15 > D3=14`（§二·⑧）。

⚠️ 只退**距离**：8~20 格与"恰好一个口"一步不退。
门只断言三档**单调**（D1 ≤ D2 ≤ D3），真实区间打印出来，不写成"通过"。

### 2. `magic_school` 原本无处投放

§21.8 列 **9 种**物件，§18.3 的 D2 只给了"斗士学院 20%"，**魔法学校没有位置**
⇒ 定义存在、永远刷不出来。门里的 `H0` 把它抓出来了（"不在任何一档的池里"）。

处理：把 D2 的 20% **对半劈**成斗士学院 10% / 魔法学校 10%。
两者是同一价值量级（+1 四维、1,000 金、每英雄一次），**期望收益逐点不变** ⇒
V4「每图 ≥1.15」不受影响，只是口味从"只有攻"变成"攻/魔二选一"。

> 若主理人要严格照抄 §18.3，另一条路是删掉 `magic_school` 的定义（9 种变 8 种）。
> 不能两个都要 —— 这条写进了 `pocketRewards.ts` 的表注释里。

## 七、仍欠
