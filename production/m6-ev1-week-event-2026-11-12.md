# M6 · EV1 周生长事件（2026-11-12）

> 计划：`production/ui-redesign-2026-10-28/PROJECT-PLAN.md` §8.2
> 规格：`production/ui-redesign-2026-10-28/spec-implementation.md` §19.1–19.2 / §19.4 V4–V5
> 门：`npm run -s probe:weekevent` → **18 条全绿**；全库 **60 门**同批全绿（`audit:androidsync` 重建后复位）

H3 的 `Growth` 是静态字段，只有随机事件会改它。这一批把那件事补上：
**第 3 周起，每周日掷一次「生物周 / 瘟疫 / 平静」**，并保证三件事 ——
概率是量出来的、数值只改本周产量、公告在玩家第一次招募之前。

---

## 一、做成了什么

| 项 | 实现 | 读数 |
|---|---|---|
| 概率 | `weekEventFor(seed, week)`：`<0.25` 生物周 / `<0.33` 瘟疫 / 其余平静 | 3,000 次：**24.8% / 7.0% / 68.2%**（判据 25/8/67 ±3pt） |
| 教学期 | 第 1~2 周直接返回 calm，**不消耗随机数** | 800 次（400 seed × 两周）非平静 **0** |
| 生物周 | 只抽四族 **T1~T3** 共 12 个兵；`eventAdd` **按档递减 T1 +5 / T2 +3 / T3 +2** | 表 = `{1:5,2:3,3:2}`；实测增量只落在被抽中的那一档 |
| 瘟疫 | `eventMult = 0.5`，只砍**本周新增** | 每兵种池子 = 平静周的 0.5 倍；已招募部队逐字节未变 |
| 作用形态 | 事件按**基础版 id** 定义；结算时 `baseUnitIdOf(dwellUnitId)` 归一 | 兵营 L2 后增量落在 `_u`，基础版池 **0** |
| 随机流 | `deriveSeed(seed, 'week', week)` **单开一条** | 同种子 28 天重跑：事件与增长池逐字节一致 |
| 公告 | `pushLog` + 顶部横幅（`#week-banner`，4.5s） | 每个非平静周都在**当天**日志里；横幅只在 `isNewWeek` 那天弹 |

一处刻意的不同（§19.1 已定稿，不是待改项）：H3 的 +5 是绝对量，它看着温和只因为
H3 的 T3 周产就有 5~8；我们的 T3 只有 4~5，照搬 +5 等于 +100%~+125%，
再叠 `banner`（×1.5）单档周产战力直接翻倍。按档递减后落在 **+31%~+60%**，
仍在 H3 自己的 +25%~+100% 区间里。

## 二、公式：`eventAdd` 加在哪个位置

```
exact = (growthPerWeek + eventAdd)
      × townMult            // max(0.5, 建筑+难度)，加算、地板只套这一段
      × eventMult           // 瘟疫 0.5，乘在乘积外
      × tierGrowthMultiplier(town, tier)     // banner ×1.5
      × dwellingLevelGrowthMult(town, tier)  // 兵营 L3 ×1.25
```

`eventAdd` **加在 `growthPerWeek` 上、再统一乘后面三个倍率**，不是加在最后。
依据是 §19.2 的算式本身：p3 建成 `banner` 后，树人一档周产战力
= `86.9 × (4+5) × 1.5 = 1,173`、按 +2 取是 `86.9 × (4+2) × 1.5 = 782` ——
两处都让事件增量吃到了 `×1.5`。若改成"最后再加 5 只"，同一句话会读成
`86.9 × 4 × 1.5 + 86.9 × 5 = 956`，既不是 1,173 也不是 782。

探针不重算这个公式：它跑**两臂**（同存档，一臂平静、一臂带事件），
逐城逐兵比 `growthPool + growthRemainder` 的差，要求**恰好**等于
`eventAdd × townMult × tierMult × dwellMult`（误差 0）。

## 三、本批发现的真问题：A5 被周事件推过 60%

接入后 `probe:aiscale` 立刻红一条：

```
seed 10104 / 阿尔文：5 栈 · 单栈 61% · 当屏 有（单栈 61%>60%）
```

关掉事件的对照臂同一天是 **52.6%**（T4 牛头怪 ×5）；开事件后变成 **61.3%**（×7）。
不是周事件直接加了 T4 —— 事件只动 T1~T3，而是"池子大小 → 买兵 → 打仗 → 收入"
这条链把 2 只 T4 放大出来了。**A5 是确定性读数，不是抖动**（重跑逐位一致）。

根因不在事件，而在 AI 的既有编队策略：`poolOrder` / `refillFromGarrison` 都是
**高档优先**，它天生倾向把战力堆进同一栈；A5 的 ≤60% 从来不是"被保证"的，
只是此前没有东西把它推过线。

修法是**把设计约束写进 AI**（不是放宽阈值）：

| 位置 | 改法 |
|---|---|
| `capForStackShare()`（`ai.ts`） | 设该栈战力 `s`、单只 `u`、全军 `V`，再加 `x` 只要求 `s+xu ≤ 0.6(V+xu)` ⇒ `x ≤ (0.6V−s)/(0.4u)`；空军队不设限 |
| `refillFromGarrison` | 从驻军抽兵时取 `min(存量, 富余, 单栈余量)` |
| `aiRecruit` / 城内补兵 | 能进英雄的进英雄，**装不下的买进驻军** —— 不许像首版那样 `break`（那会把兵晾在池子里、钱也花不出去，实测 seed 4242 的 D28 英雄战力 1315 → 1003） |

修后读数（8 种子 × 60 天）：

| 项 | 修前（事件开） | 修后 |
|---|---|---|
| A5 单栈最大值 | **61.3%（红）** | 55%（4 局全绿） |
| D35 内买到 T5 | 63%（5/8） | **75%（6/8）** |
| D28 英雄战力（seed 4242） | 1,341 | 1,679 |

> 这条改动改变了 AI 的编队行为，B4 的旧基线（每金战力 / D28 战力）不再是同一个世界。
> 读数照打，**B5 重跑基线时必须把这批算进去**（见欠账）。

## 四、公告为什么单独一条横幅

底部 `#hint` 是 2s 的操作反馈；周事件的下一句提示就是「第 N 天」——
混进去会被立刻顶掉，玩家还没读到。所以 `#week-banner` 在顶部中央停留 4.5s，
`pointer-events:none`，且只在 `isNewWeek(state.day)` 那天弹（否则整周每次结束一天都重播）。
