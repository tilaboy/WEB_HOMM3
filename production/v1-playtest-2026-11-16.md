> 2026-11-16。跑法：`node tools/probes/playtest.mjs --games=20 --days=60`
> 原始读数：`production/v1-playtest-2026-11-16/playtest-20d60.json`
> 判据出处：`production/ui-redesign-2026-10-28/PROJECT-PLAN.md` §10.1（F1–F6）

---

## 1. 这份读数是什么、不是什么

V1 原来是一份**人做的手记**（5 人 × 3 局 + 5 局）。人这一栏到现在仍然是 **0 局**。
本文件补的是另一半：**四族全交给 AI、同一套代码、同一批种子**跑出来的 20 局。

| 能由脚本回答 | 只能由人回答 |
|---|---|
| 建造树在真实对局里**会不会被选**（F2/F3/F4） | 玩家**愿不愿意**选（同样三条线的采纳率） |
| 爆发怪有没有**交战**、比例多少（F5） | 玩家觉得打还是绕划算 |
| 一局**多少天**结束、模拟一天几毫秒 | 真人一天 1.4~1.5 分钟、一局 45~60 分钟 |
| 四族**存活率 / 战力 / T5 时点** | 四族**各自当玩家**的胜率（F6） |

**F1 与 F6 本脚本判不了，原因在数据本身，不是没跑**：

- **F1（前三次建造重合度 ≤70%）**：AI 只有一套策略，重合度天然 100%。
  它证明的是"存在压倒性最优路径"，**不是**"玩家都这么建"。
- **F6（四族胜率各 20%~30%）**：`createGame` 把 p1 固定成 `FACTION_ORDER[0]`，
  阵营与出生位绑死。脚本只能给 **p1（骑士）的胜率**，给不出"四族各当一次你"。

## 2. 方法（口径写死，否则读数没法比）

- **20 局 = 4 种布局 × 5 个种子**（`wild` / `ring` / `islands` / `lanes`，seed 6100 / 7077 / 8054 / 9031 / 10008）。
  轮换布局是为了让 p1 不要永远占同一个相对出生位。
- **四族全 AI**：`turn.ts` 硬写 `if (player === 'p1') continue`，所以把 `players.p1.isHuman` 置 false 后
  每天补一次 `runAiTurn(state, 'p1')`。**p1 排在三族之后行动**（后手）。
- **normal 档**：`playerStartMul / playerMoveMul / monsterMul` 全 1、AI 起始 ×1 —
  p1 除了后手之外没有额外加成（D1 实测四族战力 994 / 1125 / 933 / 1034）。
- **一局 = 35 天**（§27.7 的五周）。判据取 D35；继续跑只为看终局。
- 20 局 × 60 天 ≈ 20 秒（每模拟日 ~9.6 ms）。

## 4. 四条值得处理的读数

### 4.1 建造树只有一条路（F1 = 100%，20/20 完全一致）

每一局的第 2 天都是 `酒馆 → 兵营 → 弓箭手营`，一条不差。
这说明**前三天不存在真正的选择**：不是"玩家偏好一致"，是"别的选择在数学上更差"。

V1 的修整条款写着「F1 超 80% ⇒ 改建筑前置 / 价格，**不加新建筑**」。
20/20 已经远超 80%，**但触发它的主体是 AI 而不是玩家** —— 所以这条要等真人那一栏
再决定改不改；现在能确定的是：**这不是"玩家多样性不足"，是"树本身没有分叉"**。

### 4.2 墙建得太晚（中位 D15.5，最晚 D34）

设计口径是"增长只在有余钱时有效 ⇒ **墙必须早建**"（`MEMORY` 经济段）。
AI 的墙首建日 **中位 15.5 天、四分之一在 D20 之后**，而同一批局里行会 D7 就起来了
—— 也就是**先魔法、后城防**是稳定策略，不是个别局。

⚠️ 这一条与"墙的回报是增长型"直接冲突：墙越晚建，增长的复利期越短，越不值。
要么接受"墙是中后期建筑"，要么让 AI 的优先级把墙提前（改 AI 策略，不改价）。

### 4.3 F5 是**窗口效应**，不能拿单点读数判设计

同一组 8 局，只改截断天数：

| 窗口 | 打 | 绕 | F5 |
|---|---|---|---|
| 40 天 | 11 | 56 | **16%** |
| 120 天 | 36 | 31 | **54%** |

差 3.4 倍。原因是爆发怪按周持续落地：窗口越长，AI 兵力越足、越可能顺手打掉。
⇒ **判 F5 必须钉死 35 天**（一局的口径），写"某天读 54%"会得出相反结论
（与铁律 66 同一类：难度判据不许用短窗，这条是"采纳率判据不许用长窗"）。

### 4.4 AI 之间**收不了局**：60 天 0/20，120 天 2/8

V1 的节奏目标是"一局 45~60 分钟"，按 1.4~1.5 分钟/天折算约 **30~40 天**。
但四族全 AI 时 60 天**一局都打不完**，拉到 120 天才结束 2 局。

这不等于"真人 60 分钟打不完"（人会集中兵力打城，AI 不会），但它说明
**终局条件对 AI 太保守**：谁都能守住一座城，"无城且无英雄"极难达成。
如果要靠 AI 施压来收局，问题在攻城/决战，不在天数上限。

## 6. 复现

```bash
cd homm-web
npm run -s build                                   # 必须，工具读 dist/
npm run -s probe:playtest -- --games=20 --days=60 --json=/tmp/pt.json
node tools/probes/playtest.mjs --games=8  --days=40    # F5 短窗（对照）
node tools/probes/playtest.mjs --games=8  --days=120   # F5 长窗（对照）
node tools/probes/playtest.mjs --games=4  --days=40 --negctrl   # 负向对照（见下）
```

**两条可执行的负向对照**（闸必须能红，铁律 2）：

| 对照 | 做法 | 实测 |
|---|---|---|
| 抹掉三条线 | `--negctrl`：把每局的 `wall/guild/t5` 与爆发怪计数清零再判 | 「可达」与「有对象」**同时红** |
| 空集 | `--days=20`（小于 35） | 「0 局走到 D35」**红** |

⚠️ 空集那条曾经写成 `with35.length !== list.length` —— `0 !== 0` 不成立，
于是「一局都没到 D35」反而**判绿**。现在先判 `=== 0` 再判数量不等。
这正是"恒绿的闸等于没有"：负数与空集必须在**第一行**拦住，不能靠后续比较兜住。

脚本只会因为三种情况退出 1：**没走到 D35**（空集）、**某条线一次都没被选中**（0 采纳）、
**爆发怪 0 对象**。F2–F5 的阈值只打印不判 —— 它们是玩家指标，AI 读数判红等于
"拿别人的尺子量自己"。
