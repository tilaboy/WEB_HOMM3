# ADR-001：移动优先交付形态 —— 选 Capacitor 而非 Tauri / 纯 PWA / 原生

- **状态**：提议（待用户批准）
- **日期**：本轮
- **决策者**：玩家（产品负责人）+ 程基岩（技术方向）
- **相关**：`design/…`、`homm-web/DESIGN.md` §十二、`docs/architecture/mobile-platform.md`
- **取代**：上一轮路线图中的「Tauri 桌面包（Windows/macOS）」

---

## 1. 背景（Context）

### 1.1 玩家的原始诉求与平台目标

玩家从一开始要的是**手机上能装的 App**。项目早期为了让"手感"能被快速迭代，先做成了 Web + Canvas2D，并在 `DESIGN.md` §十二把「Web + PWA，不做原生 App」**写成了正式决策**——理由是：零美术资源 → 首屏 60–90 KB、比任何原生包小三个数量级、一套代码跨平台、一个链接就能分发。

这个决策在"验证玩法"阶段是对的，但它把**交付形态**当成了终点，而它其实只是个起点。

### 1.2 三处相互冲突的历史记录

| 来源 | 说法 | 冲突点 |
|---|---|---|
| `DESIGN.md` §十二 | 交付形态 = Web + PWA，并论证"为什么不做原生 App" | 与玩家诉求（手机 App）**方向相反** |
| `DESIGN.md` §十二 性能表 | "576 格 × 3 面 ≈ 1728 多边形/帧，**手机 60fps 无压力**" | 该结论基于 **M1 时期的多边形渲染**；此后 P0.1 加了惯性/缩放/边缘滚屏，P1.1 改成**整图烘焙**（巨型图 9 MiB canvas），P1.3 加了**每帧三遍全屏混合光照**——负载结构已完全不同，这句话**已经过期** |
| 上一轮路线图 | 交付形态 = **Tauri 桌面包**（Windows / macOS） | 与"手机优先"**方向相反** |

冲突的根因：交付形态被反复重定，而**没有一份文档记录"为什么"。** 本 ADR 就是来补这个洞的。

### 1.3 技术现状（决定成本的关键事实）

| 事实 | 值 | 来源 |
|---|---|---|
| 业务代码 | 14,016 行 TypeScript，`tsc` → ESM，零运行时依赖 | 仓库统计 |
| 分层 | `core/` 零 DOM 纯逻辑；`render/`+`ui/` 只用标准 Web API | `src/core/*` |
| 磁盘资源 | 图片/音频/字体 **0 字节**；图集与地图纹理**运行时程序化生成** | 实测 `dist/` |
| dist 体积 | JS 493 KB / CSS 24 KB（gzip 合计 145 KB） | 实测 |
| 测试 | 471 项 smoke 单测 + 5 个 CDP 端到端审计 | `npm run smoke` 实测 471/471 |
| 渲染 | Canvas2D（非 WebGL） | `render/MapRenderer.ts` |

**推论**：业务代码**与渲染目标无关**（没有 DOM 深度耦合、没有浏览器官能依赖）。这意味着"套壳"的边际成本极低——**这是本决策能成立的核心前提**。

---

## 2. 决策（Decision）

**采用 Capacitor 把现有 `dist/` 直接打包为 iOS / Android 原生 App；Web 版保留为开发与测试的主目标；Tauri 桌面方案作废。**

具体：
1. `@capacitor/core` + `@capacitor/ios` + `@capacitor/android` + 一组官方插件（app / preferences / haptics / status-bar / screen-orientation）。
2. `webDir = dist`，即 **Web 构建产物是被包进原生工程的唯一输入**；原生工程零业务逻辑。
3. **不重写任何一行业务代码**；只做移动端专项（触屏手势、安全区、方向锁、性能分档、生命周期）——详见 `mobile-platform.md`。
4. **Web 版继续存在且是 PWA**：开发和自动化测试仍跑浏览器（`npm run smoke` / `audit:*` 全部基于 Web），原生壳是"发布形态"，不是"测试形态"。

---

## 3. 备选方案与被否决的理由（Alternatives）

### 3.1 纯 PWA + 添加到主屏幕（维持 §十二 原决策）

**否决**，但这是最接近的备选：
- **拿不到"App"**：玩家要在手机上看到图标、从商店装——PWA 在 iOS 上必须走 Safari 的「添加到主屏幕」，普通用户根本不知道这一步，且**首次进入必须过 Safari**。
- **iOS PWA 能力缺口**：无法控制状态栏（`apple-mobile-web-app-status-bar-style` 能力有限）、无法锁横屏、无触觉反馈（`navigator.vibrate` 在 iOS 上不支持）、无法可靠地后台保活。
- **存储不保**：iOS 对 PWA 站点数据有 7 天未使用清理策略（ITP 相关），**丢档风险比原生壳更高**。
- **保留的部分**：PWA 的文件（`manifest.json` / `sw.js` / `icon.svg`）**继续保留**，供 Web 版使用，不为原生而删。

### 3.2 Tauri v2（含移动端）

**否决**，理由分三层：
1. **价值主张不匹配**：Tauri 的核心卖点是"用 Rust 换掉 Electron 的大体积、拿系统 WebView"。本项目**根本没有 Electron**，Web 产物只有 0.5 MB——Tauri 想解决的问题我们不存在。
2. **移动端成熟度与生态**：Tauri v2 的 iOS/Android 支持晚于 Capacitor 数年，插件生态（尤其是 preferences / haptics / orientation 这类基础能力）与真机踩坑量远不如 Capacitor；iOS 上两者**都用 WKWebView**，所以 Tauri 在 iOS 端**没有任何渲染优势**，只是多了一层 Rust 桥 + 更陡的构建链。
3. **引入新技术栈**：团队无 Rust 经验，为"包壳"引入 Rust 工具链与跨语言 FFI 调试，是纯粹的复杂度净增。
- **代价说明**：这个决定**放弃了桌面端**。如果将来要出 Windows/macOS 版，Tauri 仍可复用同一份 `dist/`（那时它的"小体积"卖点才真正成立，因为对标 Electron 场景），所以这个放弃是**可逆的**。

### 3.3 原生重写（Swift/SwiftUI + Kotlin/Compose）

**否决**：
- 14,016 行实现良好的 `core/` 逻辑（地图生成、A* 寻路、战斗解算、AI、存档）要重写**两遍**（iOS + Android），且两边的战斗规则极易产生分歧——**这是把"零业务分叉"的最大优势亲手毁掉**。
- 丢失"程序化渲染"的资产优势：Canvas2D 的像素级绘制代码无法直接搬到 Metal/OpenGL，等于美术管线重来。
- 工期与验证成本不可接受（是这个方案本身的 10 倍量级）。

### 3.4 Unity / Unreal / Godot

**否决**：
- 三者都要用 C#/C++/GDScript 重写逻辑；且会把 0.5 MB 的产物变成**几十上百 MB**（引擎运行时基线），直接推翻本项目最大的体积优势。
- 本项目的美术是**程序化像素绘制**，引擎的素材管线、精灵系统完全用不上——用重型引擎只为了"导出 App"，是杀鸡用牛刀。

### 3.5 React Native / Flutter

**否决**：同样要求重写（Dart / RN 渲染层与 Canvas2D 不兼容），且会把"零依赖"变成庞大的框架依赖树。

## 4. 后果（Consequences）

### 4.1 得到什么

| 收益 | 量化 |
|---|---|
| 应用商店可安装的 App | iOS + Android 双端，一份代码 |
| 包体仍然极小 | **< 15 MB**（对比商业手游 100 MB–2 GB），业务代码只占 0.5 MB |
| 业务代码零分叉 | 触屏专项是"新增层"，不是"第二套实现"；471 项测试继续在 Web 上跑 |
| 原生能力 | 触觉反馈、方向锁定、安全区、可靠后台、随 App 备份的存档 |
| 离线天然可玩 | 资源在包内，不依赖 Service Worker |
| 迭代路径不变 | `npm run build` → `cap sync` → 真机；Web 版仍是"改完刷新"的快速回路 |

### 4.2 代价与放弃的东西（必须写清楚）

1. **放弃"零运行时依赖"的纯度**：`package.json` 从 1 个 devDependency 变成 +6 个运行时依赖。这**推翻了项目一直以来的一个架构卖点**（`DESIGN.md` §八 明写"零依赖"）。建议在依赖说明里写清"这些依赖只在原生壳中生效"，并保留一条**可打包 Web-only 的构建路径**（Capacitor 插件全部用动态 import + 能力探测，Web 下不可用时不报错）。
2. **放弃"一个链接即可玩"的分发形态**：从"发 URL"变成"过商店审核"。Android 首次审核通常 1–3 天，Apple 首次 1–3 天但**可能因 Guideline 4.2（Minimum Functionality）被拒**——纯 WebView 套壳是他们明确针对的形态。缓解：**完全离线可玩 + 原生能力使用（触觉/方向锁/安全区）+ 非内容站形态**，并在提审说明里主动论证这三点。**这是本方案最需要主动经营、而不能"装完就没事"的风险。**
3. **引入原生工具链**：Xcode 15+ / Android Studio / JDK 17，以及 Apple Developer（$99/年）、Play 开发者（$25 一次性）。CI 要能在 macOS runner 上出 iOS 包（成本显著高于纯 Web CI）。
4. **两份原生工程要维护**：`ios/` 与 `android/` 目录进入仓库，`cap sync` 之后要留意 `Info.plist` / `AndroidManifest.xml` 的手改内容被覆盖。缓解：手改项集中在一处并写进文档（`mobile-platform.md` §2.4/§2.5）。
5. **WebView 行为不可控**：iOS/Android 各版本 WebView 的 Canvas2D 合成路径、`env()` 支持、事件时序都有差异，**这是"白盒测试测不出来"的一类问题**——必须真机验证，且需要一套设备矩阵（至少：老安卓 WebView、iPhone 小屏、iPad 大屏）。
6. **放弃桌面 Tauri 路线图**（可逆，见 3.2）。
7. **审核节奏由平台决定**：热修一个 bug 在 Web 上是分钟级，在商店里是"提审 → 审核 → 灰度"。缓解：**把 Web 当灰度环境**，先在 Web 验证再打原生包。

### 4.3 风险接受与缓解对照

见 `mobile-platform.md` §7（Top3：光照合成掉 GPU 快路径 / WebView 内存被杀 / iOS localStorage 丢档）。三条都有具体缓解手段，**没有一条构成"不做"的理由**。

## 5. 什么情况下应该重新考虑这个决策（Revisit Triggers）

明确写下触发器，避免这次决策又变成一条"没人记得为什么"的历史记录：

| 触发条件 | 应重新评估的方向 |
|---|---|
| **真机实测**中端安卓 WebView 上冒险地图稳定低于 45 fps，且 §4 的降级手段（DPR 钳制 / 光照降档 / 图集瘦身）**全部用上后仍不达标** | 考虑**渲染层单独替换**：Canvas2D → WebGL（保留 `core/` 与输入层，只重写 `render/`），仍是 Capacitor 壳；再不行才考虑原生渲染器 |
| App Store 以 Guideline 4.2 / 4.7 反复拒审，且补原生能力（内购、Game Center、推送）后仍被拒 | 重新评估 iOS 端的可行性（可能只剩 Android），或走企业分发 / TestFlight 长期内测（不可上架） |
| 产品需要**深度原生能力**：实时多人联机、Game Center/Play Games 排行榜、复杂内购订阅、AR、后台定位 | 评估**局部原生模块**（写原生插件）还是整体转原生；多数情况下 Capacitor 插件 + 一个自写原生模块仍够用 |
| 玩家明确要求桌面版（Windows / macOS） | 重启 Tauri 桌面壳（复用同一 `dist/`），**双壳并存**而不是替换移动端 |
| Tauri v2 的移动端生态在 12 个月内追平 Capacitor（插件覆盖 / 真机稳定性 / CI 方案） | 可评估迁移，收益是桌面+移动统一工具链；**迁移成本应只在壳层，不涉及业务代码** |
| 包体或启动时间被商店/产品指标卡住（例如要求 < 5 MB） | 评估去掉 Splash 资源分档、只出单密度图标、按需加载 `ui/BattleScreen`（当前 45 KB 是最大单文件） |
| 出现 Capacitor 无法绕过的平台政策限制（如某平台禁止 WebView 上架） | 评估 WebGL + 原生壳的组合，或局部原生重写关键界面 |

## 6. 对本决策的诚实声明

- **性能未实测**：本 ADR 的"包体 < 15 MB"里，Web 资源部分是实测（493 KB），平台运行时部分是公开经验值；**帧率与内存全部是几何推算，未在真机上测过**。移动平台是否真能"手机 60fps 无压力"（`DESIGN.md` §十二 的原话），**必须真机实测后才能确认**——它是本决策唯一可能被推翻的技术前提。
- **因此给出分阶段建议**：先出 **Android 内测 APK**（门槛最低、无年费、审核快）验证手感与性能，**再决定是否投入 iOS**。这既是最省的验证路径，也把 `mobile-platform.md` §8.2 的开放问题（上架范围）变成了一个可以用数据回答的问题。
