### 1.1 两个此前没人发现的既存缺陷

**（a）`normal` 档的 AI 周增长加成几乎是空转。**
`town.ts:332-336` 的算法是 `Math.floor(g.count * mult)`。normal 的 AI `growthBonus = 0.1` → `mult = 1.1`：

| 兵种 | 基础周增长 | ×1.1 后 floor | 实际增量 |
|---|---|---|---|
| peasant | 10 | 11 | +1 |
| archer | 5 | **5**（5.5→5） | **0** |
| pikeman | 4 | **4**（4.4→4） | **0** |
| knight | 3 | 3 | 0 |
| angel | 2 | 2 | 0 |

即"普通档电脑周增长更快"这句描述，除农民外**一个兵都没多给**。

**（b）`aggression` 有隐性上界。**
`ai.ts:462` 用 `(1.2 - diff.aggression * 0.3)` 作为 outward 权重系数。当 `aggression ≥ 4.0` 时系数转负，AI 的"向外扩张"评分会反向。当前最大值 1.35 安全，但这是必须写进注释的约束。

## 2. 难度设计原则与难度哲学

> **命名说明（2026-09-19 改名，主理人批准）**：本节原先叫「设计支柱」，但仓库里的「**支柱**」一词**只指游戏设计支柱（探索 / 经营）**，权威出处见 `design/gdd/game-concept.md §1`。
> 下面四条是**难度这个子系统自己的设计原则**，不是游戏支柱 —— 沿用「支柱」会让读者误读成"游戏有四大支柱"。故改名 **D1–D4**。
> **术语约定**：其他子系统同理，其原则须命名为「<子系统>设计原则」，不得复用「支柱」一词。

**D1：难度是"我这边变难"，不是"对面变笨"。**
玩家必须能在三档里感受到自己的处境不同——资源、行军、野外阻力。

**D2：normal 必须零改动。**
所有玩家侧倍率在 normal 一律为 1.0，保证现有玩家的基准手感**一个字节都不变**。这是本次改动的回滚底线。

**D3：E2/E3 之后，AI 的"作弊系数"应当下调，而不是上调。**
E2（AI 会发展：英雄兵峰值 +63%、建筑数 +31%）与 E3（无城 7 日出局 + 矿场动态权重）已经让 AI 会**转化**资源了。旧数值（hard `startMul 1.4` / `growthBonus 0.3`）是在"AI 会浪费资源"的前提下调的，现在再叠加就是纯资源碾压。所以 hard 的 AI 侧倍率**下调**，把难度来源从"数值碾压"转向"对手水平 + 玩家自身受压"。

**D4：一个旋钮管一类对象。**
新增字段只有 4 个，且每个都对应一类清晰的对象（玩家资源 / 玩家增长 / 玩家移动 / 全部非玩家部队），不做"按地形/按天数"的特例表——否则半年后没人敢调。

## 5. 每个数值的理由

**`playerStartMul` = 1.2 / 1.0 / 0.7** —— 锚点是**兵营 `dwell3`（2500 金 / 10 矿）**，它是开局第一个真正的决策：
- normal 2500 = **正好**够兵营，一天不差（基准手感）。
- easy 3000 = 兵营(2500) + 市场(500 金 / 5 木)，**正好**把木石卡脖子的问题一次解决，且**没有余量挥霍**（剩余 0 金 + 7 木 / 2 矿）。选择"正好"而不是 3250，是为了让轻松档仍有一个"先兵营还是先市场"的真决策，而不是无脑全买。
- hard 1750 = **第 1 天盖不起兵营**。500 金/日的基础税收下，D1 结算 2250、D2 结算 2750 → **最早第 2 天末**建成，推迟 1 天且矿石（7 + 矿场 3/日）同步吃紧。选 1750 而不是 1500，是因为 1500 会把"招第二个英雄（2500）"推到离谱的远处，且与市场之外的所有选项互斥，会退化成"唯一路线"。

**`playerGrowthBonus` = +0.25 / 0 / 0**（**决策②已闭合 · D-21：困难档不给负向周增长**）—— 数值由 §1.1(a) 的 floor 缺陷倒推：
- 小于 0.20 的正向加成对弓手 **完全无效**（5×1.15=5.75→5）。要让"轻松档真的多产弓手"，0.25 是**能让弓手 5→6 的最小值**，再往上 0.30 对弓手仍是 6（6.5→6），收益断层。所以 0.25 是性价比拐点。**困难档保持 0，不做对称的负向。**
- **为什么放弃 −0.10（记录被否掉的方案，防止有人再提）**：−0.10 是全表**最重的单点惩罚**（天使周增长 2→1 腰斩），且因 floor 缺陷，**任何负值都是离散跳变**（详见 §4.3 表）。更关键的是它是**唯一会让进行中的旧存档中途变难**的字段（用户设备上已有存档）。⇒ **D-21 拍板：不给**。困难档的强度改由**开局 ×0.70 / 移动力 ×0.90 / 野怪 ×1.25 / AI 更早出击**承担——这四处都是**开局即确定、玩家立刻能感知**的，而周增长是长线、隐形的。
- **代价（明说）**：困难档**中后期**压迫感因此变弱。若日后实测确认偏软，**要重新开决策**再补负向，不要据此档自行加回。

**`playerMoveMul` = 1.15 / 1.0 / 0.90** —— 移动力是**复利型**杠杆（每天 +2.7 / −1.8 格，30 天累计 ±54 格 ≈ 中型图两条对角线），不能给太猛。±10~15% 是"日感知几乎无感、月尺度明显"的量级。取 0.90 而不更低，是因为低过 0.85 会让人觉得"游戏变卡了"而不是"游戏变难了"——那是**负体验**不是**难度**。

**`monsterMul` = 0.75 / 1.0 / 1.25** —— 锚点是"弱档野怪必须仍然打得过"。
- 弱档守卫是玩家前 10 天的**主要现金来源**（700–1600 金 ≈ 1.4–3.2 天的城税）与**矿场来源**（金矿 400/日）。把它放大到打不动，会让困难档直接经济断流，那是死亡螺旋不是难度。
- 1.25 时弱档狼 25–35（200–280 总血），起手 20 弓手（200 血 / 12 发）仍能靠风筝拿下，但会疼。**1.35 会越过这条线**，所以取 1.25。
- 0.75 与 easy 的 AI `startMul`（原 0.75）保持同一个数字，便于口头沟通："轻松档所有非玩家的东西都打七五折"。

**AI `startMul` = 0.70 / 1.00 / 1.25**（原 0.75 / 1.0 / 1.4）—— hard 从 1.4 降到 1.25：E2 之后 AI 会把资源真正变成兵和建筑，1.4 的边际收益比半年前高得多。降 0.15 是"抵消 E2 增益"的估计量。

**AI `growthBonus` = 0 / 0.10 / 0.20**（原 0 / 0.1 / 0.3）—— 同理下调 0.1。**normal 保持 0.10 不变**：虽然它因 floor 缺陷近乎空转（§1.1a），但把它抬到 0.20 会让 normal 的 AI 凭空多产弓手，等于**悄悄把普通档变难**——违反 **D2**。
（**勘误**：本段原文末尾写作"列为决策②"，是**误标**——决策② 指的是"困难档玩家负向周增长"，与 AI 的 `growthBonus` 无关。是否把 normal 的 AI `growthBonus` 提到 0.20 **从未列为决策**，按 D2 保持 0.10 / 与代码一致。另 AI `startMul` / `growthBonus` / `aggression` 三档取值与 `core/data/factions.ts` **完全一致** ✅。）

**AI `aggression` = 1.50 / 1.10 / 0.80**（原 1.35 / 1.0 / 0.75）—— normal 从 1.0 抬到 1.10（阈值 200→220），是因为 E2 让 AI 攒兵更快，若门槛不变它会比今天更早出门，normal 会变味；+10% 是抵消项。easy 抬到 1.50 让"发育迟缓"更明确；hard 抬到 0.80（阈值 160）让它敢带更薄的队伍出门。

### 5.1 总难度曲线（等距校验）

以"同一时刻 AI 资源 ÷ 玩家资源"作为压力比：

- easy：1750 / 3000 = **×0.583**
- normal：2500 / 2500 = **×1.000**
- hard：3125 / 1750 = **×1.786**

取对数：ln 分别为 −0.539 / 0 / +0.580。**三档在对数尺度上基本等距**，说明"轻松给的甜头"与"困难给的苦头"量级相当，不会出现一侧过陡。这是一条**校验结论**，不是设计目标——它证明三组数不是随手挑的。

## 6. `opponents` 默认值：**1**（✅ 已拍板 · **D-20**）

原状 `DEFAULT_CONFIG.opponents = 0`（`core/data/factions.ts`）；**决策记录 `production/roadmap.md` D-20 = 1（0 仍保留）**，代码已落地为 `1`。

**为什么是 1**，理由：

1. **直接修掉摆设问题**：有对手时，AI 侧三根杠杆才有效。
2. **节奏合适**：中型图 32×32、2 个阵营，`layoutHomeIdeals` 保证两家距离恒定；按 18 格/日的移动力，探索期约 7–10 天后接触，留足发育窗口。
3. **不默认 2**：默认局是玩家的第一局。2 家 AI 会在第 2 周形成夹击，第一局体验太陡。2 家应当留作"我玩明白了"之后的主动选择。
4. **0 仍然保留**在 UI 里（`StartScreen.ts:136`），且此时难度**依然生效**——通过 `playerStartMul` / `playerGrowthBonus` / `playerMoveMul` / `monsterMul` 四根玩家侧杠杆。这正是本次重设计的意义：**对手数量不再是难度的前提**。

## 9. 边缘情况

**9.1 招新英雄 = 移动力后门（漏洞级）**
`town.ts:543` 用 `BASE_MOVE_POINTS` 硬编码给新英雄满移动力。若不同步缩放，困难档玩家可以花 2500 金招一个"满移动力"英雄，把 `playerMoveMul: 0.9` 完全绕过。改动 #12 是**必须项**，不是优化项。

**9.2 旧存档不会因为周增长而中途变难（决策② 已闭合 · D-21）**
新增的 4 个字段全在**数据表**里，不在 `GameState` 里 → 存档结构零变化，`VERSION` 保持 7，不需要迁移。
`playerGrowthBonus` 是**运行时每周结算**生效的，所以任何**玩家侧负值**都会让进行中的旧档在更新后立刻被扣周增长。**D-21 已拍板困难档不给负向**（`playerGrowthBonus = 0`，与代码 `factions.ts` 一致）⇒ 三档为 **+0.25 / 0 / 0**，**旧存档风险归零**。
- 保留的旧档风险**只剩"利好方向"**：进行中的 easy 档会立刻多得周增长（+0.25）——这是**增益**，不需要处置。
- 不推荐 bump `VERSION` 到 8：`loadGame()` 会因版本不符**直接丢弃存档**，丢档远比这点差异严重。

**9.3 种子稳定性**
`monsterArmy` 用 `mulberry32` 序列。只要在 `randInt()` **之后**乘系数、`Math.round` 归整，**rng 调用次数与顺序完全不变** → 同种子仍生成同样的地形、城镇位置、野怪分档，只有数量变化。
**红线**：任何"为了难度多摇一次骰子 / 少摇一次骰子"的实现都会让全服种子失效。必须在 `monsterArmy` 上方写死这条注释。
附带：默认 `opponents` 0→1 会改变 `layoutHomeIdeals(count)` 的入参，**同种子在新版本生成的图与旧版不同**。跨版本分享种子会失效，属可接受的一次性代价。

**9.4 `aggression` 必须 < 4.0**
`ai.ts:462` 的 `(1.2 - aggression × 0.3)` 在 `aggression ≥ 4.0` 时转负，AI 的向外扩张评分会反向（越远越不想去）。当前最大 1.50，余量充足，但这条约束要写进 `DifficultyDef.aggression` 的注释。

**9.5 `Math.floor` 让小幅增长加成失效**
见 §1.1(a)。实现时**不要**试图"优化"成 `Math.round`——那会同时改变 AI 的既有行为。保留 floor，靠**把数值选在拐点上**（0.25 / 0.20）来绕开它。

**9.6 数值退化到 0**
`Math.max(1, Math.round(count × mul))` 是**必须的**。`boar 4 × 0.75 = 3` 当前安全，但如果未来 `monsterMul` 调到 0.5 以下，1 只的栈会归零 → 生成一个空部队，战斗系统可能崩。

**9.7 `opponents: 0` 时 AI 侧三参数无对象**
此时 `startMul` / `growthBonus` / `aggression` 全部空转——这是**设计上接受的**（难度改由玩家侧 4 根杠杆承担）。但 `town.ts` 与 `ai.ts` 里对 `DIFFICULTIES[...]` 的读取不能因为"没有 AI"就崩，保持现状即可（它们本来就是在遍历 `factionIds` 时空转）。

### 10.1 E3 矿场权重耦合（本次最需要工程确认的一条）

`ai.ts:315-321` 的矿场权重按"相对资源缺口"计算：`missing = max(0, ref − stock) / ref`，权重 `1 + min(1, missing) × 1.2`（最高 2.2×）。
把 easy 的 AI `startMul` 从 1.0 降到 0.70 → AI 起始库存变低 → `missing` 变大 → **easy 档的 AI 会更凶地抢矿**。这与"轻松档电脑发育迟缓"的意图**部分对冲**。

两个选择，需与工程对齐：
- **(a) 接受**：AI 抢矿是"更聪明"而非"更强"的表现，且抢矿要打架，弱 AI 打得反而更差。改动量 0。
- **(b) 让 `ref` 也随难度缩放**：`ref × diff.startMul`，使缺口计算保持相对一致。改动量小，但会牵动 E3 已验收的权重行为，**需要重跑 E3 验收**。

我的建议是 **(a)**，理由是 E3 刚验收过，不值得为一个"方向相反但幅度不大"的耦合去重跑验收。**这条要请程基岩确认。**

### 10.2 hard 不可赢时的降级预案（按优先级）

1. `playerStartMul` 0.70 → 0.80（回 250 金 ≈ 半天，最便宜的放松）
2. `monsterMul` 1.25 → 1.15（弱档狼 23–32，回到"打得动"区间）
3. **最后**才动 AI 侧 `startMul` 1.25 —— 动它会牵动 E3 权重（§10.1）

> ~~原第 3 条「`playerGrowthBonus` −0.10 → 0」已作废~~ —— **D-21 已直接把该值定为 0**，它不再是一个可调的放松旋钮。困难档若仍偏难，就按上面 1 → 2 → 3 的顺序松。**不要为了"给困难档加压"把 `playerGrowthBonus` 调成负值**，那会重新引入旧档中途变难的问题（§9.2）。
