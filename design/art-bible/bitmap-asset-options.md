## 0. 如果你只读一段（TL;DR）

- **位图** = 把画面的像素**事先存成一张图片文件**（PNG 等），代码不再当场画，只把文件读出来贴上去。
- **我们现在是"零位图"**：整个游戏**没有一个图片素材**，所有画面都是代码当场算出来的。这是**硬事实**（核验命令见附录）。这是本项目最不寻常、也最值钱的一条架构约定。
- **五档选项**（互斥，见 §2）：
  - **(a) 维持零位图**（现状）
  - **(b) 极小切片** —— 只给"大尺寸门面"用位图（启动图 / 选族立绘 / 英雄城堡 / 过场插图 / 单位头像），**游戏内地图与战场仍全部程序化**
  - **(c) 中型切片** —— 再允许**地形砖 / 地表 / 地图装饰**用位图，单位仍程序化
  - **(d) 全面位图** —— 单位、地形、UI 全部位图
  - **(e) 等尺寸位图替换** —— 把现有 32/24/64px 资产**按原尺寸**换成 PNG，**分辨率不变**（用来"证伪"：贴图本身到底等不等于画质）
- **我的结论（专业意见，非实测）**：
  1. **推荐 (b)**，且**先做 1 张验证、不批量**。
  2. **位图不是"画面提升"的必要条件。** 用户说"感觉不到提升"，真正的瓶颈在**尺寸 / 内容量 / 地图尺度构图**，而不是"像素是画出来的还是存下来的"（论证见 §3）。
  3. 位图只在**"大尺寸 · 非平铺 · 构图性 · 复用率低"**的一小撮资产上有**真实增益** —— 那正是 (b)。其余部分程序化**还没榨干**。
  4. 位图意味着**"要有图的来源"**（画师 / AI / 授权素材 / 外包）。这一条在本项目是**从零新增的产能面与法务面**，**与体积、内存同等重要**，且在 (c)/(d) 里才是真正劝退项（见 §2.3）。

## 1. 先讲清楚：「位图」和「程序化」到底差什么（给外行）

### 1.1 用我们自己的例子

| | 现在的做法（程序化） | 位图的做法 |
|---|---|---|
| 地图上那棵树 | `atlas.ts` 里约 **40 行代码**，运行时当场算出每个像素，画进一张离屏画布 | 一个叫 `tree.png` 的文件，里面**已经存好**了那棵树的像素 |
| 运行时发生什么 | 每次启动，代码**重新画一遍** | 代码**把文件读出来贴上去** |

**差别只有一句话**：像素是**"当场算出来的"**，还是**"事先存好的"**。

### 1.2 为什么这不是「好 / 坏」，而是「换一种代价结构」

两种做法都**能画出像素画**。区别不在"画得像不像"，在于**这笔成本付在哪**：

| | 程序化（现在的做法）买什么 | 它的代价 |
|---|---|---|
| **优点** | ① 体积 ≈ 0（不进安装包）② **可参数化**：改 1 行代码就能换族色 / 换尺寸 / 生成一整批 ③ **一致性来自结构**（同一套骨架，20 个单位一定像一家人）④ 能做动画（`squash & stretch` / idle 浮动）⑤ 天生只使用我们的色板 | ① 要**写代码**，不能"画" ② 画不出**有机细节**（布褶 / 毛发 / 写实纹理）③ 每加一个新造型要重新编码 |

| | 位图买什么 | 它的代价 |
|---|---|---|
| **优点** | ① 画面**细节上限高**（一笔就是一笔）② 可以**买现成的 / 外包**（不占我们的编码时间）③ 改图不用改代码 | ① **体积进包** ② **内存**（解码后按 w×h 常驻）③ **网络请求 / 首屏延迟** ④ **要有图的来源**（见 §2.3）⑤ 一致性**靠人盯**，不靠结构 ⑥ **最近邻 + 非整数缩放下会劣化**（见 §3.3）⑦ 改一张 = 重走一遍管线 |

> **一句话**：位图不是"更高级的画"，它是**把成本从"编码时间"挪到"素材产能 + 体积 + 内存"**。

### 1.3 一个反直觉的事实：本项目的"好看"不来自像素密度

我们这套画面的**识别度**来自 4 条纪律（见 `cartoon-style.md`）：

1. **1px `ink0` 暖色描边**（一律最近邻、硬边）
2. **四族调色板**（每族一个母题色区间）
3. **每个单位只有一处比例失调**（卡通的核心，不是"越怪越好"）
4. **切角**（直角一律切掉）

这 4 条**位图也能满足**（要走 §4 的管线），但**它们不是位图带来的**。少了纪律，位图只会让画面**更花**，不会更"高级"。

## 2. 选项（5 档，互斥、可执行）

### 2.1 总表

| 选项 | 允许什么 | 用来买什么 | **明确不允许什么** | 图的来源 | 主要代价 |
|---|---|---|---|---|---|
| **(a) 维持零位图** | 什么都不允许 | 最低体积、零来源面、最强结构一致性 | 任何图片文件 | **不需要** | 大尺寸叙事图像只能靠程序化构图（这是弱项） |
| **(b) 极小切片（英雄镜头）** | 只允许**大尺寸 · 非平铺 · 静态**的位图：启动图 / 选族立绘 / **英雄城堡** / 过场插图 / 单位头像 / 加载图 | 门面画质 + 叙事表现力 —— **位图唯一有真实增益的表面** | **地图格内的任何物**（单位 / 地形砖 / 装饰 / UI 图标）**不得用位图** | 画师或 AI（AI 走 7 步管线） | 新增来源面（小）+ 少量体积 + 一次管线投入 |
| **(c) 中型切片（地形/地图装饰也位图）** | 在 (b) 之上，地形砖 / 地表 / 地图装饰也可位图 | 单块地表的"笔触 / 材质"上限 | **单位剪影仍程序化**（不进 4×5 矩阵） | 画师 / AI，但**数量级上升**（地形砖 26+ 张起） | 重写成本 + 平铺无缝 + **与 §3.1.1 地图层冲突** + 两种管线并存 |
| **(d) 全面位图** | 单位、地形、UI **全部**位图 | 追 HOMM3 那种手绘密度 | 不再由结构保证一致（或必须人工守） | 需要**一支画师团队或大额外包** | 产能 / 法务 / 体积 / 内存 / 一致性**全面上台阶** |
| **(e) 等尺寸位图替换** | 允许把现有 32×32 / 24×24 / 64×56 资产**按原尺寸**换成 PNG，**分辨率与帧数都不变** | **用来"证伪"**：同分辨率下，贴图本身是否等于画质 | 不改任何尺寸 / 帧数 / 网格 | 画师 / AI | 几乎只增加体积，**画质提升按定义 ≈ 0** |

> **五档的关系**：**(b) ⊂ (c) ⊂ (d)** 是"允许位图的表面"逐级放大（后面的档包含前面的）。**(e) 是另一根轴** —— 它和 (a) 用同样的表面，只换介质，专门用来**隔离变量**：如果 (e) 都不能让用户觉得画面变好，就说明"贴图 ≠ 画质"。

### 2.2 逐档说明

**(a) 维持零位图（现状）**
就是现在这样：没有一个图片文件，一切都是代码。**它不会给你**：一张能"讲故事"的启动图、一张能"撑门面"的选族立绘、一张有想象力的过场插图。这些位置要么留白，要么用程序化色块硬凑（偏弱）。

**(b) 极小切片 —— 只给"英雄镜头"用位图**
把位图**严格限制在"游戏世界之外"的大图**上：启动 / 加载图、选族页立绘、地图上的英雄城堡（全项目最大精灵，72×96）、过场插图、单位头像。**游戏内的地图格、战场、UI 图标一律仍程序化。** 它买到的是"**打开游戏第一眼**"的画质，以及叙事表达力。**它不会给你**：地图上的任何"更精细"——因为地图格内的东西**明确不允许**位图。

**(c) 中型切片 —— 允许位图地形与地图装饰**
在 (b) 之上，把**地形砖（32×32 平铺）和地图装饰**也交给位图，单位仍程序化。它买到的是"单块地表的材质感"。**它不会给你**：地图整体观感的提升 —— 因为**铺开之后的问题（壁纸感）位图一样有**（§3.1 第 2 行）。而且它会**和我们已经做对的那一层打架**（§3.1.1 的地图层是靠程序化在烘焙期算光，不靠砖的精度）。

**(d) 全面位图**
单位、地形、UI 全部交给位图，走 HOMM3 的手绘路线。**它买到**：最接近"手绘沙盘"的观感。**它的代价是全面的**：需要一支画师队伍（本项目目前**一个画师都没有**）、法务面（许可 / 署名 / 二次分发）、体积与内存上台阶，以及**放弃"结构保证一致性"** —— 20 个独立单位要满足 `cartoon-style.md §5.6` 的 4×5 正交矩阵（形状家族 × tier 体量），这件事**程序化靠结构一定成立，人工凑几乎必然退化**（`asset-spec.md` §4.2 R5）。

**(e) 等尺寸位图替换（对照实验档）**
把现有资产**按原尺寸**换成 PNG（32px 的砖还是 32px 的砖，64×56 的单位还是 64×56）。**它买到的是答案，不是画质** —— 因为分辨率没变，位图能装的像素量和程序化一样多，**画质提升按定义 ≈ 0**，代价却几乎只有体积。**这档不是拿来选的，是拿来"证伪"的**：做 1 张，向用户证明"问题不在贴图"。

### 2.3 ★ 一等成本：位图的「来源」—— 本项目从零新增的产能面与法务面

**一个必须点明、且通常被忽略的事实**：

> **本项目没有任何画师，也没有任何外部素材。所有美术都是程序化代码。**
> ⇒ (b)(c)(d)(e) 里"位图从哪来"这个问题，在本项目**没有一个现成答案**，它是**从零新增**的四条路：

| 来源 | 现成条件 | 适用 | 代价面 |
|---|---|---|---|
| **① AI 生成** | 已有 **7 步管线**（抠底 → 块众数降采样 → 钳色 → 整数比缩放 → **描边重建** → 手修 → PNG-8，见 `asset-spec.md` §5） | **大尺寸 · 少量 · 门面图** | AI 天生带脏色（P1.4 草稿约 40 种浑浊中间调，缩到 44px 读成一坨褐色）；**不适用** 32px 单位（细节在降采样那一步被销毁） |
| **② 招画师** | 无 | (c)/(d) 的持续产能 | 进入招聘 / 协作 / 版本管理 / 风格把控的人力面 |
| **③ 买授权素材** | 无 | 理论上最省事 | **法务面**：商用许可 / 可否修改再分发 / 是否要求署名；且现成素材与本项目的 32px / 四族风格**几乎不可能对得上** |
| **④ 外包** | 无 | 一次性买"门面图"可行 | 风格一致性要**我们出规范 + 逐张验收** |

**法务面三个必答**（任一路都要先答）：**能不能商用 / 能不能改了再发 / 要不要署名。**

## 3. 画质天花板分析（**本文最核心、最需要诚实的一节**）

### 3.1 逐资产类别：程序化真的到顶了吗？

| 资产类别 | 典型尺寸 | 位图会不会真的更好？ | 判断 |
|---|---|---|---|
| **32–64px 单位精灵**（20 兵种 ×3 帧） | 冒险 52×44 / 战斗 64×56 | **不会** | 画布就这么大，位图和程序化**存的像素数一样多**；卡通的本质是"**减少信息量**"，而位图的优势（更多有机细节）**正是我们要丢的东西**；且 4×5 正交矩阵（形状家族 × tier 体量）**只有程序化的"结构一致性"能保证**。⇒ 维持程序化 |
| **地形砖（32×32 平铺）** | 32×32 | **不会，甚至更差** | 平铺砖要的是"无缝 + 铺开不露重复"；**位图平铺同样会露重复**。真正的瓶颈是"**地图尺度的大地貌**"，而这一层**已用零位图手段解决**（`cartoon-style.md` §3.1.1：烘焙期叠方向光 + 低频起伏；口径 = **全草地图、无物件**，见 §7）。⇒ 维持程序化，继续榨"地图层" |
| **大地图背景（整张，非平铺）** | 视口 752×264 × zoom | **可能真的更好（有条件）** | 非平铺、构图性强，是程序化**较难做**的；但会与 32px 单位 / 砖**并置**（风格风险 §4），且"整图多大、多少张"的内容量成本**未测**。⇒ 归入 (b) 或 (c)，**先小规模验证** |
| **UI 图标** | 24×24 | **不会** | 24px 太小，位图无优势；图标要"一族一眼可辨"，一致性靠结构。⇒ 维持程序化 |
| **城堡 / 城镇立绘**（地图上的英雄城堡） | 72×96 | **会** | 全项目**最大精灵**、构图强、**复用率低**（只 4–5 张）、是"城市风格差异化"最强的表达点。⇒ 归入 (b) |
| **阵营立绘 / 过场插图 / 启动图 / 单位头像** | 256×384 等大图 | **会** | **一次性 · 叙事性 · 大尺寸**；程序化的构图能力是真实短板；**不进游戏内地图网格**，不破坏 32px 世界。⇒ 归入 (b) —— **这正是唯一该给位图的地方** |

### 3.2 ★ 直接回答：「换成位图就能解决'画面感觉不到提升'吗？」

**不能 —— 至少单靠位图不能。** 三条真正的瓶颈，**没有一条在"像素来源"这一层**：

1. **尺寸天花板 —— 但两个"尺寸"必须分开（本档 V1.4 更正一处事实错）。**
   - **世界尺度（真的偏小）**：我们的**巨型地图** `48×48`（`MAP_SIZES.huge`，是**地图格数**，**不是单位**）只到 HOMM3 **XL 图 `144×144`** 的 **33% 边长 / 11% 面积**（出处 `design/maps/homm3-map-design-lessons.md §3.1`：48/144 = 0.333）。⇒ 世界偏小：**主城→主城** 巨型/旷野 = **2.6 天**（8-seed 中位；同文 §3.2）。
   - **单位尺度（其实不小）**：单位画布 = 地图 `u_*_map` **52×44** / 战斗 `cu_*` **64×56**（`asset-spec.md §2`）。**52 宽**对 `TILE=32` 的格子 ⇒ 一"队"**已横跨 ≈1.6 格**，**相对格子偏大**（HOMM3 的单位大致也只占 1 格）。⇒ **"单位画得太小"这条常见解释在本项目站不住。**
   **两条都是"世界 / 格子"尺度的量，位图都不改** —— 换成 PNG，巨型地图还是 48 格、单位还是 52px。
2. **地图尺度的构图。**
   屏幕 **90% 面积是地形**（`cartoon-style.md` §3.1.1）。**砖画得再细，100 块一样的砖铺开还是壁纸。**
   §3.1.1 用**零新资产**的改法（烘焙期叠一层地图尺度的明暗）就量到了**可感知的提升**：**逐格平均 L\* 极差 2.37 → 31.79、相邻格平均 \|ΔL\*\| 0.49 → 2.22**（脚本链 = `tools/artshot.mjs` 出 `g_uniform_*.png` → `CMP_TILE=32 node tools/imagecmp.mjs …`；commit `b4c1c93` / `8cfd35b`）。
   ⚠️ **口径不可省：全草地图、无物件** —— 同一算法换到"全地形 + 全物件"的图上会变成 **58.6 → 63.5 / 2.71 → 3.13**（都对，量的不是同一件事）。
   ⇒ **这证明瓶颈在"地图尺度"这一层，而这一层恰好是程序化擅长的**（算方向光 / 低频起伏是代码的强项，不是画师的强项）。
3. **内容量 / 变化量。**
   玩家看到的是"**种类少、变化少**"。**位图不增加种类、不增加帧数。**

> **★ 一条真机视口的旁证（支持本节结论）**：在**真机视口 `792×320 @DPR3`**（`tools/deviceshot.mjs`，**真实 headless Chrome**）上实测，**裁到地图区** `CMP_CROP=84,804` ——
> ① 地貌层 关→开（同 mid 档）：平均 \|ΔL\*\| **1.41**（变化像素 22.8%）；
> ② 只降渲染倍率（同 high 档，`?devdpr=1.5`）：平均 \|ΔL\*\| **1.26**；
> ③ 档位 low↔high：平均 \|ΔL\*\| **2.28**（变化像素 28.0%）；④ 同配置抓两次：**0.00**（噪声底）。
> ⇒ **"档位差"≈"地貌层"的 1.6 倍**（2.28 / 1.41），**且档位差里 dprCap 占逾半**（②/③ ≈ 55%）—— 所以**"档位差主因是氛围层"这个猜测不成立**（锐度同等重要）；用户真机自动探测正落在 **low**（G-15）。
> **意义**：真机上这些差**能测出来、但不足以读成"一次画质升级"** —— 真正的杠杆在**尺寸 / 内容量 / 构图**，**不在"像素是画出来的还是存下来的"**。**又一次说明瓶颈不在位图。**
> ⚠️ **诚实边界（两条）**：㈠ 档位对照（③）**混了两个变量**（氛围层开关 ＋ `dprCap` 倍率），非"纯氛围层"测度；㈡ **数字绑构建** —— ①②③④ 绑 **`a43acee`**（其后 `f62713f` 改了 `setDressing.ts` ⇒ HEAD 需重抓）；本条曾引的 `0.75 / 2.14` 是**已被取代的"整页"口径**（未锁构建），换成地图区后即本条的 `1.41 / 2.28`。出处 `shots/README.md`。

> **⇒ 结论：位图是"画质"的必要条件吗？不是。**
> 它只在**一小撮"大尺寸 · 非平铺 · 构图性 · 复用低"的资产**上是**充分增益** —— 而那正是 (b)。
> 其余部分（地图 + 战场 + UI），**程序化还没榨干**：地图层目前只解冻了"明暗"（§3.1.1），**还没做地貌特征、水体、更多砖变体**。
>
> **给用户的一句话**：如果目标是"**打开就觉得画面牛**"，**先做 (b)（门面图）＋ 继续榨地图层**，性价比远高于"把 32px 单位换成 PNG"。

### 3.3 反例论据：最近邻 + DPR 3 + 非整数 zoom ——「位图能提升画质」的一个直接反例

- 本项目的渲染纪律是 **`imageSmoothingEnabled = false`**（一律**最近邻**，为的是硬边像素的干净）。相机 **zoom 默认 2、区间 0.75–3**；真机 **DPR 3.0**（OPPO PMA110）。⇒ 位图会被**以非整数倍**放大到屏幕（zoom 可能是 0.75 / 1.3 / 2.7 …）。
- **后果**：最近邻在**非整数缩放**下会出现像素块**忽大忽小的抖动 / 锯齿**，位图原本的细节反而**劣化**；程序化因为每次都"按当前整数像素重画"，**没有这个采样问题**。
- **这一条正好打在 (c)/(d) 上**（游戏内地图 / 单位会随 zoom 变化）。**对 (b) 的"面板型"图影响小**：立绘 / 头像 / 启动图 / 插图贴在**固定大小的面板 / DOM 卡片**上，**不参与地图 zoom**。⚠️ **但 (b) 若含"英雄城堡"就不成立** —— 城堡画在地图网格里、随 `zoom`，**§3.3 对它同样适用**（见 §2.4 的澄清）。
- **⇒ 规则**：位图要**用在能整数倍呈现的地方**，否则它买到的不是画质而是**劣化**。

## 4. 风格一致性风险

**本项目的识别度来自 4 条纪律**（§1.3）：1px `ink0` 暖描边 / 四族调色板 / 每单位一处比例失调 / 切角。

- **位图能不能守住这 4 条？能 —— 但不是自动的。**
  必须走 7 步管线里的 **"钳色 + 描边重建"** 两步（`asset-spec.md` §5.4）。**步骤 [5] 描边重建是让外部资产与本项目"像一家人"的唯一决定性步骤**：丢掉外部图自带的不均匀描边，用 `PixBuf.outline(ink0, 1.0)` 重跑。**省略它，(b) 就会变成"两张图贴在一个像素游戏上"。**
- **(c)/(d) 的额外风险：两种画风并置。**
  位图地形（有材质笔触）紧挨程序化单位（平涂）→ 画面读成"**两个游戏拼起来**"。这正是被废弃的 P1.4 SNES 草稿的病（约 40 种浑浊中间调，缩到 44px 读成一坨褐色）。
- **(d) 的风险最大**：项目不再有"同一套骨架"来保证一致性，**一致性从"结构保证"变成"人工保证"** —— 20 个独立单位要在形状家族 × tier 体量上两两可辨，人工凑几乎必然退化成"四套换色 + 额外帽子"。
- **维护路径**：一旦 (c)/(d)，"改一个单位" = 重新生成 → 重跑管线 → 人工重验；而程序化**改 1 行代码即可**。

> - **产出（等排期到）**：① (b) 里挑**收益最高的 1 张**（"打开游戏第一眼"那张），走**既有 7 步 AI 管线**；② **1 张 (e) 对照**；③ **一对改前 / 改后** + 一句"**你应该注意到什么**"；④ **诚实预期：(e) 的预期结果是"看不出变化"，而这正是它的用途** —— 报告里**不许包装成"提升"**；用户判断的是"**这个方向值不值得投**"。

### 6.2 复审触发条件（**满足任一 → 回来重看本题**）

| # | 触发条件 | 届时看什么 |
|---|---|---|
| **R1** | 做完 (b) + 地图层之后，用户**第 2 次**仍说"画面没提升" | ⇒ 假设错在"资产来源"，转向"**尺寸 / 内容量 / 构图**"假设（放大单位？加帧数？加 tile 变体？） |
| **R2** | **地图层三条延展手段全部落地**（= team-lead 定义的 `X`，见下；**不是一个数字**） | ⇒ 这才是 (c) 值得考虑的时点，**且优先用位图做"整张非平铺背景"而非 32px 平铺砖** |
| **R3** | 团队**真的**有了画师 / 外包产能 | ⇒ (c) 的"来源"成本下降，重新比价 |
| **R4** | (b) 的 1 张验证证明"**玩家确实感知到门面图提升**" | ⇒ 扩到 (b) 全量，并评估是否值得进 (c) |
| **R5** | 真机出现**位图劣化**（非整数 zoom 下的抖动 / 锯齿） | ⇒ 回退 (a)，或把位图限制在"**整数倍呈现**"的表面 |

> **`X` 的定义（team-lead 2026-09-21 拍板 · 刻意不用数字）**：`X` = **地图层三条延展手段全部落地** ——
> ① **地貌特征**（不只是明暗：有可辨识的地貌单元）；② **水体表现**；③ **砖变体数量翻倍**（当前 N → ≥2N）。
> ⇒ **`X` 达成 = "程序化在地图层还没榨干"这句话不再成立**，到那时才谈 (c)。
> **理由**：本档 §3.2 第 2 条自己写了"地图层只解冻了**明暗**，地貌特征 / 水体 / 更多砖变体**还没做**" —— 那三条就是"榨干"的**可核定义**，比随手拍一个数可靠。
> **如果这三条全部落地后仍没有可感知提升，那才是 (c) 的真正证据。**
