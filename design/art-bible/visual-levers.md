# 画面提升的三条杠杆 —— 互斥选项 · 代价 · 「玩家看到什么不同」

> **状态**：决策稿（待项目所有者 / 主理人拍板）
> **作者**：林绘澄（美术 / 视觉 / 可访问性）
> **读者**：项目所有者（**不懂美术术语**）+ 主理人
> **它回答什么**：用户 `F-3.7`「画面没提升」——**位图之外**，真正能把这件事推进一步的，是哪**三条**杠杆、各有哪几种**互斥**做法、代价多高、**玩家能看出什么不同**。
> **上游结论（已论证，本文不重复）**：**位图不是画质提升的必要条件** —— `bitmap-asset-options.md §3`；**地貌层（明暗）已落地** —— `cartoon-style.md §3.1.1`（真机视口 平均 \|ΔL\*\| **1.41**，量级偏小）。
> **不重复规格**：地图层三条的**配方 / 判据**在 `cartoon-style.md §3.1.2`（X1 / X2 / X3）；位图五档在 `bitmap-asset-options.md §2`。**本文是决策层**，只做「互斥选项 + 代价 + 感知」。
> **共同硬约束（三条都不破）**：`TILE = 32` · `imageSmoothingEnabled = false` · 画家算法不改 · **零位图**（本文三条**都不引入任何图片文件**）。

## 0. 如果你只读一段（TL;DR）

用户说「画面感觉不到提升」。已经被排查掉的解释：**贴图来源**（位图 ≠ 画质）；**地貌层明暗**（已落地、量级偏小）。**剩下三条杠杆**：

1. **尺寸** —— 东西画得**够不够大 / 够不够细**。
2. **内容量** —— 同样的东西**有没有变化**（砖变体 / 帧数 / 物件种类）。
3. **构图** —— **整张地图**有没有可读的「大结构」（成片林 / 水 / 取景）。

**我的结论（专业意见，非实测）**：
- **先做「内容量 C1（砖变体 3→6）」+「构图 G1（地貌区）」** —— 两条都是**零新资产、零位图、只改烘焙参数或一行取模**，且感知增益最大（配方见 `cartoon-style.md §3.1.2` 的 X3 / X1）。
- **「尺寸」里只有 S2（提默认 zoom）是低成本的**；S3 / S4（放大单位画布 / 提 TILE）是**全面返工**，**不建议**。**"单位太小"这条常见解释，在本项目站不住** —— 我们的单位相对地图格**已经很大**（见 §1.1）。
- **一张地图上的"变化量"是当前最值钱的低垂果实**：玩家看的是"**种类少、变化少**"，而这三条里**只有内容量与构图直接增加"看到的东西"**。

## 1. 杠杆一：尺寸（画得够不够大 / 够不够细）

### 1.1 先纠正一个前提（重要）

网上 / 直觉里常说"我们的单位太小（48×48），所以画面不行"。**这条在本项目是误读**，须先纠：
- **48×48 不是单位，是「巨型地图」的格数**（`types.ts` 的 `MAP_SIZES.huge = {width:48,height:48}`）。"33% 边长 / 11% 面积"是**巨型地图 48 对 HOMM3 XL 图 144**（`homm3-map-design-lessons.md §3.1`），**不是单位**。
  > ⚠️ `bitmap-asset-options.md §3.2` 第 1 条**原**把 48×48 标成"'巨型'**单位**"、并把 33%/11% 挂到"HOMM3 **中图** 72"上 —— **标错了**（48/72 = 66.7%，不是 33%）。**已报** `art-director-3`（该档单一写者），**其已核证并更正（该档 V1.4）** ⇒ 两档口径现已一致。
- **真实单位画布**：冒险 `u_*_map` **52×44**、战斗 `cu_*` **64×56**（`asset-spec.md §2`，D-73 加宽后）。对 **TILE = 32** 的地图格，一个"一队"单位（52 宽）**已横跨 ≈1.6 格**；HOMM3 的单位大致也只占 1 格。⇒ **单位相对格子已偏大，不是偏小。**

### 1.2 选项（互斥）

| # | 做法 | 玩家看到什么不同 | 代价 / 风险 | 判 |
|---|---|---|---|---|
| **S1** | **不动**：默认 `zoom=2` · `TILE=32` · 单位 52×44 / 64×56 | 现状 | 0 | 基线 |
| **S2** | **提默认 zoom**（`camera.ts` 默认 2 → 2.5，`STEPS` 加一档） | 一屏从 **≈12×4 格**变为 **≈9.6×3.2 格**（真机口径 792×240 CSS，`zoom` 2→2.5）：**单位和物件在手机上更大**、表情/描边更清楚；**代价 = 一屏看得更少**（战略视野↓，与"看清全图"的玩法诉求相抵） | **极低**（1–2 行 + 落 `STEPS`）；风险 = 视野变小 | ✅ **可做**（小、可回退） |
| **S3** | **单位内部细节**（不是放大画布，是**在现有画布内画清楚**）：红眼/表情（§1.3 已列"现状 1px 黑点、必须重做"）、高光/阴影分层 | 单位从"一团有轮廓的色块"变成"**看得出在看哪、有表情**" | **中**：只重画**内容**、不动画布/锚点（避免 §8.5 的锚点连锁）；但 20 兵种 × 帧是真工作量 | ✅ 值，但**属"美术返工"而非"杠杆"** |
| **S4** | **放大单位画布**（52×44 → 64×56 等）+ 改锚点 | 单位更清楚；**但**在地图上一格 32px 里塞更大的单位 ⇒ **更挤、更重叠、更花** | **高**：20 兵种全量重画 + 锚点/命中/战斗 scale 连锁（§8.5 明令不手工改锚点） | ❌ **不建议** |
| **S5** | **提 TILE**（32 → 40 / 48） | 一切变大，但**图集 / 烘焙面 / 命中 / 相机 / UI 全部连锁重定基** | **极高**（架构级） | ❌ **不建议** |

> **为什么把 S3 和 S4 分开**：S3 是"**在同样大的格子里画得更清楚**"（纯内容，零连锁），S4 是"**把格子本身放大**"（纯连锁）。两者常被混为一谈，代价差一个数量级。

## 2. 杠杆二：内容量（同样的东西有没有变化）

| # | 做法 | 玩家看到什么不同 | 代价 | 判 |
|---|---|---|---|---|
| **C1** | **砖变体 3 → 6**（= `cartoon-style.md §3.1.2` 的 **X3**） | 大片同地形里**读不出规律**（V2.11 已证"3 个印章不够"）。这是"壁纸感"的**直接**解药 | **低**：图集多 3 变体/地形 + 一行取模；**但须先落一个可复算指标**（自相关 / 同变体率） | ✅ **先做** |
| **C2** | **布景 / 装饰加量**（A 组已落地） | 地面多些小涂鸦 —— 但**实测最坏一屏仅 3 个、覆盖 <1.5%**（`shots/measurements-setdressing-density.md`）⇒ **感知弱**、**该层设计目标就是"几乎察觉不到"** | 低（已在） | ⏸️ **已到顶，不必再加** |
| **C3** | **单位帧数**（现每兵 3 帧：地图 / 待机 / 攻击）→ 加 idle / 多帧 | 单位"**活**"起来（会呼吸、会晃） | **高**：每帧重画；图集容量涨 | ⚠️ 后期再说 |
| **C4** | **地图物件种类 / 数量** | 地图"内容更多"（更多资源堆 / 地标 / 中立建筑） | **设计线**（不属本文；见 `races.md` / `maps.md`） | ➡️ 交 `design-strategist` |

> **C2 的诚实点**：布景层刚落地，但**它的设计目标就是"地面质感、不抢注意力"** ⇒ **不要指望它去解"感觉不到提升"**。用户要的是"**看得出不同**"，那是 C1 和 G1。

## 3. 杠杆三：构图（整张地图有没有可读的大结构）

| # | 做法 | 玩家看到什么不同 | 代价 | 判 |
|---|---|---|---|---|
| **G1** | **地貌区**（= `cartoon-style.md §3.1.2` 的 **X1**）：烘焙期叠**比地貌层更大尺度**的低频场（≈12–16 格团），划 3–4 个"地貌区"，每区一套砖变体 + 明暗偏移 | 从"一整张均匀草地"变成"**一眼认出这是哪片地**"：**成片林 / 成簇丘 / 裸岩**，而不是均匀噪点 | **中**（纯烘焙参数）；风险 = 分得太硬会读成"贴块分区" | ✅ **感知增益最大** |
| **G2** | **水体**（= `cartoon-style.md §3.1.2` 的 **X2**）：岸线三段过渡 + 近岸浅滩 + 深水压暗 + 水面 2 帧整数微动 | 水从"一块蓝"变成"**有岸、有深浅、会动**" | **中**：**三条里唯一引入运行期成本**（2 帧水动），须记入 §6.1.6 性能口径 | ✅ **最后做** |
| **G3** | **取景 / 相机**：暗角（`vignette` 已有、mid+ 生效）、相机默认位置 | 边缘压暗、视线聚焦中心 | **低**（已有） | ⏸️ 已够 |

> **G1 为什么最值钱**：屏幕 **90% 面积是地形**（§3.1.1）。让这 90% 从"壁纸"变成"**有地貌的地**"，是**每一位玩家、每一秒**都在看的改进。而它**恰好是程序化擅长的**（算低频场是代码的强项，不是画师的强项——又一次印证"瓶颈不在位图"）。

## 4. 组合、推荐与代价总表

### 4.1 我的推荐（互斥组合）

| 组合 | 含哪些 | 一句话 |
|---|---|---|
| **★ 推荐** | **C1（砖变体）+ G1（地貌区）** | 零新资产、零位图、感知增益最大、可分别出改前/改后；**先做最便宜、最能证伪的 C1**，再做 **G1** |
| 次选 | ★ + **S2**（提默认 zoom） | 若实测后仍觉得"小"，加 S2（1–2 行、可回退） |
| 最后 | ★ + **G2**（水体） | 唯一动运行期成本的一条，放最后 |
| 不做 | **S4 / S5**（放大画布 / 提 TILE） | 全面返工、收益不成比例 |

### 4.2 建议顺序（**先最便宜、最能证伪的**）

**C1 → G1 → S2（若需要）→ G2。**

> **为什么先 C1**：它是**唯一能单独证伪 V2.11 归因**的一条 —— 若砖变体翻倍后"壁纸感"明显降，则"3 个印章不够"成立；若**无变化**，则壁纸感来自**重复率之外**（构图 / 内容量），正是 `bitmap-asset-options.md §6.2` R1 指向的方向。**花最少的钱，先买一个"假设对不对"的答案。**

### 4.3 代价总表（人日 / 连锁面）

| 选项 | 新资产 | 返工范围 | 运行期成本 | 连锁风险 |
|---|---|---|---|---|
| C1 砖变体 3→6 | +3 变体/地形（程序化） | `atlas.ts` + `terrainLayer.ts` 一行 | **0** | 低 |
| G1 地貌区 | 0 | 烘焙参数（`terrainShade.ts`） | **0** | 中（分块过硬） |
| S2 默认 zoom | 0 | `camera.ts` 1–2 行 | **0** | 低（视野变小） |
| G2 水体 | 0 | 烘焙 + 水面 2 帧 | **有**（唯一） | 中 |
| S3 单位内容 | 0（重画） | 20 兵种帧内容 | 0 | 低（不动锚点） |
| S4 放大画布 | 0（重画） | 20 兵种 + 锚点 + 战斗 scale | 0 | **高** |
| S5 提 TILE | — | 全渲染层 | — | **极高** |
