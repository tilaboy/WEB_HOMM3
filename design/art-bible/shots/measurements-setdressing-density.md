# 布景层密度判据 —— 「会不会让地图变花」的实测（可复算）

> **作者**：林绘澄（美术 / 视觉）· 画面主线收口
> **为什么有这份文件**：主理人问「道具的**密度**是否会让地图"变花"」（用户同一轮既要"画质提升"又要"简洁"）。
> 这不是能在一张图上用肉眼回答的问题 —— 需要 **① 多张真图**、**② 不变量证明它没挤到别的东西**、**③ 用最坏局部窗口衡量"密不密"**（整图总数会被地图大小摊薄，看不出拥挤）。
> **本文件的每一个数都能用 §2 的命令重跑出来。**

---

## 0. 一句话结论

**不会变花。** 9 张真图合计算下来，布景在**最坏的一屏**里也只有 **3 个**、全图**覆盖率 0.69%–1.46%**，且**结构上被画在一切游戏物件之下、永不与任何物件同格**。
⇒ 它只能"给地面加一点质感"，**不可能"抢注意力"**。**这一层旧的问题是"太稀到看不见"，不是"太密到变花"。**

> 这条与 `measurements-visible-delta.md` §0 是同一结论的两面：那层本身就写着"氛围、连续、**几乎察觉不到**"（`cartoon-style.md` §2.3）——一个以"几乎察觉不到"为设计目标的东西，**结构上不可能**变成"变花"的来源。

---

## 1. 这次修了什么（密度是被一个 bug 压住的）

**真 bug**：`SetDressingLayer.canPlace()` 把 `CLEAR = 2`（与物件的净距）套给了**一切** `objectId`，包括真图上**每张 130–330 个障碍物**（树 / 岩石 / 山）。后果：

1. **本层几乎放不下**：9 张真图**合计只放下 9 个道具**（全是 `sd_g_map`）⇒ ≈0.2/屏 = 玩家看不到。
2. **`sd_g_helmet` 逻辑上不可能放下**：它的 `fits` 要"附近 2 格有障碍物"，而 `canPlace` 要"2 格内无任何物件"。

**修法**：`canPlace` 拆三层 —— ① footprint 同格排除（对一切物件）；② 净距**只对 `TARGET_KINDS`**（资源 / 宝箱 / 神器 / 圣泉 / 城镇 / 矿 / 地窖）；③ 障碍物 / 游荡怪**只禁同格、不设净距**。
规格侧同步记入 `cartoon-style.md` §6.1.4 **V2.11**。

## 2. 复算命令

```bash
cd homm-web
npm run build

# 密度表 + 不变量 I1–I4（9 张真图）
node tools/dressdensity.mjs

# 真图「布景 off / on」对照 + **最坏一屏**裁图（人眼只需看最挤那屏）
node tools/dressshot.mjs          # 输出到 design/art-bible/shots/h_real_*.png
```

> 两个工具都**只读**：调 `placementsOf()` / `TerrainLayer` / `SetDressingLayer`，不改任何东西。
> 真图 = `createGame()` 生成，**不是**手搭测试图 —— 手搭图物件太少，会掩盖上面那个 bug（旧 `artshot.mjs` 就是这么漏掉的）。
> ⚠️ 与 §8.2 同一条纪律：**数字绑构建** —— `npm run build` 后立刻跑，跑完核对 `dist/render/setDressing.js` mtime 未变。

## 4. 四条不变量（`dressdensity.mjs` 每次跑都断言）

| # | 判据 | 含义 |
|---|---|---|
| **I1** | 不与任何 `objectId` 同格，且布景彼此不叠格 | 不能压在任何单位 / 建筑 / 资源上 |
| **I2** | 距 `TARGET_KINDS`（资源 / 宝箱 / 神器 / 圣泉 / 城镇 / 矿 / 地窖）外沿 ≥ `CLEAR=2` | 保"一眼要找到"的交互物 |
| **I3** | 布景彼此切比雪夫 ≥ `MIN_PROP_GAP=3`；同型 ≥ `MIN_SAME_GAP=9` | 不结块、同型不重复 |
| **I4** | 不在水面格 | 布景是地面上的东西 |

`CLEAR` / `MIN_PROP_GAP` / `MIN_SAME_GAP` / `TARGET_KINDS` 在 `src/render/setDressing.ts` 里是**模块私有 const**，`dressdensity.mjs` **镜像**了一份（文件头已注"改动须同步"）。

## 5. 图：最坏一屏的「布景 off / on」

`tools/dressshot.mjs` 在 `seed=20260921 · size=medium`（32×32、218 物件、11 个布景）上，取**最挤的那 12×4 屏**裁出对照：

| 文件 | 内容 |
|---|---|
| `h_real_dress_off_crop.png` | 最挤一屏 · 布景 **off**（草稿） |
| `h_real_dress_on_crop.png` | 同一屏 · 布景 **on** |
| `h_real_dress_off.png` / `h_real_dress_on.png` | 同一张真图 · **整图** off / on |

**同屏量化**（`node tools/imagecmp.mjs <off> <on>`）：
- **整图**（2048×2048）：平均 \|ΔL\*\| **0.11**、变化像素 **0.4%** ⇒ 11 个 32–64px 小涂鸦铺在 4 Mpx 上必然被摊薄。
- **最挤一屏**（裁 12×4，1152×384）：平均 \|ΔL\*\| **0.42**、变化像素 **1.7%**。

⇒ 肉眼可见的差异是**地面层的低对比小痕迹**（如岩石旁多出的一顶头盔涂鸦、草地上一块湿痕），**读起来像纹理细节，不像物件**（A 组**无 1px 描边**，§6.1.1/§6.1.2 —— 这正是它不"变花"的结构原因）。

## 7. `b_before` 在哪（回主理人的问）

`shots/` 里与布景层配对的是 `b_dress_off.png`（**off**）/ `b_dress_on.png`（**on**）—— 即 **`b_before` = `b_dress_off.png`**（手搭 26×16 测试图）。
本轮**新补**了真图上的同变量对 **`h_real_dress_off.png` / `h_real_dress_on.png`**（+ 最坏一屏 `h_real_dress_*_crop.png`）—— **真图才是能看出密度的图**（手搭图物件少，会把密度问题藏起来）。
两组的**「off」= `setDressing='off'`**，**「on」= `setDressing='static'`**，其余变量（同构建、同光照、同视角）全同。
