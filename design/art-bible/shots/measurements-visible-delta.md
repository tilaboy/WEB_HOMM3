# 「画面提升」到底看得见多少 —— 实测差异表（可复算）

> **作者**：林绘澄（美术 / 视觉）· 任务 #84
> **为什么有这份文件**：用户第 3 次试玩说 `F-3.7`「画面也没什么提升」/ `F-3.8`「各种**贴图**各种**画质**，试玩感觉不到有什么提升」。
> 这句是**观感断言**。要回答它，先得把「我这一层加了，玩家看到多少」从"看着变了"变成**一个能复现的数**。
> **本文件只放数**。每张图都能用下面两条命令重跑出来。

---

## 0. 一句话结论

**我这一轮加的「氛围类」画面（地貌层 §3.1.1、夜光 §2.3 L1/L2、布景层 §6.1），在真机视口下的实测差异是 `L*` 均值 1 上下 —— 也就是"能测出来、但不足以读成一次画质升级"。**

同一套测量里，**差异最大的东西不是新加的层，而是 `dprCap`（分辨率）与一天中的光照相位** —— 前者被档位误判掐掉了（G-15，已修），后者不挂档位、本来就有。

⇒ **结论不是"再加一层氛围"，是"氛围这条线的天花板到了"**：`cartoon-style.md` §2.3 自己写的意图就是「氛围、连续、**几乎察觉不到**」。一个以"几乎察觉不到"为设计目标的东西，**结构上不可能**承担"画质升级"的信号。要让玩家感到提升，杠杆在**尺寸 / 内容量 / 构图**（与 `bitmap-asset-options.md` §3 §6.2 同一条结论）。

## 1. 工具与口径（都在 `homm-web/tools/`）

| 工具 | 干什么 | 为什么不能用旧的 |
|---|---|---|
| `tools/deviceshot.mjs`（新） | 真实 headless Chrome + CDP；`Emulation.setDeviceMetricsOverride` 到**真机视口 792×320 @DPR3**；可选在 `main.js` **之前**注入 `localStorage['homm.tierMode']` ⇒ 能出「只差档位」的对照 | `chromeshot.mjs` 固定 `--window-size=1280,900`，且**不能在加载前写 localStorage** ⇒ 换不了档位、也换不了设备视口；`artshot.mjs` 是 node 垫片 |
| `tools/imagecmp.mjs`（新） | 自带 PNG 解码（零依赖）：平均 RGB / 平均 L\* / 全图 sd；两图之间 平均\|ΔRGB\|、**变化像素占比**（任一通道 \|Δ\|>8）、平均\|ΔL\*\|、p95\|ΔL\*\|。`CMP_CROP=t,b` 只比某个行区间 | 之前没有任何工具能把"看着不一样"变成数 |

**为什么量两个量**：
- **平均 \|ΔL\*\|** = 「整块画面挪了多少」——对应"扫一眼觉得整体变了没"。
- **p95 \|ΔL\*\|** = 「最明显的地方挪了多少」——对应"局部有没有看得出的东西"。
- 只报其一都会被误读（前者摊薄、后者夸大）。

**裁切口径**：截图是 **2376×960**（整页 @DPR3）；游戏画布占 **device y ≈ 84…804**。下表凡标「地图区」＝ `CMP_CROP=84,804`，即**排除顶栏 / 底栏 / 侧栏**（那三块两版逐像素相同，会把差异摊薄）。

## 2. 复算命令

```bash
cd homm-web
npm run build
nohup node tools/serve.mjs >/tmp/serve.log 2>&1 &      # 或另开终端 node tools/serve.mjs

U='http://127.0.0.1:5173/?devquick=0&devsize=medium&devseed=20260917&devreveal=1'

# ① 只差「地貌层」（同档 mid、同光照正午）
node tools/deviceshot.mjs /tmp/shade_off.png "$U&devlight=0.22&devshade=0" mid
node tools/deviceshot.mjs /tmp/shade_on.png  "$U&devlight=0.22"            mid
# ② 只差「档位」（同光照正午）
node tools/deviceshot.mjs /tmp/tier_low.png  "$U&devlight=0.22" low
node tools/deviceshot.mjs /tmp/tier_high.png "$U&devlight=0.22" high
# ③ 只差「光照相位」（同档 high）
node tools/deviceshot.mjs /tmp/light_dawn_high.png "$U&devlight=0.0"  high
node tools/deviceshot.mjs /tmp/light_dusk_high.png "$U&devlight=0.5"  high

# 量差异（地图区）
CMP_CROP=84,804 node tools/imagecmp.mjs /tmp/shade_off.png /tmp/shade_on.png
```

> 注：`?devlight` / `?devshade` 都是既有 `?dev*` 家族（`lightLayer.ts` / `main.ts` + `MapRenderer.setMacroShade`）。**无人传参 ⇒ 恒为生产行为**。

## 3. 实测差异表（真机视口 792×320 @DPR3）

| # | 对照组 | 变的**只有**这一个变量 | 平均 \|ΔRGB\| | 变化像素 | 平均 \|ΔL\*\| | p95 \|ΔL\*\| | 读感 |
|---|---|---|---|---|---|---|---|
| ① | `e_shade_off` → `e_shade_on` | 地貌层（§3.1.1） | 2.84 | 17.6% | **0.98** | 4.89 | 并排看得出，单人看不觉得 |
| ①′ | 同上，**整屏**（不裁） | 地貌层 | 2.15 | 13.4% | 0.75 | 4.46 | 被 UI 摊薄 |
| ② | `f_tier_low_noon` → `f_tier_high_noon` | 档位（low↔high，正午） | 6.44 | 40.0% | **2.78** | 9.15 | 明显 —— 但**主因是锐度**（见 §4） |
| ③ | 黄昏 low → 黄昏 high | 档位（黄昏） | 5.25 | 26.7% | **2.05** | 7.67 | 隔离出「high 专属氛围层」的贡献 |
| ④ | `f_tier_high_noon` → `g_light_dusk_high` | 光照相位（正午→黄昏） | **18.23** | **80.9%** | **5.24** | 9.24 | **一眼就是"另一个时刻"** |
| ⑤ | 正午 high → `g_light_dawn_high` | 光照相位（正午→清晨） | 8.01 | 72.5% | 1.89 | 3.54 | 偏冷偏灰，看得出 |

**排序**：光照相位 ④（5.24）> 档位 bundle ②（2.78）> 档位@黄昏 ③（2.05）> **地貌层 ①（0.98）**。
⇒ **我新加的那层，是这张表里最小的一个。**

## 4. 两个顺带实测出来的硬事实

**（1）档位表在真机视口下逐项对得上 —— `dprCap` 是真的在生效**

同一 URL、同一视角，只换 `homm.tierMode`，画布 backing 尺寸：

| 档 | `dprCap`（`quality.ts`） | 实测画布 backing | CSS 画布 |
|---|---|---|---|
| low | 1.5 | **1188×360**（= 792×1.5） | 792×240 |
| mid | 2 | **1584×480**（= 792×2） | 792×240 |
| high | 3 | **2376×720**（= 792×3） | 792×240 |

⇒ 组②/③ 的差异里，**"锐度"这一项占了很大一块**：low 的 1188 宽 backing 被浏览器拉到 2376 设备像素，1px `ink0` 描边被插值抹开 ⇒ 整屏发亮发糊（low 的地图区平均 RGB **99.0/122.7/105.7**，high 是 **95.5/117.5/101.5**）。
**所以我不能把"组②差 2.78"全记成"氛围层的功劳"** —— 它是一捆（锐度 + 暗角 + 水光 + 城镇辉光 + 布景），而锐度很可能占大头。

**（2）光照相位是全屏最可见的一项，而且它不挂档位**

正午→黄昏：平均 \|ΔRGB\| **18.23**、**80.9%** 的像素变了 >8 —— 地图区平均 RGB 由 `95.5/117.5/101.5` 变成 `100.0/101.5/67.3`（G、B 双双掉、R 微升＝琥珀味）。
**这是玩家唯一"一定会注意到"的画面变化**，而它既不是我这一轮加的，也不受档位影响。

## 5. 诚实边界（哪些是实测、哪些是判断、哪些没测）

| 类别 | 内容 |
|---|---|
| **实测（可复算）** | §3 全表 6 行 + §4 的 dprCap 三档 backing。命令见 §2。 |
| **实测的局限** | ① 只测了**一张地图、一个视角**（`devseed=20260917`、`devsize=medium`、`devreveal=1`、相机默认缩放）——**换地图/换缩放会变**；② 数值是**像素差**，不是**主观阈值**：「0.98 够不够看」是判断不是测量；③ 组②/③ 是**多变量捆绑**（档位本来就捆着五项），本表**不能**当成"暗角 = 2.78"这种单变量结论用。 |
| **我的专业判断（非实测）** | ① 把 `L*` 均值 ≈1 读成"读不出一次画质升级"；② 把组②的主因判给锐度（依据是 low 整屏偏亮发糊的 RGB 偏移，**没有做"只降 dprCap、其它全开"的隔离实验**——那需要一个新 dev 开关，本轮没做）；③ "氛围线天花板到了"这个结论。 |
| **本轮没测** | ① 真机（PMA110）上的同一组对照 —— 本轮是 **headless Chrome**，视口/DPR 对齐了，但**不是真机**；② 主观阈值实验（找 N 个人做并排 A/B）；③ 垫片（`artshot.mjs`）与真 Chrome 的**逐像素**一致性。 |
| **⚠️ 与 `e2_*` 的关系** | 同目录另有 `e2_shade_off.png` / `e2_shade_on.png`（同变量、**另一个场景**，均值 L\* 30.7 起，明显更暗）。两组不冲突：本文件的数**只对应 `e_*`**，不要去量 `e2_*` 对不上号。 |

## 6. 这张表改变了什么（给主理人的一行）

在组①（我的新层）只有 **0.98 L\***、而组④（本来就有、不挂档位的光照）有 **5.24 L\*** 的前提下，
**"再叠加一层氛围"是收益最低的方向**；用户 `F-3.8` 说的「各种**贴图**」也已经由 `bitmap-asset-options.md` §3 论证过不是瓶颈。
⇒ 建议把"画面提升"的下一笔投在**尺寸 / 内容量 / 构图**上，并在**真机**上复测这份表（任务 #89 的阻塞解除后）。
