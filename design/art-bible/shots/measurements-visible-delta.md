# 「画面提升」到底看得见多少 —— 实测差异表（可复算）

> **作者**：林绘澄（美术 / 视觉）· 任务 #84
> **为什么有这份文件**：用户第 3 次试玩说 `F-3.7`「画面也没什么提升」/ `F-3.8`「各种**贴图**各种**画质**，试玩感觉不到有什么提升」。
> 这句是**观感断言**。要回答它，先得把「我这一层加了，玩家看到多少」从"看着变了"变成**一个能复现的数**。
> **本文件只放数**。每张图都能用下面两条命令重跑出来。

## 0. 一句话结论

**我这一轮加的「氛围类」画面（地貌层 §3.1.1、夜光 §2.3 L1/L2、布景层 §6.1），在真机视口下的实测差异是 `L*` 均值 1 上下 —— 也就是"能测出来、但不足以读成一次画质升级"。**

同一套测量里，**差异最大的东西不是新加的层，而是 `dprCap`（分辨率）与一天中的光照相位** —— 前者被档位误判掐掉了（G-15，已修），后者不挂档位、本来就有。

⇒ **结论不是"再加一层氛围"，是"氛围这条线的天花板到了"**：`cartoon-style.md` §2.3 自己写的意图就是「氛围、连续、**几乎察觉不到**」。一个以"几乎察觉不到"为设计目标的东西，**结构上不可能**承担"画质升级"的信号。要让玩家感到提升，杠杆在**尺寸 / 内容量 / 构图**（与 `bitmap-asset-options.md` §3 §6.2 同一条结论）。

## 1. 工具与口径（都在 `homm-web/tools/`）

| 工具 | 干什么 | 为什么不能用旧的 |
|---|---|---|
| `tools/deviceshot.mjs`（新） | 真实 headless Chrome + CDP；`Emulation.setDeviceMetricsOverride` 到**真机视口 792×320 @DPR3**；可选在 `main.js` **之前**注入 `localStorage['homm.tierMode']` ⇒ 能出「只差档位」的对照 | `chromeshot.mjs` 固定 `--window-size=1280,900`，且**不能在加载前写 localStorage** ⇒ 换不了档位、也换不了设备视口；`artshot.mjs` 是 node 垫片 |
| `tools/imagecmp.mjs`（新） | 自带 PNG 解码（零依赖）：平均 RGB / 平均 L\* / 全图 sd；两图之间 平均\|ΔRGB\|、**变化像素占比**（任一通道 \|Δ\|>8）、平均\|ΔL\*\|、p95\|ΔL\*\|。`CMP_CROP=t,b` 只比某个行区间 | 之前没有任何工具能把"看着不一样"变成数 |

**为什么量两个量**：
- **平均 \|ΔL\*\|** = 「整块画面挪了多少」——对应"扫一眼觉得整体变了没"。
- **p95 \|ΔL\*\|** = 「最明显的地方挪了多少」——对应"局部有没有看得出的东西"。
- 只报其一都会被误读（前者摊薄、后者夸大）。

**裁切口径**：截图是 **2376×960**（整页 @DPR3）；游戏画布占 **device y ≈ 84…804**。下表凡标「地图区」＝ `CMP_CROP=84,804`，即**排除顶栏 / 底栏 / 侧栏**（那三块两版逐像素相同，会把差异摊薄）。

## 2. 复算命令

```bash
cd homm-web
npm run build
nohup node tools/serve.mjs >/tmp/serve.log 2>&1 &      # 或另开终端 node tools/serve.mjs

U='http://127.0.0.1:5173/?devquick=0&devsize=medium&devseed=20260917&devreveal=1'

# ① 只差「地貌层」（同档 mid、同光照正午）
node tools/deviceshot.mjs /tmp/shade_off.png "$U&devlight=0.22&devshade=0" mid
node tools/deviceshot.mjs /tmp/shade_on.png  "$U&devlight=0.22"            mid
# ② 只差「档位」（同光照正午）
node tools/deviceshot.mjs /tmp/tier_low.png  "$U&devlight=0.22" low
node tools/deviceshot.mjs /tmp/tier_high.png "$U&devlight=0.22" high
# ③ 只差「光照相位」（同档 high）
node tools/deviceshot.mjs /tmp/light_dawn_high.png "$U&devlight=0.0"  high
node tools/deviceshot.mjs /tmp/light_dusk_high.png "$U&devlight=0.5"  high

# 量差异（地图区）
CMP_CROP=84,804 node tools/imagecmp.mjs /tmp/shade_off.png /tmp/shade_on.png
```

> 注：`?devlight` / `?devshade` 都是既有 `?dev*` 家族（`lightLayer.ts` / `main.ts` + `MapRenderer.setMacroShade`）。**无人传参 ⇒ 恒为生产行为**。

|---|---|---|---|---|---|---|---|
| ① | `e_shade_off` → `e_shade_on` | 地貌层（§3.1.1） | 2.84 | 17.6% | **0.98** | 4.89 | 并排看得出，单人看不觉得 |

## 4. 两个顺带实测出来的硬事实

**（1）档位表在真机视口下逐项对得上 —— `dprCap` 是真的在生效**

同一 URL、同一视角，只换 `homm.tierMode`，画布 backing 尺寸：

| 档 | `dprCap`（`quality.ts`） | 实测画布 backing | CSS 画布 |
|---|---|---|---|
| low | 1.5 | **1188×360**（= 792×1.5） | 792×240 |
| mid | 2 | **1584×480**（= 792×2） | 792×240 |
| high | 3 | **2376×720**（= 792×3） | 792×240 |

⇒ 组②/③ 的差异里，**"锐度"这一项占了很大一块**：low 的 1188 宽 backing 被浏览器拉到 2376 设备像素，1px `ink0` 描边被插值抹开 ⇒ 整屏发亮发糊（low 的地图区平均 RGB **99.0/122.7/105.7**，high 是 **95.5/117.5/101.5**）。
**所以我不能把"组②差 2.78"全记成"氛围层的功劳"** —— 它是一捆（锐度 + 暗角 + 水光 + 城镇辉光 + 布景），而锐度很可能占大头。

**（2）光照相位是全屏最可见的一项，而且它不挂档位**

正午→黄昏：平均 \|ΔRGB\| **18.23**、**80.9%** 的像素变了 >8 —— 地图区平均 RGB 由 `95.5/117.5/101.5` 变成 `100.0/101.5/67.3`（G、B 双双掉、R 微升＝琥珀味）。
**这是玩家唯一"一定会注意到"的画面变化**，而它既不是我这一轮加的，也不受档位影响。

## 8. 后补：做完 §5「本轮没做 ②」那个隔离实验 + 一条比数字更要紧的限制（2026-09-21）

> 本节写于主理人裁定「`shots/` 归 art-director 单一 owner」之后。**不改上文任何一句**，只补两块。

### 8.1 `?devdpr` 已落地 ⇒ §5 里「本轮没做 ②」现在做完了

上文 §5 写着：**「把组②的主因判给锐度……没有做『只降 dprCap、其它全开』的隔离实验——那需要一个新 dev 开关，本轮没做」**。
那个开关已按既有 `?dev*` 惯例实装：**`quality.ts` 的 `?devdpr=<n>`** —— **只覆写 `dprCap`，其余开关按档位正常生效**（无人传 ⇒ 不做任何事）。

**同一场景、同一构建、裁到地图区（`CMP_CROP=84,804`）**：

| # | 只差什么 | 平均 \|ΔL\*\| | p95 | 变化像素 |
|---|---|---|---|---|
| ② | **只在 high 档内**把 `dprCap` 3 → 1.5（`?devdpr=1.5`） | **1.26** | 5.54 | 11.9% |
| ③ | 档位 low ↔ high（捆绑：氛围层＋dprCap） | **2.28** | 7.96 | 28.0% |
| ④ | **零假设**：同 URL、同档，抓两次 | **0.00** | 0.00 | 0.0% |

**结论（改正上文 §5 的"主因判给锐度"）**：**锐度不是"主因"，是"一半"** ——
`1.26 / 2.28 ≈ 55%` 的档位差**只靠压低渲染倍率就能造出来**，剩下约 45% 才是氛围层那几项开关。
⇒ 上文那句判断**方向对、程度过头**：正确说法是「**锐度与氛围层各占一半上下**」。（两项不严格可加，只作量级比较。）

### 8.2 ⚠️ 比上面任何数字都重要：**数字必须绑构建**

同一条 URL、同一个档位，**在两份不同的 `dist` 上**抓出来可以差到 **平均 |ΔL\*| 2.08 / 61.6% 像素变化** ——
**比本表任何一项"信号"都大**。（触发方式很普通：并行的人在两次抓图之间跑了一次 `npm run build`。）

因此：
- 本文 §3 与 §8.1 的数字**都只在"自己那一次构建"内成立**；上文 §3 未记录构建指纹 ⇒ **它的绝对值不可与 §8.1 逐位比较**（同向其结论不受影响）。
- **可复算的正确做法**：`npm run build` 后**立刻**批抓，抓完再 `stat -f "%m" dist/main.js` 核对 mtime 未变；`README.md` 已按此记录并给了全部复跑命令。
- ④ 那行证明：**同一构建内，这套测量是逐像素确定的（0.00）** ⇒ 抖动不在工具，在构建。

### 8.3 `shots/` 的 owner 与文件口径

主理人已裁定：**`shots/`（含本文件）由 `art-director` 单一 owner**；本目录内每个文件的**场景 / 档位 / 用途**已在 `README.md` 的「每个文件的场景（写死）」表里逐行钉死。

### 9.3 三个订正（都比"X1 差 9%"更重要）

**① `2.28` 这个阈值本身是跨构建残留，且它的来源被记错了。**
§8.1 的表证明 **2.28 是当时那一构建的实测杠值**（不是另设的阈值）。而 §3.1.2 记的**同构建**杠是 **2.24** ——
即门控阈值取自**另一个构建**的杠，比本构建的杠还高。按 §8.2 立的纪律（阈值必须与所守护代码同构建），
该阈值对任何后续构建都无效。当前构建同条件重测：**杠 = 2.80**（阈值比杠低 18%，已从"难过"翻成"易过"）。

**② 量纲错配：这条杠是"六层之和 + 锐度"，X1 是一层。**
档位 low↔high 捆了 lighting 模式 / vignette / warmOverlay / waterGlint / townGlow / gridLines **六项氛围开关** + dprCap。
把锐度钉死后（⑤）纯氛围杠 = 2.38，X1 = 2.07 = 其 **87%**；像素占比 33.6% vs 34.7% = **97%**。
⇒ **要求单独一层 ≥ 六层之和**，这个门控没有任何单层能过。它是坏尺子，不是 X1 的测量。

**③ "锐度占 ≈55%"在当前构建不可复现。**
§8.1 结论「锐度与氛围层各占一半上下」（1.26/2.28≈55%）。当前构建实测：纯锐度 0.78 / 杠 2.80 = **28%**，
氛围是主项（85%）。⇒「画质档的感知主要来自锐度」这个前提在当前构建上**不成立**，反而氛围才是主项。

**④ 文档里两个「地貌层」数（§8.1 的 1.41 与 §3.1.2 的 1.70）现在能分清了：是两层。**
`devshade`（macroShade）与 `devregion`（X1 地貌区层）是**不同层**。当前构建：macroShade **1.19** / X1 **2.07**。
两个文档数都既不等于当前值、也不互相对应 ⇒ 均为跨构建残留。

### 9.4 X1 自己的规格判据从未验收（比门控更根本）

`cartoon-style.md` §3.1.2 表格里 X1 的验收判据是「**① 全草图 adjMean 不降；② 地貌区边界盲测可辨 ≥70%**」，不是后来的「≥ 档位差」。

- **② 全仓没有盲测工具 ⇒ 从未量过。**（`tools/` 无 blindtest；`grep -l 盲测` 零命中。）
- **① 在唯一可量口径下方向为负**：真 Chrome DPR3、带物件全图，相邻格平均 \|ΔL\*\| **8.64 → 8.30（−3.9%）**，
  且在 1 / 2 / 4 格三个尺度上一致下降（−3.9% / −3.8% / −5.4%）⇒ X1 在**所有**空间尺度上都轻微**降低**局部对比。
  ⚠️ **口径边界**：这不是 §3.1.1 要求的「全草、无物件」口径 —— `artshot.mjs` 没有 `devregion` 开关，做不出该口径下的 X1 A/B。
  所以这条只能记为「**在可量口径下方向为负**」，**不是**「按规格口径判定失败」。

### 9.5 结论与建议（待用户书面确认后才动口径）

**定性：主因是门控口径缺陷（坏尺子），次因是参数确实偏弱且方向存疑。**

- 不支持「调参去够 2.28」：那是拿坏尺子量，且会把参数推向圣经自己标的 X1 风险「分得太硬会读成贴块分区」。
- 建议口径订正：把 X1 的验收从「≥ 档位差」**改回** §3.1.2 表格里原本写的两条（① adjMean 不降；② 边界盲测 ≥70%），
  并补 `regionblind.mjs` 把 ② 从"从未量过"变成可复算。
- 参数侧：2.07 对纯氛围杠 2.38 仍差 13%，且 adjMean 方向为负 ⇒ 若盲测也不可辨，才值得调参；
  方向应是「提高**区域间**差异」，不是「整体加对比」。
