> **为什么图标统一到 24×24**：现状 16×16 的标记 + 18×18 的资源图标，加上卡通化要加的 1px 描边（描边画在画布内侧会吃掉内容，画在外侧需要预留 1px → 实际可用内容只剩 14×14 / 16×16）。24×24 才装得下"描边 + 图形"。
>
> **为什么地图物件高度统一到 48**：现在 `tree=40 / mine=42 / vault=44 / mtn=46` 四档不齐，画新资产时每次都要重新算 `ay`。统一到 48 后**所有物件共用一条 `ay = 32 - 48 = -16`**，一劳永逸。

### 1.3 与 zoom / dpr 的关系（决定"描边看起来多粗"）

```
最终屏幕像素 = 画布像素 × zoom(2) × dpr(2~3) = 画布像素 × 4~6
```
→ 结论：**1 画布像素 = 手机上 4~6 物理像素**。所以：
- 44×56 的战斗单位在手机上实际显示为 **176×224 ~ 264×336 物理像素**——足够表达卡通表情，**不需要放大画布**。
- 描边**不要加粗**（详见 cartoon-style §1.1 的警告）。

### 3.3 文件落地（仅 AI 资产才落盘）

```
assets/sprites/<前缀>/<名称>.png
  例：assets/sprites/crestL/crestL_p1.png
      assets/sprites/castle/castle_p2_3.png
```

**格式硬约束**：
- **PNG-8（索引色），≤ 32 色**，带完整 alpha（0 或 255，**禁止半透明**——半透明像素在硬边像素风里会变成灰边）
- 无交错（no interlace）、无 `sRGB` / `gAMA` / ICC chunk（避免浏览器做色彩管理导致偏色）
- 单文件 ≤ 8 KB（128×128 的 32 色像素画通常在 2–5 KB）
- 文件名即精灵名（`crestL_p1.png` → 帧名 `crestL_p1`）

## 4. 程序化 vs AI 生成：划分结论

### 4.1 结论（**最关键的一页**）

> **卡通化不需要推翻"零外部素材"。程序化继续承担 ≈ 95% 的资产；AI 生成只引入 3 类「英雄级」资产，共 ≤ 11 张。**

### 4.2 逐条理由

| # | 理由 | 论证 |
|---|---|---|
| **R1** | **方向是反的** | AI 的价值在"补有机细节"（布褶、毛发、材质纹理）。卡通的定义是**减少信息量 + 放大特征量**。我们要丢掉的东西，正是 AI 最擅长生产的东西 |
| **R2** | **搞笑靠动，不靠静** | 卡通笑点 = `squash & stretch` + idle 浮动 + 受击位移（cartoon-style §4 H5）。AI 产出**静态位图**，做不了程序化动画。程序化资产反而是唯一能"免费动起来"的 |
| **R3** | **尺寸天花板** | 目标画布 32–72 px，AI 出图 1024²，**信息损失 16–32 倍**。它最擅长的细节在这一步被销毁，只留下色彩污染和伪像素伪影 |
| **R4** | **色板纪律** | AI 天生不守色板。P1.4 的草稿就是活证据：约 40 种浑浊中间调，缩到 44px 后读成一坨褐色（cartoon-style §3.5）。要用 AI 就必须加"钳色"后处理，而**钳色之后剩下的信息量，程序化本来就能给** |
| **R5** | **一致性成本** | 4 族 × 5 单位 = 20 个兵种若用 AI，需要保证"20 张图互相像一家人"，这在生成模型上是**最不可控**的事情。程序化只需换色板参数，一致性是**结构保证**的 |
| **R6** | **架构代价** | 引入 AI = 打破"零外部素材"（见 §4.3）。收益是 5% 的资产，成本是 100% 的架构约定 |

### 4.3 如果打破"零外部素材"，代价清单（诚实版）

| 代价 | 具体 | 缓解 |
|---|---|---|
| **① 体积** | 11 张 128×128 PNG-8 ≈ 30–60 KB（可接受）；但若铺开到 100 张就是 300–600 KB，对"JS 187KB"的项目是成倍增长 | 严格锁死在 ≤11 张 |
| **② 离线 / PWA** | `public/sw.js` 的缓存清单要加资源，否则离线打开缺图 | 见 ③ |
| **③ 请求数** | 每个 PNG 一次网络请求（首屏 11 次） | **推荐 base64 内联进 JS**：保持**同步构建**（`atlas.ts` 的 `Atlas.build()` 是同步的，异步加载要改动启动流程）+ **零请求** + **离线天然可用**。代价：体积 +33% → 11 张约 40–80 KB。✅ 值 |
| **④ 管线工具** | 需要新增 `tools/import-sprite.mjs`（抠底 / 降采样 / 钳色 / 对齐 / 描边），见 §5 | 一次性投入（约 1 天） |
| **⑤ 维护路径变长** | 程序化改 1 行代码即可调；AI 资产要"重新生成 → 重跑管线" | 锁死在 ≤11 张，可接受 |
| **⑥ 一致性风险** | AI 资产的画风可能和程序化资产"不像一家人" | §5.4 的**描边重建 + 钳色**是强制步骤，是本风险的唯一解 |

### 4.4 分项划分表

| 资产类别 | 方式 | 理由 |
|---|---|---|
| 地形 / 岸线 / 装饰 / 水 | **程序化（现状不动）** | 已达标；重写成本 >> 收益 |
| 地图物件（树石矿箱泉） | **程序化** | 形状简单，程序化完全够；数量大（20+），AI 一致性成本高 |
| 城镇 / 城堡（4 族 × 4 级） | **程序化为主**（矩形 + 母题参数化） | 需要 20×2 = 40 张**结构一致、仅换母题**的图，只有程序化能做到"结构一致"。**例外见 §6-①** |
| 兵种（地图 + 战斗，4 族 × 5） | **程序化** | 40 帧，必须共用一套 `humanoid()` / `quadruped()` 骨架 + 换色板 + 换道具 → 这是唯一能保证"同一族的兵看起来像同一族"的方法 |
| 英雄 / 怪物 | **程序化** | 同上，且要参与战斗缩放动画 |
| 图标 / 标记 / 徽记 | **程序化** | 尺寸小（24px），AI 在这一档毫无优势 |
| VFX | **程序化** | 必须逐帧可控 + 参与屏幕扰动，且是"动作" |
| **① 阵营徽记大图（4 张）** | **AI** | 128px 够大、只 4 张、作为加载图/开场/成就徽章的"门面"，AI 的构图能力在这里是真实增益 |
| **② 每族的"英雄建筑"城堡造型（≤5 张）** | **AI** | 这是玩家第一眼看到的东西（72×96，全项目最大精灵）。"城市风格差异化"的最强表达点，值得 5 张的成本 |
| **③ 2 张 example map 的地标（≤2 张）** | **AI** | 叙事地标（巨像 / 沉船 / 古树），一次性、不可复用、需要想象力，AI 最合适 |

## 5. 生成 → 落地管线（7 步，含参数）

### 5.1 全流程图

```
[0] 出图 1024×1024（洋红底 + 指定区块）
      ↓
[1] 抠底（ΔRGB < 40 → 透明）      ← 必须在降采样【之前】
      ↓
[2] 块众数降采样 8:1 → 128×128 真像素
      ↓
[3] 调色板钳制（映射到 cartoon-style §3 色板）
      ↓
[4] 裁剪 → 整数比缩放 → 画布落位 → 基线对齐
      ↓
[5] 描边重建（丢掉 AI 的边，重跑 outline）
      ↓
[6] 手工修（只修 3 处，见 §5.5）
      ↓
[7] 存 PNG-8 ≤32 色 → assets/sprites/<前缀>/<名>.png → base64 内联 → 进图集
```

### 5.2 已知陷阱与解法（**本节是文档的核心价值**）

> **陷阱：AI 的"伪像素"直接降采样会糊成一团。**

**病因**（三条同时发生）：
1. AI 画的"像素块"是**软边**的，块与块之间有 1–3px 的抗锯齿过渡带；
2. `bilinear` / `area` 平均会把过渡带**平均成新的中间色** → 输出的每个像素都变成"糊掉的平均色"，相邻块互相污染 → 全图退化为**低对比度灰浆**；
3. AI 的块尺寸**不是精确 8**，会在 7–9px 之间漂移 → 用 `nearest` 会随机采样到过渡带像素（得到错色），表现为 sprite 上出现**随机杂点**。

**解法（三步组合，缺一不可）**：

| 步骤 | 做法 | 为什么这样能解决 |
|---|---|---|
| **① 先抠底，再降采样** | 在 **1024 原图**上按色距把洋红键成透明，**不要等降采样之后再抠** | 若先降采样，洋红会和角色边缘的过渡带平均成**粉边**，且粉边无法再被抠掉（色距已经不匹配） |
| **② 用「块众数」降采样，不用 nearest / bilinear** | 按检测到的块尺寸 k（默认 **8**）切 `1024/k × 1024/k` 个方格；每格取**出现次数最多的颜色**（mode，平票时取中位亮度）作为输出像素；**透明像素参与投票但不做加权** | mode 天然完成两件事：㈠ 吃掉块内的过渡带（少数派过渡色被多数派真实色击败）；㈡ **自动色彩量化**（AI 画的伪渐变被众数压成平面色块，正是我们要的"平涂"）。nearest 会采到过渡带，bilinear 会造出新色——mode 都避开了 |
| **③ 降采样后再钳色，不钳色就先修** | 把 128×128 的每个颜色映射到 `cartoon-style §3` 色板里**最近的色**（先在 HSL 空间分桶到 5 个明度台阶，再取同台阶内色相最近者；**不要用朴素 RGB 欧氏距离**，它会把深红映射到深绿） | 这是"一家人"的保险。AI 永远会带脏色，不钳色就不像本项目 |

### 5.3 出图阶段的参数建议（把问题挡在生成侧）

| 参数 | 建议值 | 理由 |
|---|---|---|
| 分辨率 | **1024 × 1024** | 现状草稿就是这个尺寸 |
| 底色 | **纯洋红 `#FF00FF`**（现状草稿已正确使用） | 与任何自然色都远离，色距阈值好定 |
| **区块大小** | 明确要求 **"each visible pixel block = 8 × 8 output pixels"** | 让 §5.2 的 k 可预期。**这是最有效的一条 prompt 约束** |
| 抗锯齿 | 明确要求 **"hard edges, no anti-aliasing, no gradients, no dithering"** | 直接减少过渡带，从源头降低"糊"的风险 |
| 色数 | 明确要求 **"limited palette, at most 8–12 flat colors"** | AI 会倾向画 40 色，限死它 |
| 构图 | 单角色居中、**四周留 ≥64px 空白**、**无投影 / 无地面 / 无文字水印** | 草稿右下角有"AI生成 WORKBUDDY"水印，**必须在 prompt 里禁止**，否则要手工擦 |
| 参考色 | prompt 里给 **3 个 hex**（该族 `accent` / `wall` / `clash`） | 让 AI 提前靠拢色板，减少钳色的暴力程度 |

**Prompt 模板**（可直接粘贴）：

```
pixel art sprite, <主体描述>, <视角: 3/4 top-down view>, 
flat cel-shaded colors with bold 1px warm-dark outline, 
cartoon proportions: oversized head (1:3 head-to-body), expressive eyes,
limited palette of at most 10 flat colors: <#hex1>, <#hex2>, <#hex3>,
each visible pixel block = 8x8 output pixels, hard edges, 
NO anti-aliasing, NO gradients, NO dithering, NO texture noise,
solid magenta background #FF00FF, character centered, 
at least 64px empty margin on all sides, 
no shadow, no ground, no text, no watermark, no logo
```

### 5.4 步骤 [4]【5】的具体规则

| 步骤 | 规则 |
|---|---|
| **[4] 裁剪** | 按 alpha 非零的 bbox 裁掉四周空白 |
| **[4] 缩放** | **只用整数比**（1/2、1/3、1/4），且目标 ≤ 画布尺寸。**禁止非整数比**（会破坏像素栅格，出现行列宽窄不均） |
| **[4] 落位** | 放入目标画布（如 72×96），**水平居中，底部基线严格对齐画布底边**。所有精灵共用同一条基线（见 `atlas.ts:702` 的 `ay = TILE - h` 设计） |
| **[5] 描边重建** | ⚠️ **丢掉 AI 自带的描边**（粗细不均、发灰、有抗锯齿残留）。用 `PixBuf.outline(ink0, 1.0)` 重跑一遍；≥65px 的图跑 2 次或加 `width=2` 参数。**这是让 AI 资产和程序化资产"像一家人"的唯一决定性步骤** |

### 5.5 步骤 [6]：**哪些必须手工修**

只修这三类（预计每个精灵 **5–15 分钟**）：

| # | 修什么 | 判据 |
|---|---|---|
| 1 | **眼睛 / 表情** | 见 cartoon-style §4 H3。AI 的眼睛基本不可用（1px 或糊成灰点），**必须重画成 ≥2px + 嘴线** |
| 2 | **剪影毛边** | 抠底 / 降采样常在轮廓上留 1–2 px 的"AI 糊出来的毛刺"。用画笔吃掉，保证轮廓是一条干净的 1px 线 |
| 3 | **遮挡与穿模** | 弓弦穿手、长矛穿身体、旗杆穿屋顶 —— AI 不理解的物理关系 |

**不要手工修**：色板（靠 §5.2③ 自动钳）、描边（靠 §5.4 自动重跑）、比例（要改比例就重新生成，别手改）。

### 5.6 落地方式（二选一，推荐 B）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. `fetch` + PNG 文件** | 存 `dist/assets/sprites/*.png`，启动时 `await` 加载 → `drawImage` 入图集 | 源码干净、体积小 | ⚠️ `Atlas.build()` 是**同步**的（`atlas.ts:750`），改成异步会牵动 `main.ts` 启动流程；`public/sw.js` 缓存清单要加；首屏 11 次请求 |
| **B. base64 内联（推荐）** | `tools/import-sprite.mjs` 输出 `src/render/generated/sprites.ts`（`export const SPRITES: Record<string,string> = { crestL_p1: 'data:image/png;base64,...' }`），`atlas.ts` 启动时 `new Image()` + `drawImage` 同步可用 | ✅ 保持**同步构建**、**零网络请求**、**PWA 离线天然可用**、TypeScript 类型安全 | 体积 +33%（11 张约 40–80 KB） |

## 6. AI 生成资产清单（≤ 11 张，全部 1024² 出图）

| 编号 | 资产 | 输出画布 | 数量 | 出图 prompt 要点 |
|---|---|---|---|---|
| **AI-1** | 阵营徽记大图 `crestL_<faction>` | 128 × 128 | **4** | 族母题居中（尖顶 / 兽刺 / 有机 / 菱形晶体）+ 族色板 3 色；**不要**文字 |
| **AI-2** | 每族"英雄建筑"城堡 `castle_<faction>_hero` | 72 × 96 | **5**（含中立） | 2×2 城堡，**平视略俯**（与现状 `castle()` 视角一致，3/4 top-down）；必须读得出 carton-style §5 的族母题；左右各外扩 4px、上边多 32px（配合 `ax=-4, ay=-32`） |
| **AI-3** | example map 地标 `misc_landmark_*` | 96 × 128 | **2** | 叙事地标（巨像 / 沉船 / 古树），一次性，地图上占 3×3–4×4 格 |

**为什么是这 3 类而不是别的**：
1. 它们是**尺寸最大的 3 类**（≥72px），AI 的细节损失最小；
2. 它们是**数量最少的 3 类**（合计 ≤11），一致性风险可控；
3. 它们是**玩家第一眼看到的门面**（加载图 / 开场 / 主城），画质收益最高；
4. 它们**不参与程序化动画**（不需要 squash & stretch），不需要逐帧控制。
