## 0. 一句话方向

**「玩具箱里的骑士进行曲」——用音乐盒/钢片琴 + 木头打击 + Karplus–Strong 拨弦，一本正经地演奏庄严的三拍子进行曲；每首曲子只在**一处**绊一下，然后立刻装作什么都没发生。**

## 1. 现状盘点（先确认事实，不凭假设）

### 1.1 `src/ui/sfx.ts` 到底是什么

| 项 | 实测结论 |
|---|---|
| 实现方式 | **纯 WebAudio 程序化合成，零素材文件**。振荡器（`tone()`）+ 滤波白噪声（`noise()`）现场合成 |
| 音色数 | **10 种**：click / step / pickup / hit / shoot / spell / build / day / win / lose / error |
| 音频图 | `osc|noise → filter → gain → master → destination`，**只有一层 master**，无子总线、无压缩器 |
| 主音量 | `MASTER_VOL = 0.18` |
| 上下文管理 | **懒创建**：第一次发声一定发生在某次点击里，天然满足自动播放策略；`unlocked` 只推一次 `resume()` |
| 静音 | `localStorage['homm.mute']`，**只拧 master gain 不销毁上下文** |
| 后台 | `suspendAudio()` / `resumeAudio()` 已导出，由 `lifecycle.ts` 显式驱动（**不靠发声时自动 resume**，注释说明部分设备会爆音） |
| CPU | 每次发声新建 `OscillatorNode` / `BufferSource` + `Gain`（+ 噪声要 `Math.random()` 逐样本填 buffer） |

**结论**：现有实现是**正确的、克制的最小可行方案**，没有要推翻的地方。缺的只是「音乐 / 环境音 / 总线」三层。

### 1.2 工程约束（决定技术路线的硬事实）

| 事实 | 出处 | 对音频的含义 |
|---|---|---|
| **零打包器**：`tsc` + `node tools/postbuild.mjs` | `package.json` | ❌ **不能 `import music from './music.mp3'`**。音频文件只能放 `public/audio/`，运行时按 URL `fetch`，由 postbuild 拷进 `dist/` |
| `public/` 整体拷进 `dist/` | `postbuild.mjs` | ✅ 放 `public/audio/` 即可自动进包 |
| `sw.js` 只缓存 install 期的 4 个 ASSETS，**fetch 分支从不 `cache.put`** | `public/sw.js:14-19` | ⚠️ **运行时 fetch 的音频永远不进缓存** → 若走文件路线，"离线可玩"会破功（见 §6.4） |
| 移动端：Android 16 / WebView 151 / DPR 3 / **90Hz** / 横屏锁定 | roadmap G-12 | 帧预算 11.1ms；音频绝对不能挤渲染线程 |
| 地形只有 7 种：grass/dirt/sand/snow/swamp/rock/water，**无地下** | `terrains.ts` | 环境音只需 4–5 层，❌ 不需要「地下/洞穴」床 |
| 美术风格 = **「玩具箱战争」** | art-bible §0 | 音乐调性天然应该"玩具化"（见 §2） |
| 喜剧原则 = **「我看见了，但这个世界假装没看见」**；每屏最多 1 处高度荒诞 | art-bible §6.1.1 | 音乐的搞笑必须**同一手法**：直着走，只在一点上歪（见 §2.3） |
| APK 4.8 MB / `dist` 1.4 MB（含 604 KB sourcemap） | roadmap G-11 | 体积增量预算见 §6.3 |

## 2. 音乐基调：三个方向 + 一个推荐

### 2.1 方向 A（**推荐**）· 玩具箱进行曲 — Music-box Processional

**音色**：音乐盒/钢片琴（正弦 + 极快衰减 + 少量二次谐波）为旋律，Karplus–Strong 拨弦（鲁特琴/竖琴）为和声，木块/响板/小鼓为节奏，极简 feedback-delay 混响做"石厅"感。
**体裁**：庄严的 **3/4 或 6/8 进行曲**，Dorian / Aeolian 调式，附点节奏，号角式纯四度/纯五度动机。

**与前稿 `69a4353` 的关系（重要，避免读成两个方案）**：
前稿推荐「方向 B · 庄重仪式 + 死面孔的荒诞装饰音」，它规定的是**音乐结构**——一段真正庄重的
仪式主题，每隔约 40s 被一个极其克制、世界拒不回应的荒诞小动机刺穿，然后继续庄严前行。
**本文档完全采纳这条结构。** 方向 A 不是它的替代，而是**它的音色落地**：
> **结构取前稿 B（庄重仪式 + 死面孔荒诞动机）＋ 音色取本稿 A（玩具箱音乐盒）＝ 最终推荐。**

即：*用什么乐器*（音乐盒/拨弦/木块）由本稿定，*怎么编排笑点*（40s 一处、死面孔、不接话）由前稿定。
这样合并后，"每 40s 一处"比本稿 §2.4 的"每曲一处"更可执行，见 §2.5 的合并版配额表。

**为什么这个音色是本作的正解（三条，都很硬）**：

1. **与美术同源。** 美术是「玩具箱战争」，音乐盒就是**玩具的乐器**。同一件乐器既给"骑士"的庄重（进行曲体裁、调式、附点），又给"玩具"的荒诞（发音体）——**庄重与荒诞不需要两首曲子打架，一个音色同时给了两样**。这是别的方向做不到的。
2. **它是极少数"廉价音色本身就是风格"的选择。** 音乐盒在 WebAudio 里几乎是**最容易合成好**的音色（正弦/三角 + 20–40ms 指数衰减 = 音乐盒），不需要为"像不像真乐器"交学费（见 §6.2 的音色成本表）。省下的预算全给编曲。
3. **笑点机制天然对。** 玩具箱演奏的庄严进行曲，本身就是"这个世界假装没看见"的听觉版——它一点没在开玩笑，是**乐器**在开玩笑。

### 2.2 方向 B · 吟游诗人鲁特琴 — Bard's Lute（伪中世纪）

Karplus–Strong 拨弦为主，竖笛（三角波 + 气声噪声 + 颤音），框鼓。更暖、更真诚、更"真实的中世纪"。
⚠️ **不选的理由**：① 竖笛/气声在 WebAudio 里极易做出"廉价 synth"味，风险高；② 它**只有庄重没有反差**——幽默得完全交给美术，音乐反而成了旁观者；③ 竖笛的持续音会长期占用 800–1500Hz，正好压在 sfx 主频段（见 §5.3）。

### 2.3 方向 C · 8-bit 骑士 — Chiptune（NES 方波）

方波/三角波/噪声，快速琶音。合成成本最低、可读性最好。
⚠️ **不选的理由**：① 读成"复古游戏"而不是"骑士"，**庄严感被稀释**；② 8-bit 的"反差梗"是**被用烂的笑话**，与本作要的**冷面**（deadpan）相冲——8-bit 是在冲你挤眼，本作需要的是不挤眼。
✅ **保留价值**：若实现时间被压到极紧，C 是**最快出声**的退路（音色全是最基础的波形）。

### 2.4 反差幽默在音乐上如何成立（关键设计纪律）

直接移植美术 §1.3「单一打破点」与 §6.1.1「世界假装没看见」：

| 纪律 | 规定 |
|---|---|
| **失调的配额（合并前稿口径）** | **循环曲：每 ~40 s 只允许一处**"绊一下"；**短 sting：整段只允许一处**。形态是一个落在拍外的休止、一个低半音的错误音、或一记忽然出现的鸡啄木声。**然后立刻恢复严肃，绝不解释、绝不重复第二次**（前稿原话：音乐对荒诞动机"既不惊讶也不接话"） |
| **笑点落在"奏的是什么"，不落在"奏得多滑稽"** | 配器/音域/混响与主体完全同一套；不许为搞笑单开"滑稽音色"（= 美术说的"两个游戏拼接"） |
| **不许用音乐讲笑话** | 禁止拟声恶搞（滑音哨、弹簧声、boing）。那些是闹剧，本作是冷面 |
| **幽默配额** | `menu` 每 40s 一处／`map` 每 40s 一处（藏在打击里）／`town` 每 25s 一处（鸡，见下）／`battle` **0 处**（战斗要玩家紧张，前稿的"战斗啾鸣"建议**不采纳**）／`victory` 整段 1 处（见下）／`defeat` **0 处** |

**具体三例**（可直接交给实现）：
- **城镇**：木块节奏里，每 ~25s 有一次用带通噪声做的**极轻"笃"**（鸡啄），音量比节拍低 12dB。玩家第三遍才注意到——**这正是要的效果**。
- **胜利 sting**：号角动机庄重上行到第 5 个音，**第 6 个音低半音**，然后照常收。听感是"号手吹破了一个音，队伍照常前进"。
- **地图**：鹅群（美术 `sd_a_goose`）走过时，环境层给一次**两声错开的**低音拨弦，像队列里有人踩错了步。

| 3 | `battle` | 战斗 | **60–75s** | 无缝 loop + 允许被随时截断 | ⚠️ **不随战斗 1×/2×/3× 变速**（见 §3.1） |
| 3b | `siege` | 攻城战 | 复用 #3 数据 | 同 #3 | Phase 2：加鼓 + 低八度即可 |

**合计 6 首正曲 + 2 个换配器变体。**

### 3.1 三条硬性循环/播放纪律

1. **无缝**：循环点必须落在小节线上，且**不允许任何音符跨循环点延音**（延音尾巴会在接缝处被切断 → 听出来）。实现上把 `dur` 钳到"距循环点的剩余拍数"。
2. **战斗曲不跟速度档位变速。** 战斗有 1×/2×/3× 档（`DESIGN.md` §22.3），但音乐若跟着加速会立刻变得滑稽且廉价。**音乐恒定速度**，速度档只影响动画与 AI。
3. **切场景用交叉淡入淡出 600–900ms**，不要硬切；`menu → map` 时可让 menu 的最后一个和弦自然收尾（800ms）再进 map。

## 4. 环境音层（Ambient）

### 4.1 分层原则：**床 = 循环 buffer；事件 = 稀疏 one-shot**

这是环境音唯一划算的做法，也直接决定 CPU：

| 层 | 内容 | 实现 | CPU |
|---|---|---|---|
| **床（bed）** | 持续底噪 | **一次性生成 2–3s 噪声/滤波 buffer，`loop = true` 常驻** | ≈ 0（一个 BufferSource 循环） |
| **事件（event）** | 鸟鸣 / 鸡 / 鹅 / 水泡 | 稀疏 `setTimeout` 调度，间隔 ≥ 8s（鸡 ≥ 25s） | 每次 1–2 个节点 |

### 4.2 环境床清单（只做 5 层，因为地形只有 7 种且无地下）

| ID | 触发地形/条件 | 频谱占位 | 内容 |
|---|---|---|---|
| `amb_wind` | rock / snow / 开阔 | **< 350 Hz** | 低通噪声 + 0.07 Hz LFO 缓慢起伏 |
| `amb_leaf` | grass（有树装饰的格） | **> 3 kHz** | 带通噪声 + 随机幅度抖动（树叶摩擦） |
| `amb_water` | 视野内水域占比 > 阈值 | **< 400 Hz** | 低通噪声 + 2.5s 周期的拍岸涌落 |
| `amb_swamp` | swamp | **< 300 Hz** + 偶发事件 | 低频嗡鸣 + 稀疏"咕嘟"（正弦快速降调） |
| `amb_town` | 城镇在视野内 / 城镇对话框 | 中频（**唯一允许进入 sfx 频段的**） | 远处人声嗡鸣（多层带通噪声）+ 稀疏鸡/鹅事件（§2.4） |

❌ **不做地下/洞穴**：`terrains.ts` 无地下地形，不做。
❌ **不做脚步之外的"行走"环境**：已有 `sfx.step()`，不重复。

### 4.3 驱动规则（避免"打架"的第一道闸）

- **同一时刻最多 1 个床 + 1 个事件层**。不做多床叠加混音（既难听又费 CPU）。
- **床的选择**：取摄像机中心（或英雄）周围可见格中**占比最高的地形** → 对应床。
- **切换**：1.5–2.0s 交叉淡入淡出；**60s 内不因地形抖动反复切换**（加滞回：新地形占比需 > 旧地形 +15% 才切）。
- **音量固定 0.3，永不参与闪避**（见 §5.2）。

## 5. 混音总线与"不打架"规则

### 5.1 目标总线结构（**在现有 master 之下拆三条子总线**）

```
destination
 └── master (gain 0.18, 静音开关在此, 保持不动)
      └── [新增] DynamicsCompressor   ← 防叠加削波（见 §5.5）
           ├── busUI      (1.00)  ← sfx.ts 的 10 个音，全部改接这里
           ├── busMusic   (0.50)  ← 音乐
           └── busAmbient (0.30)  ← 环境床 + 事件
                └── [send] convolver (程序化 IR，1 次生成，共享)  — 仅城镇/战斗用
```

**`MASTER_VOL` 保持 0.18 不变**（用户已习惯这个响度）。音乐进来后总能量上升由压缩器兜住，不手动调 master。

### 5.2 闪避（ducking）：只对**低密度**事件做

| 事件 | 是否闪避 | 参数 |
|---|---|---|
| `win` / `lose` / `build` | ✅ 闪避 | music → 0.6×（≈ −4.4 dB），200ms 下、500ms 回 |
| `spell` / `hit` / `shoot` | ❌ 不闪避 | 战斗中频率高，闪避会造成**可听见的"抽水"** |
| `click` / `step` / `pickup` / `day` | ❌ 不闪避 | 同上，且 `step` 是每格一次，闪避必崩 |

理由：闪避的价值在于"让位给重要信息"。`step` 每 0.3s 一次，对它闪避等于**每 0.3s 抽一次音乐**，是灾难。

### 5.3 频率分离（"不打架"的第二道闸，也是最有效的）

实测现有 sfx 的能量分布：`click 660` / `shoot 2400` / `spell 880→1320, 1108→1660` / `hit 130+900` / `pickup 523,784` / `build 300+392` / `day 440,554` / `win 523,659,784` / `lose 392,311,233` / `error 170`。

→ **sfx 主战场 ≈ 500–2400 Hz，峰值在 660 与 2400。**

**规定**：
- **音乐**：旋律基频压在 **200–1200 Hz**；**禁止**在 2.2–2.6 kHz 放持续音（会盖 `shoot` 的 2400Hz 扫频）。音乐盒的二次谐波会自然落在 2k+，用**低通 3.2 kHz** 削掉顶端即可。
- **环境床**：一律 **< 400 Hz 或 > 3 kHz**（已在 §4.2 表内定死），**挖空 sfx 频段**。
- **唯一例外**：`amb_town` 的鸡/鹅事件允许进中频——因为它是喜剧点，且用 **≥25s 间隔 + 低于床 12dB** 双重限制，不构成遮蔽。

### 5.4 与现有 `sfx.win()` / `sfx.lose()` 的关系（**待拍板 Q4**）

现有 `win`/`lose` 是三音琶音式的即时反馈，已接在 `BattleScreen.ts:857-858`。

- **方案 i（推荐）**：**保留 `sfx.win/lose` 作为"结果已定"的即时反馈，音乐 sting 在其后 600ms 叠加**。两者音区错开（sfx 在 523–784，sting 走低八度 + 号角），不会撞。
- **方案 ii**：用 sting 完全替代，删掉 `sfx.win/lose`。更干净，但会丢失"点下去立刻有反应"的手感。

### 5.5 其它混音规定

- **高通 90 Hz**（音乐 + 床）：手机扬声器放不出 90 Hz 以下，留着只会吃动态余量并让喇叭发闷/破响。
- **单声道化**：环境床与音乐的和声层做成**窄立体声（宽度 ≤ 30%）**；手机扬声器是单声道，宽立体声在单声道下会相位抵消、变薄。
- **压缩器**：`threshold −12 dB, ratio 4, knee 6, attack 0.004, release 0.18`。防"音乐 + 床 + 4 个 sfx 同时响"时削波。**这是 0.18 master 能继续用的前提。**

## 6. 技术路线：程序化 vs 音频文件（**核心论证**）

### 6.1 结论（先给答案）

> **继续程序化（WebAudio 合成），但把音乐做成"数据驱动"——音符是数据、播放器是引擎——并在接口层预留音频文件通道。**

四条理由，按权重排序：

1. **本项目没有音乐来源。** 全部美术 100% 程序化生成（`asset-spec.md` §4.1，≈95% 程序化），没有作曲者、没有素材库预算、没有授权流程。选文件路线 = 先要解决"曲子从哪来"（采购/CC0/AI 生成），**那是一个比写合成器大得多、且不可控的问题**。
2. **与"零素材"的工程身份一致。** README/DESIGN 的核心卖点就是"图片/字体/音频资源 = **0**"。引入 2.5 MB 音频会把 APK 从 4.8 MB 推到 ~7.3 MB（+52%），直接削弱这个身份。
3. **程序化在本作不是妥协，是加分。** 见 §2.1 —— 我们要的恰恰是"音乐盒"这种**廉价音色=风格**的声音。程序化的天花板在这里**不构成限制**。
4. **预留文件接口的成本几乎为零。** 只要播放器接口是 `play(id)` / `stop()` / `setBus()`，将来换成 `decodeAudioData` 或 `<audio>` 播放，调用点一行都不用改。

### 6.2 诚实的局限评估：**"能做出像样的旋律吗？"**

**分两半回答，这是全篇最重要的一句**：

> **旋律、和声、节奏 = 数据问题 → 程序化完全能做，且能做得很好。**
> **音色 = 物理问题 → 有硬天花板。**

音色成本表（我们的可行性）：

| 音色 | 合成难度 | 可行性 | 说明 |
|---|---|---|---|
| **音乐盒 / 钢片琴** | 低 | ✅ **很好** | 正弦/三角 + 20–40ms 指数衰减 + 少量二次谐波。**最容易合成好的音色** |
| **拨弦（鲁特琴/竖琴）** | 中低 | ✅ **好** | **Karplus–Strong**：噪声脉冲 → 延迟线 + 低通反馈。最像"中世纪"的廉价方案，强烈推荐 |
| **木块 / 响板 / 小鼓** | 低 | ✅ 很好 | 带通/高通噪声 + 极短包络 |
| **竖笛 / 木管** | 中 | ◐ 勉强 | 三角波 + 气声噪声 + 颤音。**远听可接受，近听塑料** → 只用短音，不做长持续音 |
| **铜管 / 号角** | 中高 | ◐ 凑合 | 锯齿 + 滤波包络 + 多层失谐。sting 里的短动机可以，铺底不行 |
| **弦乐群（弦乐 pad）** | **高** | ❌ **别做** | 多层失谐锯齿 + 慢起音 + chorus，做出来像 80 年代廉价合成器，比不做更掉价 |
| **人声 / 合唱** | — | ❌ **不可能** | — |
| **管风琴** | 中 | ◐ 可一试 | 多正弦 drawbar 叠加；城镇教堂场景可 |

**所以**：
- ✅ **能做**：一首结构完整、有主题动机、有编曲层次、能无缝循环的音乐盒进行曲。**它会好听。**
- ❌ **不能做**：HOMM3 那种"管弦乐/合唱"的史诗感。**不要朝那个方向许诺。**
- ⚠️ **必须承认的两个真实代价**：
  1. **长时间听感疲劳**：单一合成音色听 30 分钟会腻。缓解手段见 §8.4（变体段 + 换配器）。这是程序化音乐的**固有弱点**，无法根治。
  2. **动态起伏有限**：没有真实演奏的力度/呼吸变化。要靠**编曲**（加/减声部、换八度、换配器）造起伏，而不是靠音量。

### 6.3 若（且仅若）用户选择文件路线 —— 预算与格式

| 项 | 规定 | 理由 |
|---|---|---|
| **总预算** | **≤ 2.5 MB** | APK 4.8 → ~7.3 MB。再大就要重新讨论 |
| **格式** | **MP3**，单声道，**64 kbps** | MP3 在 Android WebView / iOS Safari / Chrome **全支持**。Ogg 在 iOS Safari 不可靠 → **排除**。AAC 质量略优但 MP3 更保险 → 选 MP3。**绝不 WAV**（10× 体积） |
| **时长** | 循环体 **30–60s**，靠 loop 撑全程 | 60s @64kbps mono ≈ **470 KB**；6 首 ≈ 2.8 MB → 需砍到 4–5 首或降到 45s（≈350 KB/首） |
| **加载** | ❌ **不要用 `decodeAudioData` 解长循环** | 60s 立体声 44.1k 解码后 ≈ **21 MB RAM**，低端机直接爆。长循环用 `<audio>` + `createMediaElementSource()` 接入总线（内存 ≈ 0）；**短 sting（<3s）才用 AudioBuffer** |
| **loop 缝隙** | ⚠️ 真坑 | `<audio loop>` 在部分 WebView 上有 **20–50ms 缝隙**。可接受则接受；不可接受则双 buffer 交叉淡入 |
| **离线** | ⚠️ **必须先改 `sw.js`** | 现状 fetch 分支**从不 `cache.put`**（`sw.js:14-19`），运行时拉的音频**永远不进缓存**，离线即失声。文件路线**前置任务**：给 sw.js 加 `cache.put` + 把音频列入 install 期 ASSETS |

### 6.4 文件路线的隐藏成本（必须让用户知道）

1. sw.js 改造（上表最后一行）——**不做则离线破功**。
2. 曲子从哪来（采购 / CC0 检索 / AI 生成）+ 授权合规 + 循环点剪辑。
3. 每首曲子的**无缝循环裁剪**是手工活，AI 生成的音乐尤其难对齐节拍。
4. 体积会永久性地改变项目的"零素材"身份。

**→ 这就是为什么推荐先程序化。**

## 7. 移动端约束（硬性）

| 约束 | 处理 |
|---|---|
| **后台暂停**（已有机制） | `lifecycle.ts` 调 `suspendAudio()` 挂起整个 ctx。⚠️ **最大风险**：见 R1 |
| **用户可能静音** | 沿用 `localStorage['homm.mute']`，`HUD.ts:92` 已有开关。**新增**：音乐不额外引入开关，避免两个音量概念 |
| **手机扬声器** | 高通 90 Hz；单声道化（§5.5）；**不依赖低频营造"庄严"**（庄严靠调式与节奏，不靠低音） |
| **横屏握持** | 横屏时手指常盖住扬声器 → 保持 **1–3 kHz 能量充足**（人耳最敏感区），这是"听得见"的关键。音乐盒音色天然在 1–3 kHz 有能量，✅ 方向 A 又一次占优 |
| **iOS 未验证** | 项目只验过 Android（G-12）。iOS Safari：静音拨杆会影响 WebAudio；`suspend/resume` 在 iOS 上偶有爆音（`sfx.ts` 注释已记录）。**iOS 需单独测**，见 R6 |
| **首屏不出声** | 保持现状：AudioContext 懒创建，第一次发声在手势内。音乐**不抢跑**，不新增自动播放风险 |
| **完全离线（App Store 4.2 防御）** | 程序化 = **零资产加载 = 离线天然成立**。这是程序化路线一项**常被忽略但很硬的优势**；走文件路线则必须先把离线方案做实 |
| **⚠️ SW 在原生壳内可能不生效** | 前稿指出（`mobile-platform.md §2.8`）：Service Worker 在 Capacitor 原生壳里**不一定拦截请求**。→ 两条后果：① 现状 `public/sw.js` **不能当作离线保障**（本作真正的离线保障是"零资产"）；② 若将来走文件路线，**不能依赖 SW 预缓存**，音频必须随 `cap sync` 打进 `android/app/src/main/assets/public/` |

## 8. 性能预算

### 8.1 并发语音数（硬上限）

| 类 | 上限 |
|---|---|
| 音乐 | **≤ 8**（典型 4：旋律 + 和声 + 低音 + 打击） |
| 环境床 | **≤ 2**（1 个循环 buffer + 1 个事件 voice） |
| sfx | **≤ 6**（战斗 spike：hit + shoot + spell 可同时） |
| **总计** | **≤ 16**；实现**全局 voice 计数 + 抢占最旧** |

### 8.2 调度器（**必须**用 lookahead 模式，不能用 `setTimeout` 逐音符）

```
定时器 setInterval(tick, 25ms)      // 25ms 探视
tick:
  if (ctx.state !== 'running') { nextNoteTime = ctx.currentTime + 0.06; return; }  // ← R1 的解法
  while (nextNoteTime < ctx.currentTime + 0.120) {   // 120ms 调度窗口
    scheduleNoteAt(nextNoteTime); advance();
  }
```
- 用 `setInterval` **不用 rAF**：rAF 在后台被节流/暂停，而 `setInterval` 的守卫由 `ctx.state` 兜住。
- 环境床**不需要**调度器（一个循环 BufferSource 即可）。
- 现有 `noise()` 每次 `Math.random()` 逐样本填 buffer（44.1k × 0.14s ≈ 6000 次）——**建议把环境床/常用噪声 buffer 预生成并复用**，别每次建。

### 8.3 内存

| 项 | 估算 |
|---|---|
| 环境床 buffer | 4 × 3s 单声道 @48kHz ≈ **2.3 MB**；**建议降到 2s** → 1.5 MB |
| 混响 IR（程序化生成，1 次） | 1.2s 立体声 ≈ **0.5 MB** |
| 音乐 | **0**（纯合成，无 buffer） |
| **总预算** | **≤ 3 MB 音频内存** |

### 8.4 抗疲劳（程序化音乐的固有弱点，必须设计进去）

冒险地图单局可玩 30+ 分钟 → 120s 的曲子会重复 15+ 遍。

| 手段 | 做法 |
|---|---|
| **变体段** | 曲子写成 A / B / A′ 三段，调度器随机排列（A-B-A′ / A-A′-B / B-A-A′） |
| **换配器** | 每循环 4 次换一次配器（去掉打击 / 旋律降八度 / 只留音乐盒） |
| **留白** | 每 3 个循环后插入 **8–12s 纯环境音**（音乐完全静默）。**留白比变奏更抗疲劳** |
| **音符密度上限** | 地图曲：**≤ 2 音/秒**。密度低才有"背景"感，也才不抢 sfx |

## 9. 优先级：如果只能先做一件事

### 先做 **「`menu` 主菜单曲 + 承载它的最小音乐引擎」**

一件事，两半，不可分：`src/audio/` 下的**总线拆分 + lookahead 调度器 + 一首 90–120s 无缝循环的 menu 曲**。约 **1.5–2 人日**。

**为什么是它（五条，按权重）**：

1. **性价比最高的"完成度信号"。** 开始屏是玩家对"这游戏是什么档次"的第一判断点。一首站得住的主题曲，感知价值远超同等工作量的任何音效补充。
2. **风险最低的试验场。** 一个屏幕、无场景切换、无摄像机驱动、无战斗时序约束。**最不可能搞砸玩法**。
3. **它是整条管线的验收件。** 总线 / 调度器 / voice 上限 / lifecycle 恢复守卫 / 无缝循环——这些**通用机制**全部在 menu 这一首里被验证。之后 `map` / `battle` / `town` 只是往同一个引擎里塞数据。
4. **它直接回答调性问题。** 用户最想知道"这游戏听起来是什么"，一首 menu 曲就能拍板，不必等全套做完再返工。
5. **它不依赖任何未定事项。** 环境音要等摄像机地形统计（§4.3）、战斗曲要等速度档位决策（§3.1），menu 曲什么都不等。

**为什么不是 map 曲**：地图是玩得最久的场景，看似最该先做——但它**必须连带环境音交叉淡入系统**（§4.3）才完整，工作量是 menu 的 2.5 倍，且更容易出 bug。**先做 menu 是把引擎磨快，再拿它去砍 map。**

**排期建议**：
```
P0  menu 曲 + 音乐引擎 + 总线拆分            (1.5–2 人日)
P1  battle + victory/defeat sting            (1 人日)   ← 战斗是最需要情绪的场景
P2  map(+night 变体) + amb_wind/leaf/water   (1.5–2 人日)
P3  town + amb_town（含鸡/鹅喜剧点）          (1 人日)
```

### 10.3 曲目数据格式（定稿前建议）

```ts

export const MENU = {

  bars: 32, loopFrom: 4,          // 前 4 小节 intro 只播一次

    { patch: 'musicbox', notes: [[0, 'D4', 1], [1, 'F4', 0.5], /* [拍, 音名, 时值] */] },
```

## 12. 风险登记

| ID | 风险 | 等级 | 缓解 |
|---|---|---|---|
| **R1** | **后台恢复时爆音/音符雪崩**：`suspendAudio()` 冻结 ctx，但 `setInterval` 调度器仍在跑 → 恢复瞬间会把积压的音符一次性播出来。**这是本项目特有的、由已有 lifecycle 机制诱发的坑** | 🔴 高 | §8.2 的守卫：`if (ctx.state !== 'running') { rebase; return; }`。**必须在实现清单里列为验收项** |
| **R2** | 程序化音乐**长时间听感疲劳** | 🟠 中 | §8.4 四手段（变体段/换配器/留白/密度上限）。**无法根治**，需在首次试玩后听反馈 |
| **R3** | 手机扬声器低频无效 → "庄严"变"闷" | 🟠 中 | 高通 90 Hz + 单声道化 + 庄严靠调式节奏不靠低音（§5.5） |
| **R4** | 若走文件路线：sw.js **不缓存运行时 fetch**，离线失声 | 🟠 中 | 文件路线的**前置任务**（§6.3）。程序化路线不受影响 |
| **R5** | 战斗 sfx 密集（hit/shoot/spell 并发）叠加音乐后削波 | 🟡 低 | 压缩器 + voice 上限 16 + 高密度事件不闪避（§5.2/§5.5/§8.1） |
| **R6** | **iOS 完全未验证**（项目只测过 Android）；iOS 静音拨杆与 WebAudio 交互、`suspend/resume` 爆音 | 🟡 低（当前） | iOS 设备到位后单测；`sfx.ts` 注释已记录同类现象 |
| **R7** | 音乐与美术喜剧层不同步（鹅走过时音乐没反应） | 🟡 低 | §2.4 的鹅/鸡事件目前**只做环境层**（成本低、无耦合）；**不**做与美术帧的精确同步（那要跨模块时序，性价比低） |

## 14. A-3 音频等价物审计（可访问性接口）

> 本节是 `design/accessibility-requirements.md` 的 **A-3（字幕是否要做）** 与条目 **#13（音频字幕/文字大小，L2）** 的**权威答案**。a11y 文档**引用本节即可，不在此重复写规则**（治 D-39）。

### 14.2 结论

> **否 —— 本作音频不通过任何音效传递"别处拿不到"的玩法信息。**

- 全部 11 种音效在触发处均伴有**同步的视觉或文字反馈**：模态弹窗、事件日志、伤害浮字、英雄位移、结果弹窗、图标切换、HUD 计数。
- 音效在此是**反馈增强（affordance / juice）**，不是信息通道。
- ⇒ **字幕 / 音频文字等价物：不需要**（A-3 答案为"不做"）。
- 听障玩家关闭 `homm.mute` 后，所有信息仍经视觉/文字通道完整可得，**不丢失任何玩法信息**。
- 满足 `accessibility-requirements.md` L2 条目 #13 的"音频字幕"项 —— 因无唯一音频信息，该项的字幕要求**不适用（N/A）**，而非未达标。

### 14.3 对未来音乐/环境音的设计纪律（防退化）

现状无问题，但**音乐一旦承载唯一语义即制造 a11y 负债**（须同步维护视觉等价物，成本失控）。写作纪律：

- **D-A3.1 音乐不得承载唯一玩法信息**：禁止"用特定旋律/动机表示某事件（城镇被袭、敌人现身视野边缘、移动力耗尽）而无视觉对应"。音乐是调性与氛围，不是信号。
- **D-A3.2 环境音同理**：环境床（风/水/叶）纯氛围；任何"事件"型环境声（鸡/鹅/水泡）若表达玩法含义（如"附近有敌方单位"），必须已有视觉通道，否则降级为纯装饰。
- **D-A3.3 新增音效的硬门禁**：未来在 `sfx.ts` 增加任何"携带状态变化"的音效（尤其战斗外的世界事件，如城镇受袭警报），**必须**在同一处提供视觉/文字反馈，否则违反 L2 #13、构成 a11y 缺陷。此门禁写入 `sfx.ts` 扩展规范（实现任务阶段落实）。
- **D-A3.4 反例（明确禁止）**：HoMM 式"城镇被攻击"专属警报音 —— 若无同步的"城镇受袭"弹窗/日志/地图标记，**不得**加该音效。

> 现状：本作**无**"城镇被袭""敌方入视野"类后台世界事件音效（`sfx.ts` 范围见 §1.1）。若将来加此类事件，先定视觉通道，再定音效。
