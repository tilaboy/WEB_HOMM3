## 1. 场景定义（先钉死"为谁、在什么时刻、玩多久"）

- **有名字的玩家**：**阿凯**。HoMM3 老玩家，现在用手机玩。他不需要教学，他需要"别挡着我"。
- **有名字的时刻（D-32 = 探索与经营并列，各为一等公民，二者都是「主场景」）**：

  | 时刻 | 循环 | 主面（在哪发生） | 对常驻元素的要求 |
  |---|---|---|---|
  | **探索时刻** | 点地格 → 英雄走过去 → 把东西捡起来 | **冒险地图**（全屏底层） | 地图零遮挡；终点与代价可见；推进回合（结束一天）在拇指带 |
  | **经营时刻** | 回城 → 看清资源缺口 → 决定造什么 / 招什么 → 走人 | **城镇管理面板** | **必须有与地图对等的一等入口**（常驻）；进入 ≤1 步；资源缺口在决策处可见（造价行"还差"）；出口不滚动 |

  **同时满足两者的方式（这是本规格的结构主张）：**
  1. **共用的常驻元素**（服务两个时刻）：地图（探索主面）· 顶栏只读状态（金/木/矿 + 稀有聚合槽——两地都要看）· **日期（两方的共享时钟：周刻度同时结算经营产出与探索节奏）** · 结束一天（回合推进，两地共用）· 拇指带入口组。
  2. **各自按需的专属面**：探索侧 = 地图与 `armedMove`；经营侧 = 城镇管理（含建筑/招募/驻军/市场·工坊四个标签页）。
  3. **两条纪律同时适用**：**"常驻元素必须为它让路"这句话，现在对两个时刻是同一句话** —— 地图不许被挡（探索），经营入口不许被埋在探索的从属位置（经营）。
  4. **不许的结构**：把经营入口塞进"英雄面板的一个从属区块"（原方案 §3 #33 就是这么降级的）→ 那等于**默认经营是探索的附属**。已按 D-32 修正为**常驻一等入口**（见 §3.0 重校）。

  **两条支柱（与设计支柱文档对齐，canonical 用词 =「经营」，不另造词）：**

  | 支柱 | 一句话 | 意图层投影 |
  |---|---|---|
  | **探索** | **「用腿换信息」** —— 每一格行军都要换回点什么（视野／资源／对手位置） | I1 / I2 |
  | **经营** | **「用信息换兵力」** —— 每一次回城都要把看到的东西变成能带出门的东西 | **I6「回城把事办了」** |

  > 两条支柱句**同构**（互为输入输出：探索产出信息、经营把信息变成兵力），这是"并列"在措辞层面不制造主次的保证。

- **有名字的会话长度**：**「一局 8 分钟的碎片会话」**（⚠️ **这是假设，不是实测** —— 推导见 §附录 A.2 / 开放问题 **Q1b**）。它的含义是：一局里阿凯会**开合面板很多次、每次停留很短**，所以"开合成本"必须接近 0，"看着被挡"必须接近 0。

> 一句话选题（D-32 后）：**地图是探索的一等面，城镇是经营的一等面 —— 两个面都按"最小常驻 + 按需可达"的同一套纪律办，谁都不许降级成对方的附属。**

## 2. 三层分离（意图 / 规则 / 数据，不要混着读）

### 2.1 意图层 —— 玩家想达到什么（设计目标，不涉及实现）

| ID | 意图 | 现状问题 |
|---|---|---|
| I1 | 「走过去把东西捡了」——只要结果，不要过程 | 路径/落点被事件窗口与提示条挡住（见 §9 F2/F5） |
| I2 | 「决定之前先知道代价」——这一步花多少移动力、要几天、会不会打起来 | **触屏上根本无法预览路径**（代码事实，见 §附录 B.3） |
| I3 | 「随时确认我有什么」——部队、英雄状态、城池——但**别挡地图** | 面板 46% 屏高常驻在底部（见 §9 F3） |
| I4 | 「推进时间」——今天做完了 → 明天 | 主操作在右上角且会横向漂移（见 §8 流程 D） |
| I5 | 「随时暂离 / 回来」 | 读档藏在红色「新游戏」后面（见 §8 流程 E） |
| **I6**（D-32 并列） | **「回城把事办了」——看清缺什么、决定造/招、然后回地图** | **经营入口被埋在"英雄面板最末一段"，要下拉到底**（见 §9 F3/F4）→ 经营被结构性降级为探索的附属 |

### 2.2 规则层 —— 系统怎么响应（**最小规则集，只 9 条**）

> 原则：**每加一条规则，都要能删掉一个常驻元素**。这 9 条足以覆盖 §8 的全部流程。

- **R1 地图是底层。** 任何面板都是叠加层；关闭后回到地图，且**镜头与选中英雄不变**（不许"关掉面板把地图重置了"）。
- **R2 入口 = 出口。** 一个面板只有一处入口，且由同一处的按钮、或一个常驻的「返回」关闭。不允许"入口在这里、出口在滚动流末端"。
- **R3 出口不滚动。** 任何面板的关闭 / 返回**固定在面板左上角**，不参与内容滚动。
- **R4 超行就分段。** 任何面板的纵向可点元素超过"一屏行数上限"（**真机 320 口径 = 4 行**，见 §5.4 / 附录 A.3）时，必须切**标签页（tab）**，**不许用纵向滚动**。
- **R5 高频在拇指带。** 「移动 / 出发确认 / 结束一天 / 打开英雄面板 / **打开城镇管理**」常驻**屏幕底部 48px 拇指带**，且**位置不随内容变化**（肌肉记忆）。**D-32 后"城"与"英雄"是并列的一等入口**——探索与经营各得一个常驻入口。
- **R6 低频进菜单。** 存档 / 读档 / 音效 / 光照 / 画质 / 新游戏**只存在于菜单**（一层交互可达），不常驻。
- **R7 顶栏只读、拇指带全交互。** 顶栏（≤32px）是**纯展示层、零可点目标**（`pointer-events:none`）；**所有可点入口集中在底部拇指带（≥44px）**。这条让"顶栏很矮"与"按钮要够大"两件事**不再冲突**（见 §4.2 决议）。
- **R8 确认层复用拇指带、不做 modal。** 「移动前二次确认」（D-31 = 方案 b）以 **`armedMove`** 态把**拇指带整条变形**为确认条，**额外屏预算 = 0**；因为 `tryMove` 会早退于 `isModalOpen()`（工程口径），确认层**不进 modal**，是轻量浮层。
- **R9 探索与经营并列，各有一等常驻入口（D-32）。** 「英雄」（探索侧信息）与**「城」（经营主面）**在拇指带内**同等级**常驻；**任何一方的入口都不得只存在于另一方的从属区块里**（这正是原方案把城镇管理埋进英雄面板末尾所犯的错）。

## 3. 信息分级表（**本交付物的核心 —— "剪掉没用的"的答案**）

判定口径：
- **常驻** = 默认地图界面上**永久可见**，不点任何东西就能看到。
- **按需** = 需要**一次交互**（点一下）才能到达。
- **可去掉** = 冗余、或可由他处推出、或语义错误 —— **删除或降级**。

> ⚠️ 判定标准：一个元素要成为「常驻」，必须回答 **"它凭什么永久占据 792×320 里的一块"**。答不上来的，一律按需或去掉。

### 3.0 D-32 重校（探索 / 经营并列口径下，48 项逐类复核）

**重校方法**：对每一项问两个问题 —— ①**探索时刻需要它吗？** ②**经营时刻需要它吗？** 只要**任一方**需要，它就不能因为它"偏另一方"而被降级/砍掉。**双方都不需要**的，才是真「可去掉」。

| 类别 | 重校结论 | 处置 |
|---|---|---|
| **共用信息**（资源金/木/矿、稀有、短日期、结束一天、地图、拇指带入口组） | 两地都要看 → 常驻 | **维持常驻**，并在 §3.1 标注"服务：两者" |
| **探索侧**（选中英雄、移动路径、跨天小旗、格子详情、`armedMove`、英雄面板） | 探索需要 | 维持原判（大多按需） |
| **经营侧**（建筑 / 招募 / 驻军 / 市场·工坊 / 税收·城防·增长） | 经营需要 | 维持原判（按需，但**都在经营主面之内**） |
| **经营主面的入口** | **经营需要，且是"一等公民"的判定点** | **🔧 恢复/新增一项**：**拇指带常驻「城」入口**（见 §3.4 新增 #49）。原方案把城镇管理埋在"英雄面板最末一段"= **默认经营从属于探索** → 违反 D-32，已修正 |
| **城镇页顶部资源 chip 行**（#35） | 建筑页不需要"总览"（每张卡已列"还差"）；**但市场页需要"我的资源"**（见下行） | **建筑页：可去掉**；理由不是"与顶栏重复"，而是"用**决策处可见的造价行**替代顶部堆叠，把经营首屏的 ≤4 行额度（R4）留给建筑卡" |
| **市场页的决策输入**（金币/木/矿/稀有当前量） | **经营需要，且属"决策处可见"的硬要求** | **🔧 恢复/新增一项**：市场页内必须有 **「我的资源」行**（见 §3.4 新增 #50）。与设计支柱复核后确认：市场页**没有建筑卡列**，不占 R4 的 5 行额度；且现状是**点了才知道**（`TownDialog.ts` 市场失败文案 `金币不足` / `水晶不足` 都是**操作后**文案，事先不可见）→ 市场页的全部决策变量就是"我现在有什么" |
| **顶栏稀有明细下钻** | 经营时刻确实要看 4 种稀有明细 | **维持"顶栏不做下钻"**，但**重校后必须保证**：① 顶栏稀有**聚合槽常驻且不隐藏**；② 明细在**经营主面内逐项可见**（造价行"还差"；市场页「我的资源」行）→ 经营侧的信息需求**在其自己的主面里被满足** |
| **存档 / 读档 / 音效 / 光照 / 画质 / 新游戏**（#12–15） | 两地都不需要常驻 | 维持可去掉（进菜单） |
| **「总第 Z 天」（#9）、玩家名文字（#10）** | 两地都可由他处推出 | 维持可去掉 |

**结论：重校后共 2 项恢复/新增** —— ① **拇指带「城」入口**（#49，经营主面的一等入口）；② **市场页「我的资源」行**（#50，决策输入）。**0 项被误砍**。另 3 项（#35、稀有下钻、日期归属）**判定不变但论证已重写**为并列口径。会话长度假设见 Q1b。

## 4. 792×320 屏幕预算（**横屏手机竖向只有 320px，这条最关键**）

> **口径更正（D-66 真机走查，2026-09-21）**：本规格初稿的屏预算按 **探针 792×360** 计（得可用内容区 752×304）。**真机自然横屏实测为 792×320**（探针未计入顶部系统栏那 40px）。两者竖向差 40px ⇒ **本规格以真机 320 为准**，全表已重算；360 口径的旧值仅保留在附录 A.2 作对照（不删，留痕）。

### 4.1 可用内容区（先算清楚"我们到底有多少地"）

```
视口          = 792 × 320            （真机实测；原探针口径 792×360）
安全区内缩    = 上40 / 下16 / 左40 / 右0   （实测 --safe-area-inset-*）
▶ 可用内容区  = (792−40−0) × (320−40−16) = 752 × 264 px
                 （原 360 口径 = 752 × 304；少 40px 竖向）
```

**关键结论：竖向只有 264px 可用，横向有 752px。→ 所有"占地方"的东西都该靠边（用横向），不能靠下（用竖向）。**
这条直接判了**底部抽屉死刑**（§9 F3）—— 且在 320 口径下比 360 口径**更狠**（竖向又少 40px）。

> **起因**：若顶栏高 ≤32px 却要放一个"必须可点"的日志入口（32×32），就与 §5.2 的「常规 ≥44」和「禁 <40px 横向相邻按钮」**结构互斥** —— 不是调尺寸能解决的。

### 4.5 阻断式面板（城镇 / 魔法书 / 设置）几何 + D-66 修法

> **起因（D-66 真机走查，2026-09-21 · 工程提供几何证据，本轮为 UX 裁决）**：真机 **792×320** 下，城镇管理面板的内容窗 `.town-pane` `clientHeight` **只剩 48px**（工程口径：P3 前 ≈248px ⇒ **P3 引入的回归**）；面板**内容总高 ≈403px、7 张建筑卡（较高的单卡 ≈149.3px）**，⇒ **一屏 0 张完整卡、需 ≈8.4 个窗高位方能滚到底**；面板空态仅 57px。**这正是用户抱怨"可玩性差 / 操作看不清"的那一条。**

**根因（两层，缺一不可 —— 只修一层不会好）**

1. **表层（CSS 尺寸）**：`.modal.wide` 只有 `max-height`（`min(248px, 88%)`）、**没有 `height`**，再叠 `display:flex; flex-direction:column` ⇒ 面板高度=内容高，而内部 `.town-pane{flex:1 1 auto; min-height:0}` 被挤到 **48px**。
   - **一个易误判点（先排掉）**：`min(248px,88%)` 在 320 上求值**仍是 248px**（88% = 281.6 > 248）⇒ **压到 48px 的元凶不是这个 `min()`，而是"没有确定高度"这一条**。
2. **深层（内容密度，真正的病根）**：**单张建筑卡过高** ⇒ 内容总高 ≈403px 远超任何可用窗高。**这层尺寸 patch 改不动。**

**修法决策：以 (c) 为终局、配 (b) 为必要伴随；(a) 只算临时止血。**（工程提供 a/b/c 三档）

| 档 | 工程提案 | 判决 | 理由（一句） |
|---|---|---|---|
| **(a)** 补 `height`（→105px，0.7 卡） | 只补确定高度，卡不变 | **❌ 不是答案（可作 1 行 CSS 临时止血）** | 能把 48px 救到 ≈105px（一步可用），但卡密度未动 ⇒ **仍要滚 8 个窗**，**R4 未解** |
| **(b)** 近全屏（→185px，1.2 卡） | 面板吃满内容区 | **✅ 必要伴随** | 320 下 `.town-pane` 需 ≥~150px 的**确定高度**才放得下"标题 + 标签页 + ≥3 卡"；近全屏是能给出这个高度的唯一形态 |
| **(c)** 卡片密度（重排：单卡 →~56–64px / 双列） | 重新排版建筑卡 | **✅ 终局修法** | **病根就在卡高**；压到 ~56px + 双列后，建筑页 **≤4 行、不滚动**（合 R4），也才可能同时满足高度预算 |

**⇒ 本规格裁决：`(c) + (b)`。** 若工程想先发 (a) 救急可以，但**必须在同一迭代内跟进 (c)** —— 否则等于把"滚 8 个窗"留在发布里。

**三条硬约束（写进验收，可机检）**

- **P1 · 内容窗必须有确定高度**：阻断面板内部内容窗用 `height`，不得只给 `max-height`。**机检**：真机 792×320 下 `.town-pane` 的 `clientHeight ≥ 150px`（当前 48px ⇒ FAIL）。
- **P2 · 建筑标签页不滚动**（R4 数值化）：**机检**：`scrollHeight ≤ clientHeight + 1`（当前 403 > 48 ⇒ FAIL）。
- **P3 · 标签页按钮高 ≥ 44px**（现状 40 < 44，违 §5.2「常规 ≥44」）：**机检**：`getBoundingClientRect().height ≥ 44`。

> **C2 豁免的正当性（为什么阻断面板可以"近全屏"）**：C2 防的是"**我正要看地图，面板却挡住它**"。而阻断面板的进入/退出**各 1 步、且由玩家主动发起**（§8-C：拇指带「城」直达 / 左上「←」常驻）—— **用到它的那几秒本就不需要地图**。所以把"地图可见性"从**阻断面板**上摘掉，是**撤掉一条被误用的约束**，不是放水。**非阻断面板（右侧英雄栏 / 日志）继续受 C2 ≥54% 管。**

## 5. 尺寸与密度规则（基于实测 **p90 = 23px** 落点散布）

### 5.1 前提（实测）

- 真人手指点击最小按钮：**误触 0/8，但落点偏差 p50 = 13px / p90 = 23px**。
- 最小的 `宝物▾` = **40×32 CSS px**，半宽 20px，手指落在离中心 19px 处 → **横向余量仅 1px**。

**⇒ 结论：不能按"能不能点中"设计，要按"p90 = 23px 会偏出去"设计。**

### 5.2 最小目标尺寸（推导）

要让"落在本目标内"不为 p90 误差所破，目标**半宽**需 ≥ p90：

```
半宽 ≥ 23px  ⇒  边长 ≥ 46px  ⇒  取整 48px（并留 2px 余量）
```

| 层级 | 最小尺寸 | 用途 |
|---|---|---|
| 主操作 | **≥ 48 × 48** | 结束一天、建造、攻击、确认 |
| 常规按钮 | **≥ 44 × 44** | 菜单、面板开关、招募 |
| 密集区元素 | **≥ 40 × 40**，且**中心距 ≥ 48px** | 部队格、宝物格、市场网格 |
| 纯展示 chip（不可点） | 允许 ≤ 32，但**必须 `pointer-events:none`** | 资源数字、状态标签、**整个顶栏** |

**5.2.1 命中区 ≠ 精灵渲染尺寸（美术侧硬约束，实现说明必须写进去）**

- 按钮**盒子**尺寸（40 / 44 / 48）只是**命中区**，与其中**图标本体**的尺寸**解耦**。
- 图标是 **24×24 画布**的图集精灵（`asset-spec.md` §1.2：加 1px 描边后 16×16 只剩 14×14 可用，故定 24）；像素画**只能整数倍**放大（`cartoon-style.md` §1.3 / §8.4：非整数缩放会让像素行列宽窄不均，硬边立刻发毛）。
- ⇒ **图标本体只允许 24×24（1×）或 48×48（2×）两档**，居中留白补齐。**36、44 等非整数倍禁止用于图标本体** —— 44px 盒子只能放 24 图标，只有 ≥48px 盒子才可放 48 图标。
- 落位核对：32px 只读 chip → **24×24 图标 + 4px 边距** ✅；48px 拇指带按钮 → **24×24 或 48×48** ✅。

### 5.3 相邻间距规则（推导）

设目标边长 S、相邻间隙 `gap`，要"点 A 不落进 B"，需 `S/2 + gap ≥ p90 = 23`：

| S | 允许的最小 gap |
|---|---|
| 48 | **≥ 0**（自然满足） |
| 44 | ≥ 1px |
| 40 | **≥ 3px** |
| 32 | ≥ 7px |

**⇒ 现状违规（两类，同一病根：横向相邻按钮太矮）**：
- `宝物▾ 40×32`（`HeroPanel.ts`，与 `‹ ›` 横向相邻，实测余量仅 1px）→ 违规；
- `.btn.tiny` 全局 `min-height:32px`（`style.css` 的 `.tiny` 规则）被用于**横向相邻按钮行**（城镇招募行 4 个：招1 / 招5 / 全招 / 驻军）→ 同违规。

**⇒ 修法（一处改、全站生效）**：把 `.btn.tiny` 最小高度 **32 → 40**，横向 gap 保证 **≥ 4px**（S=40 需 gap ≥ 3），再靠 `.tap::after` **只纵轴**扩 4px → 命中高 48。招募行若 4 钮排不下，改 **≤ 3 钮/行**。

**⇒ 禁则**：**不允许出现高度 < 40px 的横向相邻按钮**。允许的例外：现有 `.tap::after` **只纵轴**扩命中区，**且仅在纵向最近邻 ≥ 14px 时可用**；横向**永不**扩（会与邻钮命中区重叠）。

### 5.4 密集区怎么办（R4 的数值化）

竖向 264px 里（真机 320 口径）：标题 ~48px + 每行 48px ⇒ **一屏最多 4 行可点元素**（4×48 = 192 ≤ 216）。**（360 口径曾为 5 行 —— 少 40px 竖向就少一行，这是 320 口径的直接后果，也加重了 D-66 城镇页的密度压力。）**

- **> 4 行 → 分段（标签页），不滚动。**
- 若确实需要更多，用**标签页 ≤ 5 个**，每个标签页内 ≤ 4 行。

## 8. 操作流程规格（5 条，标注"最少必要步数 vs 当前实际步数 + 摩擦点"）

> 「步数」= 玩家的**独立交互动作数**（点一下 / 滑一次算 1 步）。只读的"看一眼"不计步。

### 流程 A：移动英雄并捡宝（**主场景**）

- **意图**：把英雄走到一处资源/宝箱上，自动拾取。
- **最少必要步数：2**（① 点目标格 → ② 点「出发」确认）。**已由用户拍板 D-31 = 方案 (b)**：宁可多 1 步，换取"移动前看得见路径与消耗"（意图 I2）。英雄默认为 `heroOrder[0]` 已选中，故不额外计步。
- **当前实际步数：1–2**（当前选中的不是想要的英雄时，需先点该英雄再点目标 → +1）。**注意**：现状是"点了就走"，代价是**触屏永远看不到路径与消耗**（`shouldHover` 只对 mouse/pen 放行，附录 B.3）。
- **摩擦点（5 条）**：
  1. **触屏永远看不到路径预览** → 违反 I2，凭感觉点（D-31 就是冲它来的）。
  2. 目标格若落在左上事件窗口下（实测该窗口在 ≤860px 下为 **220px 宽**）→ **看得见挡、看不见格**；且 `pointer-events:none` 让点击照样生效 → **"看不见但点得中"**，最坏组合。
  3. 每次 hover/点击都改写底部提示条 → 文字闪烁（已判"可去掉"）。
  4. 移动力耗尽后提示"点右上角结束一天"，而该按钮**在主操作最远处**（右上，见 §8-D）；且顶栏声明了 `overflow-x:auto`（`style.css` 的 `#topbar` 规则，**潜在**横滑风险，792 实测未触发）—— 真正的病灶是**该按钮在压缩下顶破 52px 条**（高 75px，见 C3 证据更正）。
  5. 长按当前被"查看格子"占用（`main.ts` 的 `longPress` → `showTileInfo`）—— (b) 不走长按，故**长按语义保持不变**，不冲突。

- **重设计后目标（按 (b)）**：
  - 点目标格 → 进入 **`armedMove`（待确认移动）** 态：地图上**画出路径**，**拇指带整条替换为确认条**（见下）。点「出发」执行；点「取消」/ 点别处 / 物理返回键撤销。
  - **确认条形态（UX 定稿）：复用底部拇指带，不新增一条、不做 modal。**
    - 原因：`tryMove` 会早退于 `isModalOpen()`，且边缘滚屏用同一闸（工程口径）→ 确认层**不进 modal**，就是普通浮层；又因 `armedMove` 是短暂态，**整条拇指带变形**即零额外占地。
    - 版面（单行，48px 内）：左＝`→ (12,7) · 3.5 移动力 · 今日可达 / 约 2 天`；右＝`[取消]`(44) + `[出发]`(48)。
    - ⇒ **额外屏预算 = 0**（复用既有 48px 拇指带）；`armedMove` 期间 菜单/英雄/城/结束一天 隐藏（避免误触），取消后原样恢复。
    - 备选形态（若工程发现拇指带放不下两行）：**目的地旁小气泡**，但需接受"浮层压在地图上、位置随目标变"两个缺点 → 本规格**不推荐**，保留为兜底。
  - **取消路径（3 条，都要能验收）**：① 确认条「取消」；② 点地图别处（改目标 = 重设 `armedMove`，点不可达处 = 撤销）；③ Android 物理返回键（优先撤 `armedMove`，见 Q5）。
- **验收**：
  - 点目标后**在不移动英雄的前提下**，可见到 路径 / 消耗 / 今日能否走完；点「出发」才动。
  - 主场景全程**无需移动镜头、无需滚动任何条、目标格不被任何常驻元素覆盖**。
  - 确认条出现期间**地图可见面积不下降**（因为它复用拇指带，C1 守恒）。
  - 三条取消路径都生效。

  **状态图（常态 ↔ `armedMove`）—— 拇指带是同一块地被换内容，不是"多出一层"：**

  ```
  ┌─ 常态 ─────────────────────────────────────────────┐
  │  [菜单] [英雄] [城] [结束一天]                        │
  └──────────────┬─────────────────────────────────────┘
                 │ 点地图目标格（路径画在地图上）
                 ▼
  ┌─ armedMove ────────────────────────────────────────┐
  │  [ → (12,7)·3.5力·今日可达 ]      [取消] [出发]     │  「结束一天」在此态不可用
  └──────────────┬─────────────────────────────────────┘
                 │ ①「取消」 ② 点别处 ③ 物理返回键
                 ▼  点「出发」→ 执行移动 → 回到常态
  ┌─ 常态（原样恢复）───────────────────────────────────┐
  │  [菜单] [英雄] [城] [结束一天]                        │
  └────────────────────────────────────────────────────┘
  ```

  > ⚠️ **行为后果（唯一副作用，必须写出来）**：`armedMove` 期间**无法「结束一天」**，因为该按钮的位置被确认条占用了。回去只需 **≤1 步**（取消/返回键），故可接受；但它确实是玩家可能察觉到的行为差异，**不许藏在实现里**。

> ⚠️ **命名（工程口径）**：本文说的"待确认移动"对应代码里的 **`armedMove`**，**不是** `pendingDest`（后者=跨天行程目的地，今日走不完→插旗→按 M 继续，两个不同状态，勿混接）。

### 流程 B：查看英雄详情

- **最少必要步数：1**（打开英雄面板）。
- **当前实际步数：1 + 纵向滚动若干**（面板在底部抽屉占 46% 屏高，内容超一屏；移动力/部队/城池散落其中）。
  - 额外硬伤（推导）：面板收起时容器 `max-height:34px + overflow:hidden`，而其中的开合按钮 `min-height:44px` → **按钮被裁到 34px，可点区连带被砍** → 违反 §5.2。
- **重设计后目标**：1 步打开右侧抽屉；**首屏不滚动**即含 移动力 / 部队 / 城池入口。
- **验收**：打开后**不滚动**即可读到 移动力 + 部队 + 城池入口；抽屉每次都在同一位置。

### 流程 C：进入城镇管理并**关闭**（经营时刻，D-32 一等公民）

- **最少必要步数：2**（进入 1 + 关闭 1）。
- **当前实际步数：4–5**：
  1. 展开底部抽屉；
  2. 把抽屉**滚到底**（城池列表是面板最后一段）；
  3. 点「管理」；
  4. 干完活后，**把弹窗滚到底**（`关闭` 在 `.actions`，而 `.modal{overflow-y:auto}` → 出口随内容滚走）；
  5. 点「关闭」（或在遮罩上点一下）。
- **重设计后目标（D-32）**：
  - **拇指带「城」= 直达（1 步）** —— 经营不必再"先展开英雄面板 → 下拉到底 → 点管理"；这是"并列一等公民"在流程上的体现。
  - **左上固定「←」= 关闭（1）**；内容用标签页，不依赖滚动。
  - 多城时「城」开"最近/选中英雄所在城"；其余城镇：地图上点城主塔，或从英雄面板城池列表进（**两条路并存，但都不是唯一入口**）。
- **验收**：**任意滚动位置都能 1 步关闭**；从主界面进入任己方城镇 ≤ 1 步（拇指带）或 1 步（地图城主塔）；城镇页内不出现堆叠式资源 chip 行。

### 流程 D：结束一天

- **最少必要步数：1**。
- **当前实际步数：1**（按钮完整在条内时的正常态）。**（原写"1 + 横向滚动" —— 该路径在 792 实测未触发，属潜在路径，见 C3 证据更正；保留为"若顶栏溢出则 +1 滑动"的条件项，不作为常态。）
- **摩擦点**：主操作放在**右上角** —— 横屏双手握持时，右上是最远、最不稳的点；**且该按钮尺寸 54×75 与邻居 44/45 不一致（"大的大，小的小"），压缩下更会顶破 52px 条**（已复现，见 C3）；`overflow-x:auto`（`style.css` 的 `#topbar` 规则）是**潜在**横滑/位置漂移源（792 实测未触发，**但机制仍在**）→ 一旦触发即肌肉记忆失效。
- **重设计后目标**：固定在**底部右侧拇指圈，48px**，永不随内容移动。
- **验收**：单手（右手）握持时，拇指不移动手掌即可点中；该按钮在**任何状态下位置固定**。

### 流程 E：存档 / 读档

- **最少必要步数**：存档 = **0**（已自动）/ 1（手动）；读档 = **1**。
- **当前实际步数**：
  - 存档 = 1（顶栏「存档」），但**冗余**（附录 B.4）；
  - 读档 = 点「新游戏」(danger) → 开始页 → 「继续」= **2 步，且入口语义错误**（红色"新游戏"暗示要丢档）。
- **重设计后目标**：菜单里 `存档 / 读档 / 回主菜单` 三者语义分明；**「新游戏」单独、二次确认**。
- **验收**：从主界面到"读取最近存档" ≤ 2 步；"新游戏"必须二次确认，且不会与"继续"混淆。

## 9. 对 5 条反馈的逐条处置（方案 + 为什么 + 验收标准）

### F1 「顶部控制栏东西非常多，大的大、小的小，很多没什么用」

- **方案**：顶栏拆成 **(a) 只读状态条（≤32px，金/木/矿 + 稀有聚合槽 + 短日期，**零可点目标**）** 与 **(b) 拇指带交互组（菜单/英雄/城/日志/结束一天） + 菜单（R6 收纳 存档/音效/光照/画质/新游戏）**；统一尺寸档（§5.2）。
- **为什么**：用户的"大的大、小的小"= 视觉层级混乱 + 尺寸不达标；且**低频项常驻零收益**（§3.1 逐项判定）。
- **验收**：顶栏可点/信息块 **9 → 5**；**顶栏内零可点元素**（C4）；所有可点目标 ≥ 44px；同一行高度差 ≤ 8px；**移除 `overflow-x:auto`（C3）**；**顶栏内任一子项高度 ≤ 顶栏高度**（消除"结束一天 75px / 新游戏 60px > 52px"的顶破，**这是当前已复现的故障**）；**多宽度扫描（如 720 / 792 / 860）均无横向溢出**（C3 修正口径）。

### F2 「事件窗口一直在滚动，挡住地图的一部分，像测试版」

- **方案**：`#logbox` 从"常驻悬浮块"改为 **(a) 收起态 = 底部拇指带内 44×44「日志 N」**（**不放顶栏**，理由见 §4.2 决议 R7：顶栏只读、且 32×32 放不下 44 的目标）；**(b) 展开态 = 点开后从右侧滑出面板**（复用英雄栏位置），显示最近若干条，点外部关闭。**移除 `pointer-events:none`**（要可交互）。
- **为什么**：日志是**低频回顾**（但"未读指示"值得常驻）；而现状把一块 UI 压在**地图左上**这一最贵位置（主场景的起点视野），**视觉上就是"测试版"** —— 它不参与任何主交互，却永久占位。
- **验收**：默认态地图左上角**无任何遮挡**；日志入口为**菜单一级项「事件日志」**（**F-3.6 后**：原判"拇指带 44×44 且与「结束一天」相邻"**已随 #23 改判**；**未读角标**改挂拇指带「菜单」按钮）；展开时**不覆盖地图中央**；日志块不再是 `position:absolute` 悬浮于 stage 左上。
- **备注（对证据的修正）**：实测该块在 **≤860px 断点下宽度为 220px**（`style.css` 的 `#logbox`（≤860px）规则），即 **220/752 = 29.3%** 内容宽（桌面 300px/792 = 38%）。无论 29% 还是 38%，都不该常驻。

### F3 「面板在左下角，查看什么要一直下拉，管理城池要拉到底」

- **方案**：**废弃底部抽屉**（删除 `@media(max-width:860px)` 里把 `#side` 变成 `bottom:0; max-height:46%` 的规则），改为**右侧垂直栏**（宽 ≤200px，默认收起为 48px 竖条）；**探索与经营各给一个常驻直达入口**（拇指带「英雄」/「城」，D-32）；城池在面板内**独立入口**，不再排在列表末尾。
- **为什么**：**根因是方向反了** —— 横屏竖轴稀缺（真机 320 口径 **264px**；360 口径曾为 304px），而断点把侧栏变成"用最缺的轴"的底部抽屉（46%×264 ≈ 121px）。横向有 752px 富余，**面板就该放侧边**。**D-32 补充**：原设计的"城池列表在英雄面板最末一段"还把**经营**做成了探索的从属 → 已修正为并列常驻入口。
- **验收**：英雄详情**首屏（不滚动）**含 移动力 + 部队（城池另走「城」直达）；从主界面进入城镇管理 ≤ 1 步；**任何面板的入口/出口都不依赖纵向滚动**。

### F4 「城市管理页面东西非常多，而且要滚到底才能关闭」

- **方案**：**① 关闭/返回固定左上角（sticky，不随内容滚动）**；**② 内容分段为标签页**（建筑 / 招募 / 驻军 & 部队 / 市场 · 工坊），每页 ≤ 4 行可点元素；**③ 删掉建筑页顶部堆叠式的资源 chip 行**（改由建筑卡造价行承担）；**④ 市场页反过来要补一行「我的资源」**（#50，那边的资源量是决策输入）。
- **为什么**：**关闭按钮是"出口"，出口不能待在滚动流的末端**（R3）；内容多本身不是错，错在**长滚动 + 出口在流末端**。删建筑页 chip 行不是因为"与顶栏重复"，而是**经营首屏的 ≤4 行额度**要留给建筑卡（决策处信息）；而市场页的决策变量本身就是"我有什么"，故必须当时可见。
- **验收**：**任意滚动位置 1 步关闭**；单页纵向可点行 ≤ 5；**建筑页不出现堆叠式资源 chip 行、且每张建筑卡的"还差"逐项可见**；**市场页出现「我的资源」行，买卖按钮的可用性在点之前就能判断**（不再只靠 `金币不足`/`水晶不足` 这类事后文案）。

### F5 「总体操作非常不方便 —— 剪掉没用的、页面再干净些」

- **方案**：**① 拇指区原则**（R5）：**全部高频操作**（移动 / 出发确认 / 结束一天 / 打开英雄面板 / **打开城镇管理**）落到屏幕**底部 48px 拇指带**且位置固定；**② 低频全部进菜单**（R6）；**③ 触屏补上"移动前可见代价"** —— 按用户拍板 **D-31 = 方案 (b)**：点目标后进 `armedMove` 态、拇指带变形为确认条（R8），确认才走。**④（D-32）** 经营获得与探索同级的常驻入口，不再从属于英雄面板。
- **为什么**：把"剪掉没用的"落地成两件可测的事 —— **提高信噪比**（§3 分级表）+ **让操作落在手指够得着、且位置不变的地方**。现状的问题是：主操作在最远的右上，低频项在最顺手的顶栏，正好**全反了**。
- **验收**：单手握持时，**移动 / 出发确认 / 结束一天 / 打开英雄面板 / 打开城镇管理 全部落在下缘 48px 带内**；顶栏不再出现任何"一局用不到"的开关；触屏在**移动英雄之前**可见 路径 + 消耗 + 今日能否走完（D-31）；`armedMove` 态下地图可见面积不下降（C5）；**经营主面 ≤1 步可达**（D-32）。

## 10. 按画质档位的行为（对接现有 `quality.ts` 三档）

原则：**UI 布局与"操作位置"绝不随档位变化**（位置稳定对肌肉记忆是硬要求）；**只有渲染相关的开关随档。**

| 元素 | low | mid | high | 说明 |
|---|---|---|---|---|
| 昼夜光照开关 | **隐藏 / 置灰** | 可用 | 可用 | low 档 `lighting` 恒为 `multiply` → 开关无意义，显示反而误导 |
| 网格线 / 暗角 / 暖光 开关 | 随档显示可用性 | 同左 | 同左 | 若放进设置，按当档实际生效项显示 |

| 事件日志自动弹出的行数 | 1 行 | 2 行 | 2 行 | 仅影响叠加层高度，**不得改变地图可见 ≥68%**（C1） |
| 地图尺寸上限 | 32 | 40 | 48 | 已在开局 clamp，UI 无需额外处理 |

### 13.2 三场景逐条（**按"英雄旁的队伍徽标"重判**）

**① 认位 —— 不成立（撤销）**
- 徽标**不占格**、不动英雄棋子的落位 ⇒ 格子的视觉锚点仍是**英雄棋子**（32 宽、恰好占满一格、居中）。**"它在哪一格"完全不受影响。**
- 旧版担心的"两徽标叠置"**由 13.4 的选侧规则自动消解**：相邻两英雄会因"一侧的徽记矩形与另一英雄棋子包围盒相交"而**各自翻向空侧**，不会撞在一起（见 13.4 规则 2）。

**② 点选 —— 不成立（撤销）；残余一条"轻且良性"的变体**
- 徽标**不可点**：`camera.pick` 与"画了什么"无关 ⇒ **"想点单位却走了一步"这个风险彻底不存在。**
- **残余（轻且良性）**：13.4 的徽标**物理上落在邻格**（选侧规则保证那是**空地形**）⇒ 点它 = 点**那个空邻格** ⇒ 若当前有选中英雄，可能触发"走过去"。但三重良性：① 概率低（剪影 ≤43px 的小图标、且无理由去点）；② 落点是**紧邻英雄的空格**，走过去代价极小；③ **D-31 的二次确认（`armedMove`）**已把"误走一步"降级为"看到路径与消耗后再确认" ⇒ **可接受，不需要为它改布局**。

**③ 遮挡 —— 成形，但**可解**（不是"真问题"，而是"一条必须守的规则"）**（见 13.0）
- 单个图标**必然占掉相邻的一格**（剪影 ≤43 > 32），并**向再下一格再溢出 ≤6px** —— 这是**量**的问题，不是"要不要"的问题。
- **可解**：只要定下"**选侧 + 只落"无信息"格 + 落不下就不画**"三条规则（13.4），遮挡即**归零**（它只覆盖**没有信息的空地形**）。
- **残余的唯一风险**：若实现时图省事、直接"**总画在最上层且不看落点**"，就会**违反 §1「常驻元素必须为地图让路」**—— 这正是要写规则的原因。

> **一句话**：**旧三场景两条作废、一条变形**；变形的那条（遮挡）从"擦边"变成"**必然占掉一格**"，但**是可解的**（靠 13.4 的三条规则）。所以对 team-lead 的问题，准确回答是：**旧的交互风险全撤；剩下的是一条"占格贴图"的**布局规则**，不是"能不能做"的障碍。**

- **M2（帧越界 ≤8px/侧且对称）→ 撤销，以 M2′ 取代。** 原判管"单位贴格绘制"；徽标是**挂在棋子旁的信息层**，"帧自身越界"不再是风险来源。**M2′** = **徽标不得遮住任何"有信息的像素"**（物件精灵 / `mk_*` / 英雄棋子，按**精灵包围盒**判定；**地形装饰 `deco_*` 不算"物件"、不纳入** —— 理由与实证见 §13.4 规则 2 注）；**覆盖无信息的空地形是允许的**（空地形没有信息可丢）。**口径别写成"不侵入邻格"** —— 24px 列无法既待在 32px 格内又不压棋子，那是**做不到的约束**。

### 13.4 布局规则（**给实现，可直接照做**）

**三条规则（= 实现的全部额外要求）**

1. **【选侧】** 按 **右 → 左 → 上 → 下**，取**第一个**满足「该格的**图标"可见剪影"矩形**（含 1px 描边，口径 = §13.0「判压格只看剪影 bbox」，**不是 52px 画布**）与所有**已揭示实体**的包围盒**都不相交**」的相邻格（实体 = 物件精灵 ∪ guard 标记 `mk_*` ∪ **英雄自身及其它英雄棋子**；**背景不计入** —— 地形 `g_*` / 岸线 `sh_*` / fringe / 空地装饰 `deco_*`，见规则 2 注）。**默认右侧。**
2. **【只落"无信息"格】** 规则 1 已蕴含：图标**只覆盖没有信息的空地形**（空地形没有信息可丢 ⇒ 覆盖它不违反 §1「为地图让路」）。**禁止**"总画在最上层、不看落点"的省事写法（那会直接违反 §1）。

   > **（补）徽标与地形已分离 —— 不是待办**：徽标画的就是兵种地图帧 `u_<cid>_map`（`MapRenderer` 的 `drawTeamBadge`），而**所有 `UNIT_FRAMES` 统一走 `buildB0Frame` 的 `outline(ink0, 1)` pass**（`unitArt.ts`）⇒ **每帧自带 1px `ink0` 描边**，由 `audit:b0` 的**断言 4「描边重跑干净」**守着（`tools/b0audit.mjs`）⇒ **视觉分离已成立，"脏"不是问题、无须为它做任何事**。

### 15.2 F-3.4 —— 遭遇对话框：≤2 行 + 选项首屏可见

**约束（可当决策）**：遭遇类对话框正文压到 **2 行**；**动作行首屏可见、不滚动**；**不再重复"我方兵力 / 敌方兵力"**（玩家自己知道）；**保留"打不打得过"这个决策结论**（原话见 `playtest-feedback.md` F-3.4）。

**"啰嗦"的机制性来源（读了 `interaction.ts` 的 `wanderingMonster` case 的 `message` 构造 + `main.ts` 里 `showModal(…, { body: […], actions: […] })` 的 `kind==='battle'` 分支，逐条点出）**

| # | 重复 / 冗余 | 出处（符号） |
|---|---|---|
| 1 | `message` 里的「对方兵力」 == 表格里的「敌方兵力」 | `interaction.ts` `wanderingMonster` case ↔ `main.ts` 该分支的 `rows` |
| 2 | `message` 里的「它们看守着」 == 表格里的「它们看守着」行 | 同上（`describeGuard(...)` 被调了两次） |
| 3 | 「**我方兵力**」整行 | 用户明确说"玩家自己知道" ⇒ 删 |
| 4 | `lossTable(rows)` 的**逐兵种** `before → after` 明细（≈ N 行） | **这是"要拉到最下面"的元凶** ⇒ 删 |
| 5 | `message` 的「预估战果」与 `lossText` 的「…（预估…）」**两处说同一件事** | 两处各写一遍 ⇒ 合一 |

**目标形态（2 行 + 动作）**

```
┌─ 遭遇成群野兽 ─────────────────────┐
│ 可以取胜 · 约损失 12% 兵力          │  ← 第 1 行：决策结论（用户点名保留）
│ 看守：宝石矿（每日 +1 宝石）        │  ← 第 2 行：看守物 / 奖励（有才出）
├────────────────────────────────────┤
│ [撤退]                 [进入战场]  │  ← 动作行：固定底部，永不滚动
└────────────────────────────────────┘
```

- **第 1 行 = 决策结论**（`outcome.win ? '可以取胜' : '难以攻克'` ∈ `interaction.ts` 的 `estimate` + 损失档 `lossGrade`）—— **这就是用户要保留的那条**。
- **第 2 行**：有 `guard` / 奖励才出；没有则只剩 1 行。
- **删掉的**：全部 `lossTable` 逐兵种明细、"我方兵力"行、重复的"敌方兵力 / 它们看守着"。
- **动作行**：`showModal` 现把 `.actions` 追加在内容之后，而 `.modal{overflow-y:auto}` ⇒ **内容一长，动作就被顶到屏幕外**（`Dialogs.ts` 的 `headClose` 注释已记录同一病因：*"出口随内容滚走，长内容要滚到底才能关"*）⇒ **须固定底部**。**与 §4.5 的 `headClose`（出口不滚动）同源**：**出口与动作永不滚动。**

**工程接口（给 `style.css` / `Dialogs.ts`）**：`.actions` 用 `position:sticky; bottom:0`，或把 `.modal` 改 `display:flex; flex-direction:column` 且 `.actions{flex:0 0 auto}`。**`style.css` = 跨域共享、同轮单一写者（engineering-lead，Q7）。**

**验收（可机检）**
- 对话框打开时，动作行 `getBoundingClientRect().bottom ≤ 视口底` 且 **无需滚动即可见**；
- **正文文本行数 ≤ 2**；
- 文案层：**"我方兵力" / "敌方兵力" 两串 0 命中**（`grep` 可查）。

**域边界（不越界）**：**超长守军明细**（若日后要"点开看详情"）**不在本约束内** —— 那属"玩家主动下钻"，不是常驻正文。
**同病提示**：`kind==='siege'`（攻城）分支也是同一套 `showModal` + `rows` 构造（"我方兵力 / 守军"同病）⇒ **本节规则对"遭遇类对话框"整体生效**，不止野怪一处。
