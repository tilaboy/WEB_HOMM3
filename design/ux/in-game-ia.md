## 1. 场景定义（先钉死"为谁、在什么时刻、玩多久"）

- **有名字的玩家**：**阿凯**。HoMM3 老玩家，现在用手机玩。他不需要教学，他需要"别挡着我"。
- **有名字的时刻（D-32 = 探索与经营并列，各为一等公民，二者都是「主场景」）**：

  | 时刻 | 循环 | 主面（在哪发生） | 对常驻元素的要求 |
  |---|---|---|---|
  | **探索时刻** | 点地格 → 英雄走过去 → 把东西捡起来 | **冒险地图**（全屏底层） | 地图零遮挡；终点与代价可见；推进回合（结束一天）在拇指带 |
  | **经营时刻** | 回城 → 看清资源缺口 → 决定造什么 / 招什么 → 走人 | **城镇管理面板** | **必须有与地图对等的一等入口**（常驻）；进入 ≤1 步；资源缺口在决策处可见（造价行"还差"）；出口不滚动 |

  **同时满足两者的方式（这是本规格的结构主张）：**
  1. **共用的常驻元素**（服务两个时刻）：地图（探索主面）· 顶栏只读状态（金/木/矿 + 稀有聚合槽——两地都要看；**短日期尤其属于经营**，周/日驱动周增长与"每周一位英雄"）· 结束一天（回合推进，两地共用）· 拇指带入口组。
  2. **各自按需的专属面**：探索侧 = 地图与 `armedMove`；经营侧 = 城镇管理（含建筑/招募/驻军/市场·工坊四个标签页）。
  3. **两条纪律同时适用**：**"常驻元素必须为它让路"这句话，现在对两个时刻是同一句话** —— 地图不许被挡（探索），经营入口不许被埋在探索的从属位置（经营）。
  4. **不许的结构**：把经营入口塞进"英雄面板的一个从属区块"（原方案 §3 #33 就是这么降级的）→ 那等于**默认经营是探索的附属**。已按 D-32 修正为**常驻一等入口**（见 §3.0 重校）。

- **有名字的会话长度**：**「一局 8 分钟的碎片会话」**（⚠️ **这是假设，不是实测** —— 推导见 §附录 A.2 / 开放问题 **Q1b**）。它的含义是：一局里阿凯会**开合面板很多次、每次停留很短**，所以"开合成本"必须接近 0，"看着被挡"必须接近 0。

> 一句话选题（D-32 后）：**地图是探索的一等面，城镇是经营的一等面 —— 两个面都按"最小常驻 + 按需可达"的同一套纪律办，谁都不许降级成对方的附属。**

## 2. 三层分离（意图 / 规则 / 数据，不要混着读）

### 2.1 意图层 —— 玩家想达到什么（设计目标，不涉及实现）

| ID | 意图 | 现状问题 |
|---|---|---|
| I1 | 「走过去把东西捡了」——只要结果，不要过程 | 路径/落点被事件窗口与提示条挡住（见 §9 F2/F5） |
| I2 | 「决定之前先知道代价」——这一步花多少移动力、要几天、会不会打起来 | **触屏上根本无法预览路径**（代码事实，见 §附录 B.3） |
| I3 | 「随时确认我有什么」——部队、英雄状态、城池——但**别挡地图** | 面板 46% 屏高常驻在底部（见 §9 F3） |
| I4 | 「推进时间」——今天做完了 → 明天 | 主操作在右上角且会横向漂移（见 §8 流程 D） |
| I5 | 「随时暂离 / 回来」 | 读档藏在红色「新游戏」后面（见 §8 流程 E） |
| **I6**（D-32 并列） | **「回城把事办了」——看清缺什么、决定造/招、然后回地图** | **经营入口被埋在"英雄面板最末一段"，要下拉到底**（见 §9 F3/F4）→ 经营被结构性降级为探索的附属 |

### 2.2 规则层 —— 系统怎么响应（**最小规则集，只 9 条**）

> 原则：**每加一条规则，都要能删掉一个常驻元素**。这 9 条足以覆盖 §8 的全部流程。

- **R1 地图是底层。** 任何面板都是叠加层；关闭后回到地图，且**镜头与选中英雄不变**（不许"关掉面板把地图重置了"）。
- **R2 入口 = 出口。** 一个面板只有一处入口，且由同一处的按钮、或一个常驻的「返回」关闭。不允许"入口在这里、出口在滚动流末端"。
- **R3 出口不滚动。** 任何面板的关闭 / 返回**固定在面板左上角**，不参与内容滚动。
- **R4 超 5 行就分段。** 任何面板的纵向可点元素 > 5 行时，必须切**标签页（tab）**，**不许用纵向滚动**（推导依据见 §附录 A.3）。
- **R5 高频在拇指带。** 「移动 / 出发确认 / 结束一天 / 打开英雄面板 / **打开城镇管理**」常驻**屏幕底部 48px 拇指带**，且**位置不随内容变化**（肌肉记忆）。**D-32 后"城"与"英雄"是并列的一等入口**——探索与经营各得一个常驻入口。
- **R6 低频进菜单。** 存档 / 读档 / 音效 / 光照 / 画质 / 新游戏**只存在于菜单**（一层交互可达），不常驻。
- **R7 顶栏只读、拇指带全交互。** 顶栏（≤32px）是**纯展示层、零可点目标**（`pointer-events:none`）；**所有可点入口集中在底部拇指带（≥44px）**。这条让"顶栏很矮"与"按钮要够大"两件事**不再冲突**（见 §4.2 决议）。
- **R8 确认层复用拇指带、不做 modal。** 「移动前二次确认」（D-31 = 方案 b）以 **`armedMove`** 态把**拇指带整条变形**为确认条，**额外屏预算 = 0**；因为 `tryMove` 会早退于 `isModalOpen()`（工程口径），确认层**不进 modal**，是轻量浮层。
- **R9 探索与经营并列，各有一等常驻入口（D-32）。** 「英雄」（探索侧信息）与**「城」（经营主面）**在拇指带内**同等级**常驻；**任何一方的入口都不得只存在于另一方的从属区块里**（这正是原方案把城镇管理埋进英雄面板末尾所犯的错）。

## 3. 信息分级表（**本交付物的核心 —— "剪掉没用的"的答案**）

判定口径：
- **常驻** = 默认地图界面上**永久可见**，不点任何东西就能看到。
- **按需** = 需要**一次交互**（点一下）才能到达。
- **可去掉** = 冗余、或可由他处推出、或语义错误 —— **删除或降级**。

> ⚠️ 判定标准：一个元素要成为「常驻」，必须回答 **"它凭什么永久占据 792×360 里的一块"**。答不上来的，一律按需或去掉。

### 3.0 D-32 重校（探索 / 经营并列口径下，48 项逐类复核）

**重校方法**：对每一项问两个问题 —— ①**探索时刻需要它吗？** ②**经营时刻需要它吗？** 只要**任一方**需要，它就不能因为它"偏另一方"而被降级/砍掉。**双方都不需要**的，才是真「可去掉」。

| 类别 | 重校结论 | 处置 |
|---|---|---|
| **共用信息**（资源金/木/矿、稀有、短日期、结束一天、地图、拇指带入口组） | 两地都要看 → 常驻 | **维持常驻**，并在 §3.1 标注"服务：两者" |
| **探索侧**（选中英雄、移动路径、跨天小旗、格子详情、`armedMove`、英雄面板） | 探索需要 | 维持原判（大多按需） |
| **经营侧**（建筑 / 招募 / 驻军 / 市场·工坊 / 税收·城防·增长） | 经营需要 | 维持原判（按需，但**都在经营主面之内**） |
| **经营主面的入口** | **经营需要，且是"一等公民"的判定点** | **🔧 恢复/新增一项**：**拇指带常驻「城」入口**（见 §3.4 新增 #49）。原方案把城镇管理埋在"英雄面板最末一段"= **默认经营从属于探索** → 违反 D-32，已修正 |
| **城镇页顶部资源 chip 行**（#35） | 两地都需要"看到资源"，但**该行是重复的**，且每张建筑卡已逐项列"还差" | **维持可去掉**（重校后理由变了：不再叫"与顶栏重复"，而是"经营页用**决策处可见的造价行**替代顶部堆叠，避免 7 个 chip 抢占经营首屏的 ≤5 行额度（R4）"） |
| **顶栏稀有明细下钻** | 经营时刻确实要看 4 种稀有明细 | **维持"顶栏不做下钻"**，但**重校后必须保证**：① 顶栏稀有**聚合槽常驻且不隐藏**；② 明细在**经营主面内逐项可见**（造价行"还差"）→ 经营侧的信息需求**在其自己的主面里被满足** |
| **存档 / 读档 / 音效 / 光照 / 画质 / 新游戏**（#12–15） | 两地都不需要常驻 | 维持可去掉（进菜单） |
| **「总第 Z 天」（#9）、玩家名文字（#10）** | 两地都可由他处推出 | 维持可去掉 |

**结论：重校后共 1 项恢复/新增（拇指带「城」入口），0 项被误砍**。另 2 项（#35、稀有下钻）**判定不变但论证已重写**为并列口径。会话长度假设见 Q1b。

### 3.3 英雄面板（`src/ui/HeroPanel.ts`）

## 4. 792×360 屏幕预算（**横屏手机竖向只有 360px，这条最关键**）

### 4.1 可用内容区（先算清楚"我们到底有多少地"）

```
视口          = 792 × 360            （实测）
安全区内缩    = 上40 / 下16 / 左40 / 右0   （实测 --safe-area-inset-*）
▶ 可用内容区  = (792−40−0) × (360−40−16) = 752 × 304 px
```

**关键结论：竖向只有 304px 可用，横向有 752px。→ 所有"占地方"的东西都该靠边（用横向），不能靠下（用竖向）。**
这条直接判了**底部抽屉死刑**（§9 F3）。

### 4.2 常驻区域预算表（**工程据此判断"某个元素能不能加"**）

| 常驻区域 | 位置 | **预算上限** | 占可用内容区 | 装什么 |
|---|---|---|---|---|
| 顶部状态条（**只读**） | 顶部横贯 | **高 ≤ 32px** | 面积 752×32 = **10.5%** | 金/木/矿 + 稀有聚合槽 + 短日期；**全是展示，`pointer-events:none`，零可点目标** |
| 底部拇指带（**全部交互**） | 底部横贯 | **高 ≤ 48px** | 752×48 = **15.8%** | 移动力细条(只读) + ☰菜单(44) + 英雄(44) + **城(44，D-32)** + ⚑日志(44) + 结束一天(48) |
| 右侧英雄栏 | 右侧竖条 | 宽 ≤ 200px，**默认收起为 48px** | 展开 26.6% 宽 | 英雄全部详情（分段） |

> **解法**：**把交互全部移出顶栏**。顶栏 = 纯只读状态（`pointer-events:none`）；日志入口下移到**底部拇指带 44×44**，与「结束一天」相邻 —— 语义也连贯：*结束一天 → 顺手看一眼日志*。
> **附带收益**：**取消了"用 `.tap::after` 向地图下扩 8px"这条妥协** —— 那会在顶栏正下方留出一条 8px 的"想点地图却触发按钮"的死区；现在不需要了。
> **代价（明说）**：顶栏不再能直接下钻 4 种稀有资源明细。但这正是**"按需"**的定义，且造价行已逐项列出"还差"（`TownDialog.ts` 的 `buildStateLine`），信息不丢。

**四条硬约束（可写进验收）：**
- **C1**：默认态（无面板）地图可见面积 **≥ 72%** 可用内容区（按 32+48 chrome 实算 = **73.7%**）。
- **C2**：任何单个面板展开时，地图仍有 **≥ 54%** 可见。
- **C3**：**禁止任何常驻元素引发横向滚动**（现顶栏 `overflow-x:auto` 必须移除）。
- **C4**：**顶栏内不得出现任何可点元素**（R7）—— 这条是可机检的。
- **C5**：**`armedMove` 确认条出现时，地图可见面积不得下降**（因为它复用拇指带；若改用"目的地旁气泡"兜底形态，则按 ≤120×48 计入，且仍须满足 C1）。

> **轻量浮层 vs modal（工程口径，影响实现）**：`tryMove` 会早退于 `isModalOpen()`，且边缘滚屏 `shouldEdgeScroll` 用**同一个闸**。所以 **`armedMove` 确认条不得进入 modal** —— 它只是一个普通浮层（只挂边缘滚屏闸），否则会连带禁掉地图交互与边缘滚屏。只有 **城镇 / 魔法书 / 设置** 三类走真 modal。这条同时解释了为什么"点别处取消"能成立：确认条存在时地图仍可点。

## 5. 尺寸与密度规则（基于实测 **p90 = 23px** 落点散布）

### 5.1 前提（实测）

- 真人手指点击最小按钮：**误触 0/8，但落点偏差 p50 = 13px / p90 = 23px**。
- 最小的 `宝物▾` = **40×32 CSS px**，半宽 20px，手指落在离中心 19px 处 → **横向余量仅 1px**。

**⇒ 结论：不能按"能不能点中"设计，要按"p90 = 23px 会偏出去"设计。**

### 5.2 最小目标尺寸（推导）

要让"落在本目标内"不为 p90 误差所破，目标**半宽**需 ≥ p90：

```
半宽 ≥ 23px  ⇒  边长 ≥ 46px  ⇒  取整 48px（并留 2px 余量）
```

| 层级 | 最小尺寸 | 用途 |
|---|---|---|
| 主操作 | **≥ 48 × 48** | 结束一天、建造、攻击、确认 |
| 常规按钮 | **≥ 44 × 44** | 菜单、面板开关、招募 |
| 密集区元素 | **≥ 40 × 40**，且**中心距 ≥ 48px** | 部队格、宝物格、市场网格 |
| 纯展示 chip（不可点） | 允许 ≤ 32，但**必须 `pointer-events:none`** | 资源数字、状态标签、**整个顶栏** |

**5.2.1 命中区 ≠ 精灵渲染尺寸（美术侧硬约束，实现说明必须写进去）**

- 按钮**盒子**尺寸（40 / 44 / 48）只是**命中区**，与其中**图标本体**的尺寸**解耦**。
- 图标是 **24×24 画布**的图集精灵（`asset-spec.md` §1.2：加 1px 描边后 16×16 只剩 14×14 可用，故定 24）；像素画**只能整数倍**放大（`cartoon-style.md` §1.3 / §8.4：非整数缩放会让像素行列宽窄不均，硬边立刻发毛）。
- ⇒ **图标本体只允许 24×24（1×）或 48×48（2×）两档**，居中留白补齐。**36、44 等非整数倍禁止用于图标本体** —— 44px 盒子只能放 24 图标，只有 ≥48px 盒子才可放 48 图标。
- 落位核对：32px 只读 chip → **24×24 图标 + 4px 边距** ✅；48px 拇指带按钮 → **24×24 或 48×48** ✅。

### 5.3 相邻间距规则（推导）

设目标边长 S、相邻间隙 `gap`，要"点 A 不落进 B"，需 `S/2 + gap ≥ p90 = 23`：

| S | 允许的最小 gap |
|---|---|
| 48 | **≥ 0**（自然满足） |
| 44 | ≥ 1px |
| 40 | **≥ 3px** |
| 32 | ≥ 7px |

**⇒ 现状违规（两类，同一病根：横向相邻按钮太矮）**：
- `宝物▾ 40×32`（`HeroPanel.ts`，与 `‹ ›` 横向相邻，实测余量仅 1px）→ 违规；
- `.btn.tiny` 全局 `min-height:32px`（`style.css:648`）被用于**横向相邻按钮行**（城镇招募行 4 个：招1 / 招5 / 全招 / 驻军）→ 同违规。

**⇒ 修法（一处改、全站生效）**：把 `.btn.tiny` 最小高度 **32 → 40**，横向 gap 保证 **≥ 4px**（S=40 需 gap ≥ 3），再靠 `.tap::after` **只纵轴**扩 4px → 命中高 48。招募行若 4 钮排不下，改 **≤ 3 钮/行**。

**⇒ 禁则**：**不允许出现高度 < 40px 的横向相邻按钮**。允许的例外：现有 `.tap::after` **只纵轴**扩命中区，**且仅在纵向最近邻 ≥ 14px 时可用**；横向**永不**扩（会与邻钮命中区重叠）。

### 5.4 密集区怎么办（R4 的数值化）

竖向 304px 里：标题 ~48px + 每行 48px ⇒ **一屏最多 5 行可点元素**（5×48 = 240 ≤ 256）。

- **> 5 行 → 分段（标签页），不滚动。**
- 若确实需要更多，用**标签页 ≤ 5 个**，每个标签页内 ≤ 5 行。

```
│    └─ 画质：自动 / 低 / 中 / 高  （原顶栏「画质」弹窗）
├─ 回到开始页
└─ 新游戏  ⚠️危险色 + 二次确认  （原顶栏「新游戏」）
```

规则：**一级 ≤ 6 项，二级 ≤ 4 项**；危险项永远放最底并二次确认。

## 8. 操作流程规格（5 条，标注"最少必要步数 vs 当前实际步数 + 摩擦点"）

> 「步数」= 玩家的**独立交互动作数**（点一下 / 滑一次算 1 步）。只读的"看一眼"不计步。

### 流程 A：移动英雄并捡宝（**主场景**）

- **意图**：把英雄走到一处资源/宝箱上，自动拾取。
- **最少必要步数：2**（① 点目标格 → ② 点「出发」确认）。**已由用户拍板 D-31 = 方案 (b)**：宁可多 1 步，换取"移动前看得见路径与消耗"（意图 I2）。英雄默认为 `heroOrder[0]` 已选中，故不额外计步。
- **当前实际步数：1–2**（当前选中的不是想要的英雄时，需先点该英雄再点目标 → +1）。**注意**：现状是"点了就走"，代价是**触屏永远看不到路径与消耗**（`shouldHover` 只对 mouse/pen 放行，附录 B.3）。
- **摩擦点（5 条）**：
  1. **触屏永远看不到路径预览** → 违反 I2，凭感觉点（D-31 就是冲它来的）。
  2. 目标格若落在左上事件窗口下（实测该窗口在 ≤860px 下为 **220px 宽**）→ **看得见挡、看不见格**；且 `pointer-events:none` 让点击照样生效 → **"看不见但点得中"**，最坏组合。
  3. 每次 hover/点击都改写底部提示条 → 文字闪烁（已判"可去掉"）。
  4. 移动力耗尽后提示"点右上角结束一天"，但顶栏 `overflow-x:auto`，**该按钮可能需横向滑动才能点到**。
  5. 长按当前被"查看格子"占用（`main.ts` 的 `longPress` → `showTileInfo`）—— (b) 不走长按，故**长按语义保持不变**，不冲突。

- **重设计后目标（按 (b)）**：
  - 点目标格 → 进入 **`armedMove`（待确认移动）** 态：地图上**画出路径**，**拇指带整条替换为确认条**（见下）。点「出发」执行；点「取消」/ 点别处 / 物理返回键撤销。
  - **确认条形态（UX 定稿）：复用底部拇指带，不新增一条、不做 modal。**
    - 原因：`tryMove` 会早退于 `isModalOpen()`，且边缘滚屏用同一闸（工程口径）→ 确认层**不进 modal**，就是普通浮层；又因 `armedMove` 是短暂态，**整条拇指带变形**即零额外占地。
    - 版面（单行，48px 内）：左＝`→ (12,7) · 3.5 移动力 · 今日可达 / 约 2 天`；右＝`[取消]`(44) + `[出发]`(48)。
    - ⇒ **额外屏预算 = 0**（复用既有 48px 拇指带）；`armedMove` 期间 ☰/英雄/城/⚑/结束一天 隐藏（避免误触），取消后原样恢复。
    - 备选形态（若工程发现拇指带放不下两行）：**目的地旁小气泡**，但需接受"浮层压在地图上、位置随目标变"两个缺点 → 本规格**不推荐**，保留为兜底。
  - **取消路径（3 条，都要能验收）**：① 确认条「取消」；② 点地图别处（改目标 = 重设 `armedMove`，点不可达处 = 撤销）；③ Android 物理返回键（优先撤 `armedMove`，见 Q5）。
- **验收**：
  - 点目标后**在不移动英雄的前提下**，可见到 路径 / 消耗 / 今日能否走完；点「出发」才动。
  - 主场景全程**无需移动镜头、无需滚动任何条、目标格不被任何常驻元素覆盖**。
  - 确认条出现期间**地图可见面积不下降**（因为它复用拇指带，C1 守恒）。
  - 三条取消路径都生效。

  **状态图（常态 ↔ `armedMove`）—— 拇指带是同一块地被换内容，不是"多出一层"：**

  ```
  ┌─ 常态 ─────────────────────────────────────────────┐
  │  [移动力] [☰] [英雄] [城] [⚑] [★结束一天]           │
  └──────────────┬─────────────────────────────────────┘
                 │ 点地图目标格（路径画在地图上）
                 ▼
  ┌─ armedMove ────────────────────────────────────────┐
  │  [ → (12,7)·3.5力·今日可达 ]      [取消] [出发]     │  ★ 结束一天 在此态不可用
  └──────────────┬─────────────────────────────────────┘
                 │ ①「取消」 ② 点别处 ③ 物理返回键
                 ▼  点「出发」→ 执行移动 → 回到常态
  ┌─ 常态（原样恢复）───────────────────────────────────┐
  │  [移动力] [☰] [英雄] [城] [⚑] [★结束一天]           │
  └────────────────────────────────────────────────────┘
  ```

  > ⚠️ **行为后果（唯一副作用，必须写出来）**：`armedMove` 期间**无法「结束一天」**，因为该按钮的位置被确认条占用了。回去只需 **≤1 步**（取消/返回键），故可接受；但它确实是玩家可能察觉到的行为差异，**不许藏在实现里**。

> ⚠️ **命名（工程口径）**：本文说的"待确认移动"对应代码里的 **`armedMove`**，**不是** `pendingDest`（后者=跨天行程目的地，今日走不完→插旗→按 M 继续，两个不同状态，勿混接）。

### 流程 B：查看英雄详情

- **最少必要步数：1**（打开英雄面板）。
- **当前实际步数：1 + 纵向滚动若干**（面板在底部抽屉占 46% 屏高，内容超一屏；移动力/部队/城池散落其中）。
  - 额外硬伤（推导）：面板收起时容器 `max-height:34px + overflow:hidden`，而其中的开合按钮 `min-height:44px` → **按钮被裁到 34px，可点区连带被砍** → 违反 §5.2。
- **重设计后目标**：1 步打开右侧抽屉；**首屏不滚动**即含 移动力 / 部队 / 城池入口。
- **验收**：打开后**不滚动**即可读到 移动力 + 部队 + 城池入口；抽屉每次都在同一位置。

### 流程 C：进入城镇管理并**关闭**（经营时刻，D-32 一等公民）

- **最少必要步数：2**（进入 1 + 关闭 1）。
- **当前实际步数：4–5**：
  1. 展开底部抽屉；
  2. 把抽屉**滚到底**（城池列表是面板最后一段）；
  3. 点「管理」；
  4. 干完活后，**把弹窗滚到底**（`关闭` 在 `.actions`，而 `.modal{overflow-y:auto}` → 出口随内容滚走）；
  5. 点「关闭」（或在遮罩上点一下）。
- **重设计后目标（D-32）**：
  - **拇指带「城」= 直达（1 步）** —— 经营不必再"先展开英雄面板 → 下拉到底 → 点管理"；这是"并列一等公民"在流程上的体现。
  - **左上固定「←」= 关闭（1）**；内容用标签页，不依赖滚动。
  - 多城时「城」开"最近/选中英雄所在城"；其余城镇：地图上点城主塔，或从英雄面板城池列表进（**两条路并存，但都不是唯一入口**）。
- **验收**：**任意滚动位置都能 1 步关闭**；从主界面进入任己方城镇 ≤ 1 步（拇指带）或 1 步（地图城主塔）；城镇页内不出现堆叠式资源 chip 行。

### 流程 D：结束一天

- **最少必要步数：1**。
- **当前实际步数：1（若按钮在视口内）/ 1 + 横向滚动**。
- **摩擦点**：主操作放在**右上角** —— 横屏双手握持时，右上是最远、最不稳的点；且随顶栏横向滚动**位置漂移** → 肌肉记忆失效；按钮尺寸 54×75 与邻居 44/45 不一致（"大的大，小的小"）。
- **重设计后目标**：固定在**底部右侧拇指圈，48px**，永不随内容移动。
- **验收**：单手（右手）握持时，拇指不移动手掌即可点中；该按钮在**任何状态下位置固定**。

### 流程 E：存档 / 读档

- **最少必要步数**：存档 = **0**（已自动）/ 1（手动）；读档 = **1**。
- **当前实际步数**：
  - 存档 = 1（顶栏「存档」），但**冗余**（附录 B.4）；
  - 读档 = 点「新游戏」(danger) → 开始页 → 「继续」= **2 步，且入口语义错误**（红色"新游戏"暗示要丢档）。
- **重设计后目标**：菜单里 `存档 / 读档 / 回主菜单` 三者语义分明；**「新游戏」单独、二次确认**。
- **验收**：从主界面到"读取最近存档" ≤ 2 步；"新游戏"必须二次确认，且不会与"继续"混淆。

## 9. 对 5 条反馈的逐条处置（方案 + 为什么 + 验收标准）

### F1 「顶部控制栏东西非常多，大的大、小的小，很多没什么用」

- **方案**：顶栏拆成 **(a) 只读状态条（≤32px，金/木/矿 + 稀有聚合槽 + 短日期，**零可点目标**）** 与 **(b) 拇指带交互组（☰/英雄/城/⚑/结束一天） + 菜单（R6 收纳 存档/音效/光照/画质/新游戏）**；统一尺寸档（§5.2）。
- **为什么**：用户的"大的大、小的小"= 视觉层级混乱 + 尺寸不达标；且**低频项常驻零收益**（§3.1 逐项判定）。
- **验收**：顶栏可点/信息块 **9 → 5**；**顶栏内零可点元素**（C4）；所有可点目标 ≥ 44px；同一行高度差 ≤ 8px；**移除 `overflow-x:auto`，752px 内不产生横向滚动**（C3）。

### F2 「事件窗口一直在滚动，挡住地图的一部分，像测试版」

- **方案**：`#logbox` 从"常驻悬浮块"改为 **(a) 收起态 = 底部拇指带内 44×44「⚑未读 N」**（**不放顶栏**，理由见 §4.2 决议 R7：顶栏只读、且 32×32 放不下 44 的目标）；**(b) 展开态 = 点开后从右侧滑出面板**（复用英雄栏位置），显示最近若干条，点外部关闭。**移除 `pointer-events:none`**（要可交互）。
- **为什么**：日志是**低频回顾**（但"未读指示"值得常驻）；而现状把一块 UI 压在**地图左上**这一最贵位置（主场景的起点视野），**视觉上就是"测试版"** —— 它不参与任何主交互，却永久占位。
- **验收**：默认态地图左上角**无任何遮挡**；日志入口为 **44×44 且与「结束一天」相邻**；展开时**不覆盖地图中央**；日志块不再是 `position:absolute` 悬浮于 stage 左上。
- **备注（对证据的修正）**：实测该块在 **≤860px 断点下宽度为 220px**（`style.css:758`），即 **220/752 = 29.3%** 内容宽（桌面 300px/792 = 38%）。无论 29% 还是 38%，都不该常驻。

### F3 「面板在左下角，查看什么要一直下拉，管理城池要拉到底」

- **方案**：**废弃底部抽屉**（删除 `@media(max-width:860px)` 里把 `#side` 变成 `bottom:0; max-height:46%` 的规则），改为**右侧垂直栏**（宽 ≤200px，默认收起为 48px 竖条）；**探索与经营各给一个常驻直达入口**（拇指带「英雄」/「城」，D-32）；城池在面板内**独立入口**，不再排在列表末尾。
- **为什么**：**根因是方向反了** —— 横屏竖轴稀缺（304px），而断点把侧栏变成"用最缺的轴"的底部抽屉（46%×304 ≈ 140px）。横向有 752px 富余，**面板就该放侧边**。**D-32 补充**：原设计的"城池列表在英雄面板最末一段"还把**经营**做成了探索的从属 → 已修正为并列常驻入口。
- **验收**：英雄详情**首屏（不滚动）**含 移动力 + 部队（城池另走「城」直达）；从主界面进入城镇管理 ≤ 1 步；**任何面板的入口/出口都不依赖纵向滚动**。

### F4 「城市管理页面东西非常多，而且要滚到底才能关闭」

- **方案**：**① 关闭/返回固定左上角（sticky，不随内容滚动）**；**② 内容分段为标签页**（建筑 / 招募 / 驻军 & 部队 / 市场 · 工坊），每页 ≤ 5 行可点元素；**③ 删掉顶部堆叠式的资源 chip 行**（改由建筑卡造价行承担）。
- **为什么**：**关闭按钮是"出口"，出口不能待在滚动流的末端**（R3）；内容多本身不是错，错在**长滚动 + 出口在流末端**。删 chip 行不是因为"与顶栏重复"，而是**经营首屏的 ≤5 行额度**要留给建筑卡（决策处信息）。
- **验收**：**任意滚动位置 1 步关闭**；单页纵向可点行 ≤ 5；城镇页**不出现堆叠式资源 chip 行**，但每张建筑卡的"还差"逐项可见。

### F5 「总体操作非常不方便 —— 剪掉没用的、页面再干净些」

- **方案**：**① 拇指区原则**（R5）：**全部高频操作**（移动 / 出发确认 / 结束一天 / 打开英雄面板 / **打开城镇管理**）落到屏幕**底部 48px 拇指带**且位置固定；**② 低频全部进菜单**（R6）；**③ 触屏补上"移动前可见代价"** —— 按用户拍板 **D-31 = 方案 (b)**：点目标后进 `armedMove` 态、拇指带变形为确认条（R8），确认才走。**④（D-32）** 经营获得与探索同级的常驻入口，不再从属于英雄面板。
- **为什么**：把"剪掉没用的"落地成两件可测的事 —— **提高信噪比**（§3 分级表）+ **让操作落在手指够得着、且位置不变的地方**。现状的问题是：主操作在最远的右上，低频项在最顺手的顶栏，正好**全反了**。
- **验收**：单手握持时，**移动 / 出发确认 / 结束一天 / 打开英雄面板 / 打开城镇管理 全部落在下缘 48px 带内**；顶栏不再出现任何"一局用不到"的开关；触屏在**移动英雄之前**可见 路径 + 消耗 + 今日能否走完（D-31）；`armedMove` 态下地图可见面积不下降（C5）；**经营主面 ≤1 步可达**（D-32）。

## 10. 按画质档位的行为（对接现有 `quality.ts` 三档）

原则：**UI 布局与"操作位置"绝不随档位变化**（位置稳定对肌肉记忆是硬要求）；**只有渲染相关的开关随档。**

| 元素 | low | mid | high | 说明 |
|---|---|---|---|---|
| 昼夜光照开关 | **隐藏 / 置灰** | 可用 | 可用 | low 档 `lighting` 恒为 `multiply` → 开关无意义，显示反而误导 |
| 网格线 / 暗角 / 暖光 开关 | 随档显示可用性 | 同左 | 同左 | 若放进设置，按当档实际生效项显示 |
| 顶栏 / 拇指带 / 面板布局 | **不变** | **不变** | **不变** | 位置稳定性优先 |
| 事件日志自动弹出的行数 | 1 行 | 2 行 | 2 行 | 仅影响叠加层高度，**不得改变地图可见 ≥72%**（C1） |
| 地图尺寸上限 | 32 | 40 | 48 | 已在开局 clamp，UI 无需额外处理 |

## 11. 假设与开放问题（**明确列出，不埋**）

**假设（请确认或推翻）**

- **A-1（会话长度 · 对应开放问题 Q1b）**：一局 ≈ 8 分钟碎片会话。**这不是实测**，是从"移动端 + 单机 + 无联机"推导的假设。若真实会话远长于此（例如一坐 40 分钟），则"面板开合成本"的权重会下降，但**"地图不被遮挡"与"经营入口不埋深"两条权重只会上升** —— 本规格的其余结论不变。

**开放问题（需用户 / 工程拍板）**

- **Q1a（已闭合 · 用户拍板 D-32）**：**"主场景"认定 = 探索与经营并列，各为一等公民**（不再是"只有探索"）。已据此刻重写 §1、加规则 **R9**、**重校 §3 全表**（见 §3.0，恢复 1 项）、把经营主面提到拇指带一等入口。
- **Q1b（仍开放 · 需用户确认）**：**会话长度**"一局 8 分钟"依然是**假设**（见 §1 / 附录 A.2）。若真实会话远长于此，则"面板开合成本"权重下降，但**"地图不被遮挡"与"经营入口不埋深"两条权重只会上升** —— 本规格其余结论不变。
- **Q2（已闭合 · 用户拍板 D-31 = 方案 (b)）**：触屏"移动前可见代价"采用 **点选目的地后二次确认（2 步）**：点目标 → `armedMove` 态（画路径 + 拇指带变形为确认条）→ 点「出发」才走。落点：§8-A 最少必要步数 **1 → 2**；§4.2 新增确认条额度行（**额外占用 0**）；规则 **R8**。
  - 原始候选存档：**(a)** 长按拖动预览松手执行（与"长按查看格子"冲突，未采纳）；**(c)** 仅对"今日走不完"的长距离移动弹确认（未采纳）。三者均**不引新依赖**（现有 `pointerdown/move/up` 已足够）。
  - ⚠️ 该决策的代价明说：**每一次移动都多 1 步**。已用三处设计把摩擦压到最低 —— 确认条**位置固定**（不用找）、**无需滚动**、**取消有三条路径**（含物理返回键）。若日后觉得太频繁，可再议"仅长距离强制确认"（但那等于退回 1 步，需用户重新拍板）。

- **Q6（已闭合 · 美术定）**：顶栏短日期字形 = **`3周2日`**（无空格 / 无「第」），**不加日历图标**（顶栏其它项已是"图标+数字"语法，再加图标更挤；日期用纯文字反而是唯一区分点）。宽 ≈39px、最坏 `15周4日` ≈52px，**≤88px 额度** ✅。**实现必须 `font-variant-numeric: tabular-nums`，或给日期槽定死宽度 + 居中** —— 字体栈是比例数字，否则每周/日数字一变整条顶栏会抖动。
- **Q7（已结案 · team-lead 已拍顺序）**：**先尺寸批、后 UI 重构批**。`style.css` 是跨域共享文件，**同轮只能一个写者**（= engineering-lead），所以这不是"同批还是分两批"的选择题，只有先后。
  - **尺寸批（先）**：`.btn.tiny` 32→40、`宝物▾` ≥40、`.btn` 与 `.btn.tiny` 特异性冲突、**`#side.collapsed` 把 44px 按钮裁到 34px**（**本条并入尺寸批，不单列**）。
  - **UI 重构批（后）**：HUD 九项拆分 / 拇指带 / 右侧栏。

### A.3 由"5 行上限"得出"分段不滚动"的依据

竖向可点空间 = 304px；标题占 ~48px；每行按钮按 §5.2 取 48px ⇒ `(304−48)/48 = 5.33`。
**⇒ 一屏最多 5 行可点元素。** 超出即必须分段（R4），否则必然要滚动，而滚动 = "拉到底"摩擦（F3/F4）的根源。

### A.4 `armedMove` 确认条的屏预算 = 0 的推导

确认条**复用**底部拇指带（原 48px 已计入 C1），故 `额外占用 = 0`；`armedMove` 期间地图高仍为 `304 − 32 − 48 = 224px` ⇒ **C1 守恒**（C5 即此意）。
对照：若改用"目的地旁气泡"兜底形态，按 ≤120×48 = 5,760px² ⇒ 约占可用区 **2.5%**，且浮层压在地图上（不推荐）。

## 附：本规格的"最小性"自检

| 常驻元素 | 凭什么永久占 792×360 的一块 |
|---|---|
| 地图 | **探索主面**（D-32 一等公民之一） |
| 金/木/矿（顶栏·只读） | 两地共用；每次建造/招募决策都要看 |
| 稀有聚合槽（顶栏·只读） | 两地共用（经营为主）；一个 24×24 图标槽换掉 4 个并列格 |
| 短日期 `3周2日`（顶栏·只读） | **经营节奏的刻度**；周/日驱动周增长与每周一位英雄 |
| 结束一天（48px·拇指带） | 两地共用的回合推进；最高频主操作 |
| 英雄入口（44px·拇指带） | 探索侧信息面的唯一切入点 |
| **城入口（44px·拇指带，D-32 新增）** | **经营主面的一等常驻入口**（R9）—— 没有它，经营就只能从英雄面板末尾进入 = 结构性降级为探索的附属 |
| 菜单入口（44px·拇指带） | 全部低频项的唯一切入点 |
| 日志角标（44×44·拇指带） | 一个 44px 入口，换掉 220px×30% 的地图遮挡 |
| 移动力细条（拇指带·只读） | 探索时刻规划一切的前提 |

> 顶栏 4 项**全是只读**（`pointer-events:none`）→ 不参与 §5.2 的尺寸约束；可点目标**全部**在拇指带内，且都 ≥44px。**拇指带共 6 件**（移动力细条 + ☰ + 英雄 + 城 + ⚑ + 结束一天）；宽度核对：44×4 + 48 + 细条 ≈ 224 + 细条，可用宽 752 ✅ 富裕。

> **`armedMove` 确认条不在此表**：它不是常驻元素（只在待确认的那一瞬间出现），且**复用**拇指带、额外占用为 0（§A.4）—— 所以它**不需要**"凭什么永久占位"的论证，只需论证"为什么是复用而不是新增"（R8）。

**其余全部为按需。** 新增任何常驻元素，都必须先在 §4.2 预算表里找到额度并给出同样的理由。
